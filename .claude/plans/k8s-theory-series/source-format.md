# ☸️ 원본 노트 형식과 변환 지침

> 원본 노트가 어떤 규칙으로 쓰였는지, 그중 무엇을 블로그로 가져오고 무엇을 버리는지.
> 2026-09-08 원본 형식 조사에 기반하며, 2026-10-21에 말투·배치 절차를 갱신했다
> 실제 변환은 최신 노트를 읽고 적용한다. 아래 템플릿·개수·분류 사례가 현재 원본과 같다고 가정하지 않는다

먼저 [공통 말투·편집 기준](../../../docs/writing-voice.md)을 읽는다
문체 예시·고정 문단 수·상투적인 맺음말은 공통 기준보다 우선하지 않는다
3편 선택, 검증, 진행 기록은 [plan.md](plan.md)의 5·7절을 따른다

## 1. 원본 노트의 11절 템플릿

원본 `☸️ 문서 형식.md` 4절 「개정된 세션 노트 형식」에서 그대로 옮긴다.

```text
  [1] 이 세션이 답하는 질문        one line
  [2] 요청 하나를 끝까지 따라가기   STORY diagram. always first.
  [3] 각 단계에서 무슨 일이         one concept per heading
  [4] 왜 이 순서인가                the "why", after the "what"
  [5] 실패하면 어디서 멈추나        the triage table
  [6] 이 세션에서 나온 개념         one-line def + [G]
  ------------------ 본문 끝 ------------------
  [7] 종료 조건 판정
  [8] LAB TODO                     one line each, with observation
  [9] SOURCE DIVE                  code paths live HERE, not above
  [10] 한 단계 더                   bridge line + 심화 질문
  [11] 이어지는 것                  all forward references collected
```

원문의 핵심 문장 — **"[6]까지가 본문이고 [7]부터는 부속"**.
이 경계가 블로그 변환에서도 그대로 살아난다. 부속을 어떻게 처리할지가 변환의 절반이다.

노트 맨 위의 좌표·등급·학습 상태 등 관리 메타는 본문에서 빼고 블로그 front matter를 작성한다
원본 좌표·파일 대응과 읽은 기준본은 plan의 진행 기록에 남긴다

```text
- 좌표: Phase 1-1
- 예상: 2~3h / 실제: —
- 상태: O
- 관련: [[☸️ progress]] · [[☸️ glossary]] · [[☸️ concept-map]]
```

## 2. 절별 처리 방침

| 절 | 원본 내용 | 블로그 처리 | 이유 |
|---|---|---|---|
| 메타 5줄 | 좌표·예상·상태·관련 | **버림** → front matter | 학습 진도 관리용 |
| [1] 답하는 질문 | 한 줄 질문 | **도입부로 승격** | 그대로 글의 후크가 된다 |
| [2] 요청 따라가기 | story 다이어그램 | **본문 유지** · 대개 SVG 1순위 | 이 시리즈의 서사 뼈대 |
| [3] 각 단계 | 소제목당 한 개념 | **본문 유지** | 분량의 대부분 |
| [4] 왜 이 순서인가 | 설계 근거 | **본문 유지** | 가장 가치 있는 부분 |
| [5] 실패 판별 | 상태코드 표 | **본문 유지** · 표 그대로 | 이미 markdown 표다 |
| [6] 나온 개념 | 용어 정의 | **본문 유지** 또는 말미 정리 | `[G]` 마커만 제거 |
| [7] 종료 조건 판정 | 자가 점검 | **버림** | 학습 도구. 독자에겐 의미 없음 |
| [8] LAB TODO | 미실행 실습 목록 | **본문에서 제외** | 실행한 결과처럼 바꾸지 않음. 원본의 실습 계획은 Vault에 보존 |
| [9] SOURCE DIVE | `[S]` 코드 경로 | **각주/말미로 축약 유지** | 이 시리즈의 근거 그 자체. 버리면 안 됨 |
| [10] 한 단계 더 | 다리 한 줄 + 심화 질문 | 새로운 질문·필요한 연결만 유지 | 앞의 설명 반복이나 상투적인 예고라면 생략 |
| [11] 이어지는 것 | wikilink 목록 | **버림** → 시리즈 navigation이 대체 | 블로그가 자동 제공 |

[9]를 남기는 게 중요하다. 소스와 공식 문서가 설명의 근거다
본문 이해에 필요한 가정·경계 조건·확인하지 못한 주장을 학습 관리용 부록과 함께 삭제하지 않는다

## 3. 원본의 표기 관례

### `[S]` — 소스 경로

```text
  [S] <repo root 기준 경로> :: <심볼>
```

9월 원본에서 확인한 표기 관례다. 현재 기준 버전은 편별로 다시 확인한다

| 항목 | 결정 | 이유 |
|---|---|---|
| 브랜치 | 당시 `release-1.35` | 릴리스 범위 표시. 브랜치도 갱신되므로 불변 근거가 필요하면 확인한 commit으로 연결 |
| 앵커 | 심볼명과 경로 | 줄 번호만 적는 것보다 찾기 쉬움. 심볼·경로도 버전별로 존재 확인 |
| 저장소 | `kubernetes/kubernetes`의 `staging/src/...` | `kubernetes/client-go`는 읽기 전용 발행 대상. 히스토리와 리뷰는 staging에 있다 |

원문 경고 — **"경로는 적기 전에 존재를 확인한다. 추측해서 적지 않는다."**
Phase 1-1 초안에서 `BeforeCreate`를 `store.go`라고 적었다가 실제로는
`registry/rest/create.go`인 걸 발견한 사고가 이 규칙의 계기였다.

**변환 시에도 동일하게 적용한다.** 블로그에 옮길 때 경로를 다시 확인하고,
확인 못 하면 경로를 추측하지 않는다
진행 기록에 확인 필요로 남기고 핵심 주장을 검증할 수 없으면 해당 글을 검수 완료로 표시하지 않는다
고정 버전 소스와 최신 공식 문서를 섞어 하나의 버전에서 모두 성립한다고 쓰지 않는다

### `[G]` — glossary 마커

`APF[G]` 처럼 붙는다. "더 자세한 건 glossary에 있다"는 표시일 뿐이다.
원본 규칙상 **본문만 읽어도 뜻을 알 수 있어야** 하므로 첫 등장에 한 문장 정의가 붙어 있다.

```text
  WRONG   APF[G]가 authn 뒤에 있다
  RIGHT   APF(과부하 시 어떤 요청을 기다리게 하고 어떤 요청을 거절할지
          정하는 층)[G]가 authn 뒤에 있다
```

블로그에서는 **`[G]` 마커만 떼고 괄호 정의는 그대로 살린다.** vault glossary가 없는
독자에게는 그 괄호가 유일한 정의다.

### 코드 — 설명하는 코드만 넣는다

원본 5절이 "설명 코드"와 "절차 코드"를 가른다. 이 기준은 블로그에서도 유효하다.

| 넣는다 (개념을 설명) | 안 넣는다 (작업을 지시) |
|---|---|
| `cpu.max = "50000 100000"` — 개념이 무엇이 되는가 | `1. KinD 클러스터 생성 2. apply 3. 확인` |
| `volumeBindingMode: WaitForFirstConsumer` — 필드가 어디 사는가 | 전체 매니페스트 |
| `kubectl get --raw /apis/apps/v1` — 어디에 드러나는가 | 예상 출력 블록 |
| 5~10줄 yaml 조각 — 필드 하나를 맥락과 함께 | 트러블슈팅 결정 트리 |
| **에러 메시지 원문** | |

에러 메시지 원문이 예외인 이유가 원문에 명시돼 있다 — 그건 출력이 아니라 **판별 재료**다.
`admission webhook "..." denied`와 `cannot create resource "..."`를 구분하는 것이
Phase 1-1의 산출물인데, 원문 없이는 그 표를 만들 수 없다.

## 4. 원본의 서술 원칙 — 변환 시 보존할 것

`문서 형식` 1절에서 채택한 7개 중 블로그에도 그대로 적용되는 것들.

1. **구조를 먼저 선언하지 않는다** — "사실 두 층이다"로 시작하지 말고, 요청 하나를
   끝까지 따라가면 두 층이 저절로 드러나게 한다
2. **요청 흐름이 보이는 story diagram** — 박스에는 처리 주체·역할을, 화살표에는 전달 정보나 질문을 넣는다
   `"누가 보냈나"` 같은 질문이 실제로 누가 무엇을 판단하는지 가리지 않게 한다
3. **한 섹션 = 한 개념** — 소제목 하나가 강의 넷이 되면 쪼갠다
4. **제목이 질문이면 첫 문장이 그 질문에 정확히 답한다** — 답의 요약이 아니라 답

2번은 요청 흐름 SVG에 적용한다. 구조나 관계 자체를 설명하는 그림에는 그 목적에 맞는 형식을 쓴다

## 6. 어투 변환

본문 서술은 격식체로 다듬고 문장·문단·bullet 끝 마침표를 생략한다
URL·버전·코드 내부는 예외다. 한 단락에 한 생각을 담되 문장 길이나 개수를 기계적으로 맞추지 않는다
원본의 질문·설명 이유·미확인 조건을 보존한다. 개인 경험이 없는 글에 실습·실패·감정을 보태지 않는다
짧은 원문 독백을 인용할 수는 있지만, 말투를 살린다는 이유로 새 독백을 만들지 않는다

```text
원본
  첫 구간의 심판들은 바디를 안 연다. 토큰과 URL과 헤더만 본다.
  오브젝트는 두 번째 구간의 첫 단계에서 처음 생기고, 그때부터 고칠 수 있게 된다.

변환
  첫 구간의 심판들은 바디를 열지 않습니다
  토큰과 URL과 헤더만 봅니다

  오브젝트는 두 번째 구간의 첫 단계에서 처음 생기고, 그때부터 고칠 수 있게 됩니다
```

위 예시는 어미 변환의 예다. “심판” 같은 비유는 실제 구성요소와 역할을 독자가 알 수 있는지 검토하고 필요하면 구체화한다
50자는 참고치다. 이유·조건을 잘라 문장을 맞추거나 모든 문장을 같은 길이로 만들지 않는다
` ```text ` 블록 **안쪽**은 마침표 규칙 대상이 아니다.

과장·직역·근거 없는 단정·반복 안내·내부 맥락은 공통 기준으로 문맥 검수한다
표의 모든 행을 산문으로 반복하지 않고, 그림 아래 설명은 이해에 필요한 관계·조건에 쓴다
기술 용어·API·설정 키는 보존하고 처음 나오는 용어만 필요한 만큼 설명한다
형식 검사는 `npm run lint:post -- <file>`, 사실·문체 검수와 배치 빌드는 별도로 수행한다

## 7. 근거 등급 고지 — 도입부에 붙일 것

각 글 상단에 소스·문서 기반 해설이라는 근거 범위를 명시한다
`src/content/essays/kubernetes/cloud-virtualization-double-tax.md`가 이미 쓰는 패턴이다.

```markdown
> **근거**: Kubernetes 소스와 공식 문서를 바탕으로 설명합니다
> 기준 버전과 소스 ref: [해당 편에서 실제 확인한 버전·ref]
> 클러스터에서 재현한 실측 기록은 포함하지 않습니다
```

대괄호 부분은 실제 확인값으로 채우고, 확인하지 못했다면 검수 대기로 남긴다
`release-1.35`나 “v1.35 공식 문서”를 모든 글에 자동으로 붙이지 않는다
서로 다른 버전의 자료를 비교하는 글은 각 자료의 범위를 구분한다
세부 URL·심볼은 근거 절에 두어 고지 자체가 장황해지지 않게 한다

## 8. 원본에서 근거를 못 잡은 3건 — 단정 금지

2026-09-08 조사에서 `☸️ progress.md`가 「확인 못 함」으로 남긴 항목이다
최신 원본에서 해결됐는지 재확인한다. 해당 편을 변환할 때
원본의 유보 표현을 **더 강하게 바꾸면 안 된다.**

| 편 | 내용 | 상태 |
|---|---|---|
| 3-4 | DNS `3 retries` | glibc `attempts` 기본값은 2인데 KEP-1024가 근거를 안 적는다 |
| 4-3 | 강제 detach 대기 시간 기본값 | 확인 못 함 |
| 5-5 | metrics-server 메모리 보관 서술 | 공식 문서에 해당 문장이 없다. 노트도 근거를 간접 추론에 뒀다 |

원본이 "근거를 못 찾았다"고 적은 것을 블로그에서 단정형으로 옮기면 사실 오류가 된다.
그대로 유보하거나, 변환 시점에 1차 출처를 다시 찾아 확정한다.
