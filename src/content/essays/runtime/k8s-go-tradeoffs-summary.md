> 시리즈 "커널과 런타임으로 톺아보는 Rust · Go · Java"의 29편 — 6부 5편

앞선 네 편에서는 쿠버네티스가 고루틴을 나누고, 직렬화 결과를 재사용하고, 캐시의 객체를 공유하는 방식을 확인했습니다
이 구조들은 할당과 복사를 줄여주지만, 캐시를 수정하는 방법이나 이벤트가 밀릴 때의 처리는 따로 챙겨야 했습니다

그렇다면 같은 구조를 일반 Go 서비스에 가져다 써도 될까요?
메모리 제한과 처리할 데이터의 양이 다르다면 설정도 달라져야 합니다
이번에는 앞서 확인한 수치를 모으고, 각 구조를 적용할 때 어떤 조건을 봐야 하는지 정리하겠습니다

수치는 쿠버네티스 v1.36.1의 kind 클러스터와 Go 1.26.5 기반 벤치마크에서 남긴 측정 기록입니다
클러스터는 Linux 6.8 환경에서 실행했고, 로컬 벤치마크에는 Apple M3를 사용했습니다
클러스터 측정, 소규모 벤치마크, 소스에서 확인한 동작을 구분해서 읽어야 합니다

## 앞선 네 편에서 확인한 것

[25편](/essays/k8s-control-plane-self-exemption)에서는 `kube-apiserver`의 시작 코드가 Go 환경변수를 로그로 출력하는 부분을 확인했습니다
다만 이 로그만 보고 환경변수가 런타임에 영향을 주지 않는다고 해석하면 안 됩니다
`GOGC`와 `GOMEMLIMIT`은 Go 런타임이 읽는 설정입니다
애플리케이션이 값을 로그로 남기는 것과 런타임이 그 값을 적용하는 것은 별개입니다

이번에 살펴본 구조도 GC 설정을 대신하는 기능은 아닙니다
불필요한 작업과 할당을 줄이는 구조를 먼저 이해하고, 실행 환경에 맞춰 런타임 설정을 함께 판단해야 합니다

![앞선 네 편에서 확인한 메모리 설정과 작업 분할·재사용 구조](/diagrams/k8s-go-tradeoffs-summary-1.svg)

| 주제 | 확인한 동작 | 적용할 때 남는 문제 |
|---|---|---|
| 컨트롤 플레인 메모리 설정 | 측정한 kubeadm 기반 파드에는 메모리 limit이 없었고 `memory.max`가 `max`였습니다 | 상위 cgroup의 제한과 노드 전체 메모리 부족은 따로 봐야 합니다 |
| 파드별 고루틴 | `podWorkers`가 파드별 동기화 작업을 고루틴으로 나눕니다 | 상태 조회, 프로브, 공유 데이터 동기화 비용은 남습니다 |
| 직렬화 캐시와 `sync.Pool` | 같은 인코딩 결과와 임시 할당 공간을 재사용합니다 | 캐시가 없는 경우의 할당과 풀의 항목 회수를 고려해야 합니다 |
| SharedInformer | 같은 informer의 캐시와 핸들러가 객체를 공유합니다 | 수정 전 복사와 느린 핸들러의 이벤트 적체를 관리해야 합니다 |

### 파드별 고루틴이 줄이는 것

`podWorkers`는 파드별로 동기화 작업을 순서대로 처리하면서, 서로 다른 파드의 작업은 병행할 수 있게 합니다
고루틴마다 OS 스레드를 하나씩 만드는 구조는 아닙니다
Go 런타임이 여러 고루틴을 OS 스레드에 나눠 실행합니다

그렇다고 락이 모두 사라지는 것은 아닙니다
[v1.36.1의 podWorkers 소스](https://github.com/kubernetes/kubernetes/blob/v1.36.1/pkg/kubelet/pod_workers.go)에도 공유 상태를 보호하는 `podLock`이 있습니다
파드별 작업을 나누는 것과 공유 데이터의 동기화 비용을 없애는 것은 구분해야 합니다

[26편](/essays/kubelet-goroutine-per-pod)에서 다룬 Generic PLEG는 컨테이너 런타임의 상태 변화를 확인하는 기능입니다
기본 relist 주기는 1초이지만, 파드별 고루틴이 각각 PLEG를 실행하는 구조는 아닙니다
파드가 많아지면 한 번의 조회에서 처리할 대상이 늘어나므로, 고루틴 수와 상태 조회 비용을 따로 확인해야 합니다

### 직렬화 캐시와 풀은 역할이 다릅니다

Watch는 리소스 변경을 구독하는 연결이고, 팬아웃은 같은 변경을 여러 구독자에게 전달하는 과정입니다
같은 객체를 같은 형식으로 보낼 때마다 직렬화하면 구독자 수만큼 작업이 반복됩니다

`cachingObject`는 객체별로 인코딩 식별자에 대응하는 결과를 저장합니다
같은 식별자로 들어온 요청은 `sync.Once`로 만든 결과를 재사용합니다
다른 인코딩 형식까지 전부 한 번에 처리한다는 뜻은 아닙니다
구현은 [caching_object.go](https://github.com/kubernetes/kubernetes/blob/v1.36.1/staging/src/k8s.io/apiserver/pkg/storage/cacher/caching_object.go)에서 확인할 수 있습니다

`sync.Pool`은 임시 객체나 버퍼를 재사용하는 쪽입니다
[27편](/essays/k8s-sync-pool-serialization)에서 확인한 Watch 경로도 지원되는 인코더에 한해 풀에서 할당자를 가져옵니다
직렬화 결과를 보관하는 캐시와 임시 할당 공간을 재사용하는 풀을 같은 것으로 보면 안 됩니다

당시 Go 1.26.5 실험에서는 `GOMAXPROCS=1`로 고정했을 때 첫 GC 뒤에는 풀의 객체를 다시 얻었고, 두 번째 GC 뒤에는 얻지 못했습니다
이는 해당 구현과 실험 조건에서 본 결과입니다
[`sync.Pool`의 API](https://pkg.go.dev/sync@go1.26.5#Pool)는 항목이 언제든 제거될 수 있다고 명시하므로, 두 번의 GC 동안 보관된다고 가정해서는 안 됩니다

### 객체를 공유하면 수정 규칙도 필요합니다

[28편](/essays/informer-shared-pointer-cost)에서는 두 핸들러가 받은 Pod 포인터 주소가 같았습니다
한 핸들러가 원본을 수정하면 다른 핸들러에도 그 변경이 보였습니다
같은 informer 안에서 객체를 공유하기 때문입니다
서로 다른 프로세스의 컨트롤러까지 하나의 포인터를 공유하는 것은 아닙니다

그래서 캐시에서 받은 객체를 바꾸려면 먼저 `DeepCopy()`로 사본을 만들어야 합니다
캐시가 내부 맵을 잠가준다고 해서, 꺼내온 객체의 필드를 직접 바꿔도 안전한 것은 아닙니다
이 조건은 [ThreadSafeStore의 주석](https://github.com/kubernetes/kubernetes/blob/v1.36.1/staging/src/k8s.io/client-go/tools/cache/thread_safe_store.go)에 명시되어 있습니다

핸들러가 이벤트를 받는 속도보다 느리게 처리하는 경우도 봐야 합니다
`processorListener`의 `pendingNotifications`는 아직 전달하지 못한 알림을 저장하는 상한 없는 링 버퍼입니다
처리가 계속 밀리면 informer를 실행하는 클라이언트 프로세스의 메모리가 늘어날 수 있습니다
API Server의 직렬화 캐시와는 위치도 역할도 다릅니다

## 측정값은 어디까지 비교할 수 있을까

| 대상과 조건 | 당시 기록 | 읽을 때 주의할 점 |
|---|---|---|
| 유휴 `kube-apiserver`, 파드 9개인 클러스터 | 고루틴 2,390개, 스택 사용량 17.4 MiB | 스택 총량을 고루틴 수로 나눈 평균이지 모든 고루틴의 스택 크기가 같다는 뜻은 아닙니다 |
| 같은 API Server의 cgroup | `memory.current` 189.3 MiB | Go 힙만의 사용량이 아닙니다 |
| 컨테이너 2개·라벨 10개인 Pod 디코딩 | Protobuf 1,540 ns/op·40 allocs/op, JSON 10,608 ns/op·79 allocs/op | 해당 객체와 코덱을 비교한 결과이며 모든 CRD나 API 요청의 비용으로 일반화할 수 없습니다 |
| `sync.Pool`, `GOMAXPROCS=1` | 첫 GC 뒤 재사용, 두 번째 GC 뒤 얻지 못함 | 풀의 보관 기간을 보장하는 실험이 아닙니다 |
| 두 informer 핸들러의 수신 객체 | 같은 포인터 주소 `0xa7e38469408` | 주소 자체보다 동일 객체를 공유한다는 사실이 중요합니다 |
| Pod 포인터 10만 개를 슬라이스에 적재한 모의 실험 | `HeapAlloc` 약 160.1 MiB 증가 | 실제 `RingGrowing`이나 운영 중인 API Server의 메모리를 측정한 값은 아닙니다 |

디코딩 실험에서는 와이어 크기가 Protobuf 647 B, JSON 736 B였습니다
전송 크기는 약 1.14배 차이였지만, 디코딩 시간은 약 6.9배 차이였습니다
같은 데이터라도 전송량과 CPU 시간, 할당 횟수는 각각 봐야 한다는 예시입니다

마지막 행은 특히 구분이 필요합니다
벤치 코드는 `RingGrowing` 대신 `[]*corev1.Pod`에 객체를 계속 추가했습니다
`160.1 MiB`에는 슬라이스뿐 아니라 새로 만든 Pod와 라벨 등의 메모리도 포함됩니다
따라서 이 수치를 링 버퍼 자체의 비용이나 OOM이 발생하는 기준으로 사용할 수는 없습니다

다만 이벤트 적체가 메모리를 계속 붙잡을 수 있다는 문제는 남습니다
[SharedInformer 소스](https://github.com/kubernetes/kubernetes/blob/v1.36.1/staging/src/k8s.io/client-go/tools/cache/shared_informer.go)의 `pendingNotifications` 주석도 느리거나 멈춘 리스너가 메모리 부족을 일으킬 수 있다고 설명합니다

## 앞에서 다룬 런타임 원리와 연결하면

### 스레드와 고루틴

[1부의 스레드 모델](/essays/thread-models-kernel-vs-user)과 연결되는 부분은 파드별 동기화 작업입니다
고루틴은 작은 스택으로 시작하고 필요에 따라 확장합니다
여러 고루틴이 OS 스레드를 공유하므로, 대기하는 작업마다 OS 스레드의 자원을 따로 확보할 필요가 줄어듭니다

하지만 고루틴이 사용하는 메모리와 스케줄링 비용까지 없어지는 것은 아닙니다
파드별 고루틴에 더해 프로브와 보조 작업도 있으므로, 파드 수만으로 전체 고루틴 수를 계산할 수는 없습니다

### AOT 컴파일과 할당

[2부의 Go AOT](/essays/go-aot-fast-build-tradeoff)는 빌드 시점의 최적화를, [Java JIT](/essays/java-jit-c2-runtime-optimization)는 실행 중 정보까지 사용하는 최적화를 다뤘습니다
Go 컴파일러도 탈출 분석으로 일부 할당을 피합니다
하지만 공유 캐시가 계속 참조하는 객체는 메모리에 남아 있어야 합니다

인터페이스를 사용했다는 이유만으로 모든 객체가 힙에 할당된다고 단정해서도 안 됩니다
실제 사용 방식과 컴파일러의 분석 결과를 확인해야 합니다
이번에 본 캐시와 풀은 반복되는 특정 작업의 비용을 줄이는 방법입니다

### 할당자와 재사용

[3부의 Go 할당자](/essays/go-allocator-mcache-contiguous-stack)는 논리 프로세서인 P별 캐시를 이용해 작은 객체의 할당을 처리합니다
캐시에 여유가 있으면 공유 자료구조에 접근하는 횟수를 줄일 수 있지만, 공간이 부족하면 새 공간을 확보해야 합니다

같은 직렬화 결과를 재사용하면 이 할당 경로에 들어가는 횟수부터 줄어듭니다
풀에서 객체를 얻지 못하면 다시 할당해야 하므로, 재사용을 적용했다는 이유만으로 할당 비용이 0이 되지는 않습니다

### GC와 오래 남는 객체

[4부의 GC](/essays/gc-tricolor-marking-write-barrier) 관점에서는 새로 만드는 양뿐 아니라 계속 참조하는 양도 중요합니다
캐시와 대기열이 객체를 붙잡고 있으면 GC는 그 객체를 회수할 수 없습니다
공유로 중복 할당을 줄였어도, 남아 있는 객체와 포인터를 확인하는 일은 계속 필요합니다

그래서 할당량이 줄었는지와 캐시가 너무 커지지 않는지는 따로 봐야 합니다
이벤트 처리가 밀려 살아 있는 객체가 계속 늘어난다면, GC를 더 자주 실행하는 것만으로 해결되지 않습니다

### 컨테이너 메모리 제한

[5부의 메모리 회계](/essays/container-memory-accounting-cgroup)는 Go 런타임이 보는 메모리와 커널이 보는 메모리의 차이를 다뤘습니다
이번에도 `memory.current` 189.3 MiB를 Go 힙 사용량으로 해석하면 출발부터 어긋납니다
컨테이너 한도 안에 들어오는지 판단하려면 런타임 지표와 cgroup 지표를 함께 확인해야 합니다

## memory.max가 max이면 OOM에서 안전할까

측정한 kubeadm 기반 컨트롤 플레인 파드에는 메모리 limit이 없었습니다
그래서 해당 cgroup의 `memory.max`도 `max`였습니다
이는 그 cgroup에 유한한 메모리 상한을 설정하지 않았다는 뜻입니다
상위 cgroup의 제한이나 노드 전체의 메모리 부족까지 없어지는 것은 아닙니다

유한한 `memory.max`를 설정한 경우, 사용량이 한도에 도달하고 회수로 줄일 수 없으면 해당 cgroup 안에서 OOM 처리가 발생할 수 있습니다
한도를 넘는 순간 언제나 즉시 종료된다는 설명도 정확하지 않습니다
[Linux cgroup v2 문서](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory)는 일시적인 초과와 할당 경로에 따른 차이를 구분합니다

`oom_score_adj`도 별개입니다
당시 기록에서는 `kube-apiserver`가 `-997`, 호스트의 `kubelet`이 `-999`였습니다
[v1.36.1의 정책 소스](https://github.com/kubernetes/kubernetes/blob/v1.36.1/pkg/kubelet/qos/policy.go)는 node-critical 파드와 Guaranteed 파드에 `-997`을 부여합니다
Static Pod라는 이유만으로 받는 점수는 아닙니다

이 음수 값들은 OOM 대상 선정에서 보호하는 쪽으로 작용하지만, 대상에서 제외한다는 뜻은 아닙니다
[`oom_score_adj` 문서](https://docs.kernel.org/filesystems/proc.html#proc-pid-oom-adj-proc-pid-oom-score-adj)에서 종료 대상 제외를 뜻하는 값은 `-1000`입니다

### 배포 형태를 바꾸면 무엇을 다시 봐야 할까

컨트롤 플레인을 다른 클러스터의 파드로 배포하더라도, 메모리 limit이나 QoS가 자동으로 하나의 값으로 정해지는 것은 아닙니다
실제 manifest와 실행 중인 cgroup을 확인해야 합니다

| 확인할 항목 | 확인하는 이유 |
|---|---|
| `requests.memory`와 `limits.memory` | 배치에 사용하는 요청량과 실행 중 한도를 구분하기 위해서입니다 |
| 컨테이너와 상위 cgroup의 `memory.max` | 직접 설정한 한도 외에도 적용되는 제한이 있는지 보기 위해서입니다 |
| QoS, 우선순위, `oom_score_adj` | 메모리 부족 때 어떤 보호 정책이 적용되는지 확인하기 위해서입니다 |
| `GOMEMLIMIT`과 런타임 메모리 사용량 | 커널 한도에 맞춰 Go 런타임의 사용량을 조절할 여지가 있는지 보기 위해서입니다 |

컨트롤 플레인인지 일반 서비스인지라는 이름만으로 안전성을 판단하기는 어렵습니다
같은 바이너리라도 메모리 한도가 달라지면 캐시와 버퍼에 허용할 크기를 다시 잡아야 합니다

## GOMEMLIMIT은 어떻게 적용할까

`GOGC=100`이면 다음 GC의 목표 힙이 이전에 살아 있던 힙 크기에 비례해 커집니다
GC 루트까지 포함한 설명용 식은 다음과 같습니다

```text
목표 힙 = 살아 있는 힙 + (살아 있는 힙 + GC 루트) × GOGC / 100
```

예를 들어 GC 루트의 크기를 생략하고 살아 있는 힙을 1,200 MiB로 놓으면 목표 힙은 약 2,400 MiB입니다
컨테이너 한도가 2,048 MiB라면 이 목표와 실행 환경 사이에 차이가 생깁니다

다만 **목표 힙은 GC를 시작하는 시점이 아닙니다**
런타임은 목표에 도달하기 전에 수집을 마치도록 시작 시점을 조절합니다
“2,400 MiB까지 GC가 기다리다가 OOM이 난다”는 설명은 이 차이를 놓칩니다
[Go GC 가이드](https://go.dev/doc/gc-guide#GOGC)는 목표 힙과 수집 주기의 관계를 설명합니다

### Go가 관리하는 메모리와 컨테이너 전체 메모리

`GOMEMLIMIT`은 Go 1.19부터 지원하는 런타임의 소프트 메모리 한도입니다
관리 대상은 Go 힙만이 아니라, 런타임이 관리하는 스택과 메타데이터 등을 포함합니다
[`SetMemoryLimit` 문서](https://pkg.go.dev/runtime/debug@go1.26.5#SetMemoryLimit)는 이를 `runtime.MemStats.Sys - runtime.MemStats.HeapReleased`로 정의합니다

반면 cgo로 호출한 C 코드의 할당이나 커널이 관리하는 메모리는 이 범위와 다릅니다
그래서 `GOMEMLIMIT`을 컨테이너 한도와 똑같이 잡는 대신, 런타임 밖에서 쓰는 메모리도 고려해야 합니다

또한 소프트 한도이므로 런타임이 항상 지킨다고 보장하지 않습니다
살아 있는 객체가 너무 많으면 회수할 수 있는 메모리도 적습니다
GC에 지나치게 많은 CPU를 쓰는 상황을 피하려고 한도를 초과할 수 있으며, OOM 위험도 남습니다

![cgroup 메모리 한도와 GOMEMLIMIT이 적용되는 범위](/diagrams/k8s-go-tradeoffs-summary-4.svg)

### 2 GiB 파드에 적용하는 예시

아래는 기존 Deployment의 컨테이너 설정에 넣을 수 있는 항목입니다
`limits.memory=2Gi`에서 `GOMEMLIMIT=1600MiB`를 시험하는 예시이며, 검증된 최적값이나 OOM 방지 보장은 아닙니다

```yaml
# Deployment의 spec.template.spec.containers[] 내부 설정 예시
resources:
  limits:
    memory: "2Gi"
env:
  - name: GOMEMLIMIT
    value: "1600MiB"
  - name: GOGC
    value: "100"
```

두 값의 차이는 `2,048 - 1,600 = 448 MiB`입니다
이 여유가 충분한지는 cgo 사용량, 커널 메모리, 순간적인 할당 증가 등에 따라 달라집니다
70~80%라는 비율을 모든 Go 서비스에 그대로 적용할 근거는 없습니다

설정을 바꾼 뒤에는 같은 부하에서 `memory.current`, Go 런타임 메모리, GC CPU 사용량, 응답 지연을 함께 비교해야 합니다
메모리 사용량이 줄어도 GC가 자주 돌아 응답이 늦어진다면 값을 다시 조정해야 합니다

CPU 설정도 사용 중인 Go 버전을 먼저 봐야 합니다
[Go 1.25부터 Linux 런타임은 cgroup CPU 한도를 고려해 기본 `GOMAXPROCS`를 정합니다](https://go.dev/doc/go1.25#runtime)
모듈의 Go 버전과 호환성 설정도 확인해야 하며, 환경변수로 값을 직접 고정하면 자동 조정은 비활성화됩니다
따라서 이 글의 Go 1.26 환경에서 `automaxprocs`를 필수 의존성처럼 추가할 이유는 없습니다

## 적용 전에 남겨둘 질문

이번에 본 구조를 가져다 쓴다면 다음부터 확인하겠습니다

1. **캐시가 붙잡는 객체의 수와 수명에 상한이 있는가?** 중복 할당이 줄어도 보관량이 계속 늘면 메모리 문제는 남습니다
2. **공유 객체를 수정하는 경로가 분리되어 있는가?** informer에서 받은 객체는 읽기 전용으로 다루고, 수정할 때 사본을 만들어야 합니다
3. **이벤트 처리가 밀리면 어떻게 할 것인가?** 핸들러는 오래 막히지 않게 하고, 작업을 큐로 넘긴다면 적체량을 관측해야 합니다
4. **큐가 가득 찼을 때의 정책이 있는가?** 용량 제한만 넣기보다 대기·거부·재시도 중 서비스에 맞는 동작을 정해야 합니다
5. **런타임 설정을 바꾼 결과를 같은 조건에서 비교했는가?** 메모리뿐 아니라 GC CPU와 응답 지연도 함께 확인해야 합니다

쿠버네티스에서 쓴 구조라도 그대로 가져오면 같은 결과가 나오는 것은 아닙니다
어떤 작업을 줄였는지, 대신 무엇을 계속 보관하는지, 문제가 생겼을 때 어느 프로세스가 영향을 받는지를 함께 봐야 합니다
6부는 이 기준으로 마무리하고, 이후에는 런타임과 커널의 변화가 지금까지 비교한 조건을 어떻게 바꾸는지 이어서 살펴보겠습니다
