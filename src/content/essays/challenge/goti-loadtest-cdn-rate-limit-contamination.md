## 한 줄 요약

> 대기열 구현체를 고르는 3000 VU 부하 테스트에서 통과율 40.89%와 응답 속도 1위가 같은 실행에 함께 나왔습니다. CDN 무료 요금제의 하루 10만 요청 한도가 토큰 발급 단계를 막고 있었고, 그 실패가 대기열 지표로 집계되고 있었습니다. 지표별로 무엇을 재고 있었는지 갈라낸 뒤에야 올바른 구현체를 고를 수 있었습니다

---

## 세 명이 만든 대기열 중 하나를 골라야 했습니다

티켓 오픈 순간에는 수만 명이 같은 초에 몰립니다. 이 트래픽을 흘려보내려면 가상 대기실이 필요한데, 대기 중 발생하는 요청의 대부분은 "내 순번이 왔는지" 묻는 상태 조회입니다

실측에서 이 엔드포인트 하나가 전체 트래픽의 70~90%를 차지했습니다

그래서 팀에서 세 명이 각자 다른 전략으로 대기열을 구현했습니다. 편의상 A·B·C로 부르겠습니다

- **A** — Redis Sorted Set + 1초 폴링. 처리량 우선
- **B** — Redis ZSET + Heartbeat + 5초 폴링. 응답성과 안정성 우선
- **C** — JWE 토큰 + 분산 Lock + CDN 캐싱. 폴링을 엣지가 흡수하는 구조

EKS 프로덕션 클러스터(10노드, Karpenter)에서 3000 VU로 최종 비교했습니다. 이 결과로 프로덕션에 올릴 하나를 정할 예정이었습니다

측정 경로는 두 가지였습니다. ALB에 직접 붙는 경로와 Cloudflare CDN을 경유하는 경로입니다

---

## 한 실행 안에서 지표가 정반대를 가리켰습니다

C 구현체를 CDN 경유로 측정한 결과입니다

| 지표 | 값 | 겉보기 판정 |
|---|---|---|
| `queue_pass_rate` | 40.89% (1826/4465) | 최하위 |
| `queue_timeouts` | 2,586건 | 최하위 |
| `queue_status` avg | 220ms | 최고 |
| `queue_status` p95 | 334ms | 최고 |
| 처리량 | 1,044 req/s | 최고 |
| `http_req_failed` | 0.08% | 최고 |

통과율 40%에 timeout 2,586건이면 탈락입니다. 경쟁 구현체 두 개는 같은 조건에서 통과율 100%, timeout 0건을 냈습니다

그런데 같은 실행에서 응답 속도와 처리량은 전체 1위였습니다

이 조합은 성립하지 않습니다. 요청의 60%가 실패하는데 응답이 가장 빠를 수는 없습니다. 실패한 요청은 보통 느리게 실패하기 때문입니다

숫자 하나가 틀렸거나, 두 숫자가 서로 다른 것을 재고 있거나 둘 중 하나였습니다

---

## 한도에 걸린 지점은 대기열이 아니었습니다

응답을 열어 보니 HTTP 429와 Cloudflare 고유 오류 1015가 찍혀 있었습니다. 무료 요금제의 **하루 10만 요청 한도**였습니다

걸린 위치가 결정적이었습니다. k6 `setup()` 단계의 **회원 가입 API**였습니다

부하 테스트는 대기열에 들어가기 전에 사용자 토큰을 먼저 발급받습니다. 이 발급이 한도에 막히면 해당 가상 사용자는 대기열에 진입조차 못 합니다

그런데 k6 입장에서 이것은 "대기열을 통과하지 못한 사용자"입니다. 그래서 `queue_pass_rate` 하락과 `queue_timeouts`로 집계됐습니다

반대로 토큰을 받아 실제로 폴링에 들어간 요청들은 아무 방해 없이 측정됐습니다. `queue_status`와 처리량이 진짜 값이었던 이유입니다

응답 헤더의 `cf-cache-status: HIT`와 `max-age=1`이 캐싱 자체는 의도대로 동작했음을 확인해 줬습니다

## 지표를 둘로 갈랐습니다

같은 실행의 지표를 측정 대상 기준으로 분리했습니다

| 지표 | 실제로 잰 것 | 신뢰 |
|---|---|---|
| `pass_rate` 40.89% · `timeouts` 2,586건 | CDN 무료 요금제 한도 | 무효 |
| `status` avg·p95 · 처리량 · `http_req_failed` | 실제 폴링 경로 성능 | 유효 |

유효한 쪽만 놓고 같은 구현체를 두 경로로 비교하면 이렇게 됩니다

| 항목 | ALB 직접 | CDN 경유 | 변화 |
|---|---|---|---|
| `queue_status` avg | 926ms | 220ms | 4.2배 개선 |
| `queue_status` p95 | 1.98s | 334ms | 5.9배 개선 |
| 처리량 | 655 req/s | 1,044 req/s | 1.6배 증가 |
| 5분당 완료 | 907회 | 1,889회 | 2.1배 증가 |
| `http_req_failed` | 1.26% | 0.08% | 16배 감소 |

폴링이 엣지에서 흡수되면서 origin까지 도달하는 요청이 크게 줄어든 결과입니다

---

## 측정 경로를 둘로 나눕니다

일회성으로 수치를 보정하는 대신 측정 방식 자체를 바꿨습니다

![측정 경로를 하나로 두었을 때와 둘로 나눴을 때|short](/diagrams/goti-loadtest-cdn-rate-limit-contamination-1.svg)

한도에 걸리는 요청과 성능을 재려는 요청이 같은 경로를 쓰는 한, 두 가지가 한 숫자에 섞입니다. 그래서 토큰 발급은 ALB 직접 경로로 빼고 폴링만 CDN을 경유하게 했습니다

세 가지 안을 놓고 비교했습니다

| 측정 경로 | 판정 |
|---|---|
| CDN 경유 단일 측정 | 기각 — 서버 처리 능력과 엣지 차단이 한 숫자에 섞임 |
| ALB 직접 단일 측정 | 기각 — 실사용자 경로가 아님. 엣지 캐싱·TLS 효과가 관측되지 않음 |
| ALB 직접 + CDN 경유 이원 측정 | 채택 |

채택안의 핵심은 두 수치를 하나로 합치지 않는다는 점입니다

서버가 얼마나 버티는지는 ALB 직접으로 재고, 사용자가 실제로 겪는 속도는 CDN 경유로 잽니다. **두 값의 차이 자체가 엣지 효과의 정량화**입니다

부하 테스트 표준 수칙에도 명시했습니다

- 토큰은 `setup()`에서 일괄 발급하고, 가상 사용자 루프 안에서 가입을 호출하지 않습니다
- CDN 경유로 대량 부하를 걸기 전에 WAF 규칙을 미리 조율합니다
- 처리 능력 기준선은 반드시 ALB 직접으로 측정합니다

같은 방향의 관측이 1000 VU 회차에도 남아 있습니다

CDN을 경유하며 반복마다 가입을 호출한 실행은 가입 성공률이 5%에 그쳤습니다. ALB 직접에 토큰 일괄 발급으로 바꾼 실행은 최종 성공률 93.79%가 나왔습니다

다만 이 회차는 경로와 발급 방식을 함께 바꿨습니다. 당시 기록도 실패 원인을 가입 서비스의 replica 부족으로 적고 있습니다

요금제 한도의 단독 증거로 쓰기에는 변수가 둘입니다. 방향을 뒷받침하는 정도로만 봅니다

---

## 그래서 무엇을 골랐나

지표를 갈라 읽은 뒤 **C 구현체를 최종 채택**했습니다

세 구현체를 3000 VU ALB 직접 기준으로 놓으면 이렇습니다

| 항목 | A | B | C |
|---|---|---|---|
| `queue_pass_rate` | 100% | 100% | 87.44% |
| `queue_timeouts` | 0건 | 0건 | 157건 |
| `queue_status` avg | 2.66s | 158ms | 926ms |
| 1K→3K 응답 증가율 | 24배 | 4배 | 16배 |

숫자만 보면 B가 안정성에서 앞섭니다. 실제로 timeout 0건에 통과율 100%였습니다

그럼에도 C를 고른 이유는 A와 B가 **구조적으로 CDN 캐싱이 불가능**하기 때문입니다. 두 구현체는 토큰마다 응답이 달라지므로 엣지가 흡수할 수 있는 형태가 아닙니다

가상 사용자가 열 배로 늘면 요청도 그대로 origin에 열 배로 도달합니다. 반면 C는 처음부터 캐시 적중을 의도한 설계였습니다

C를 택하면서 감수한 것도 있습니다

- 토큰 발급과 분산 Lock 경합이 입장 경로에 몰립니다. 핵심 폴링 경로는 엣지가 흡수하므로 영향은 제한적입니다
- `max-age=1` 때문에 대기 순번에 최대 1초 지연이 생깁니다
- CDN 없이 운영하면 B보다 불안정합니다. 캐싱이 전제인 선택입니다

요금제 한도를 구현체 결함으로 읽었다면 통과율 40%짜리를 버리고 확장되지 않는 대안을 골랐을 겁니다

이 선택으로 폴링이 엣지에서 흡수되면서 origin Redis 부하가 크게 줄었고, Redis Cluster 전환을 피할 수 있었습니다

## 검증되지 않은 채 남은 것

경로 분리는 결정과 수칙으로 확정했지만, **3000 VU 재측정은 하지 못했습니다**

시연 일정이 1주 남은 시점이라 후속 과제로 남겼습니다. 따라서 "경로를 나눈 뒤 통과율이 회복됐다"는 문장은 이 글의 범위 밖입니다

지금 말할 수 있는 것은 두 가지입니다. 오염의 원인과 지점을 특정했고, 다시 섞이지 않도록 측정 구조를 바꿨습니다

가입 경로 자체의 취약점도 그대로 남았습니다. 실서비스에서 오픈 순간의 가입 폭주를 받으려면 이 경로를 CDN 밖으로 빼거나 요금제 한도를 다시 계산해야 합니다

## 배운 점

### 한 테스트의 모든 지표가 같은 것을 재고 있다고 가정하면 안 됩니다

이번 실행에서는 통과율 악화와 응답 속도 개선이 나란히 나왔고, 원인이 서로 달랐습니다. 하나는 외부 요금제 한도를, 다른 하나는 구현체 성능을 재고 있었습니다

지표가 나쁘게 나왔을 때 첫 질문은 "구현이 나쁜가"가 아닙니다. **"이 숫자가 지금 무엇을 재고 있는가"**입니다

### 모순은 버그가 아니라 단서입니다

통과율 40%와 응답 속도 1위가 함께 나온 것은 처음엔 측정 오류처럼 보였습니다

실제로는 두 숫자가 서로 다른 계층을 정직하게 보고하고 있었습니다. 모순을 발견하면 한쪽을 지우는 게 아니라, 두 숫자가 각각 어느 계층을 보고 있는지 찾아야 합니다

### 측정 환경의 제약도 아키텍처입니다

무료 요금제 한도는 애플리케이션 코드 어디에도 없습니다. 그런데 의사결정을 뒤집을 뻔했습니다

부하 테스트는 대상 시스템만 검증하는 작업이 아닙니다. 테스트를 통과시키는 경로 전체가 측정 대상에 포함됩니다
