# 글쓴이 말투와 편집 기준

Codex와 Claude가 글을 작성·변환·검토할 때 함께 읽는 기준입니다
목표는 글쓴이의 상황과 판단을 보존하면서 과장, 직역, 근거 없는 단정, 불필요한 반복을 줄이는 것입니다
문장만으로 AI 작성 여부를 판정하거나 AI 탐지 점수를 매기지 않습니다

## 적용 범위와 우선순위

- 신규 글과 사용자가 수정·검토를 요청한 글에 적용합니다. 이 문서 추가만으로 기존 글을 일괄 수정하지 않습니다
- 현재 사용자의 명시적 지시를 우선합니다. 이 문서는 기존 지침·스킬·시리즈 plan의 문체 예시, 문단 수 할당, 상투적인 도입·마무리 요구보다 우선합니다
- 시리즈의 slug·order·기준 버전, 트랙·카테고리, 이미지 규격은 해당 프로젝트 규칙과 plan을 따릅니다
- 사실·수치·기전·판단 근거를 보존합니다. 문체를 자연스럽게 만든다는 이유로 조건·한계·실패 과정을 지우거나 경험을 보태지 않습니다

## 보존할 말투

**개인 경험 글**은 원본에 있는 상황, 의문, 확인한 결과, 판단이 바뀐 이유를 연결합니다
“처음엔 이렇게 하려 했는데, 작업하다 보니 이런 문제가 있어 바꿨습니다”는 흐름의 예시이며 모든 글에 강제할 문장 틀이 아닙니다

- `처음엔`, `그런데`, `~하다 보니`, `~해봤습니다`, `그래서`, `이번에는`처럼 평범한 연결어와 행동을 나타내는 동사를 씁니다
- 원본의 `저는`, `저희는`, 당시의 제약과 망설임을 격식체 변환 과정에서 지우지 않습니다. 사람이 한 선택을 무생물 주어와 명사형 표현으로 바꾸지 않습니다
- `이게`를 항상 `이것이`로 바꿀 필요는 없습니다. `띄우다`, `돌아가다`, `헤매다`처럼 이해하기 쉬운 작업 표현을 유지합니다
- “뭐지? 설정이 틀렸나?” 같은 원본의 짧은 독백은 인용으로 보존할 수 있습니다. 본문 서술은 격식체를 유지하고 독백·질문·감탄을 새로 만들어 분위기를 꾸미지 않습니다
- 짧은 문장과 이유를 설명하는 문장을 섞습니다. 50자는 가독성 참고치이며 길이만 맞추려고 인과관계를 잘라내지 않습니다. 한 단락에는 한 생각을 담습니다
- 오타·중복·늘어진 문장은 다듬습니다. 말투를 살리기 위해 오타나 비문을 재현하지 않습니다

**개념 해설 글**은 독자가 이해해야 할 질문과 기전부터 설명해도 됩니다
실제 경험이 없는 원본에 “직접 해봤습니다”, “처음에는 실패했습니다”, “팀에서 고민했습니다”를 추가하지 않습니다
독자를 위한 가정 예시는 가정임을 밝히고 실측·경험과 구분합니다

## 말투 참고 자료

2025년 10~11월 글 16편의 초기 등록본과 후속 글을 비교한 분석에 기반합니다
초기 등록본도 전부 직접 쓴 문장이라고 확인된 것은 아닙니다. 글 전체를 문체 정답이나 기술적 근거로 취급하지 않습니다
2026-04-08 커밋 `34fcda8`에서 격식체 통일이 이루어졌으므로 현재 문장 끝맺음이 최초 말투와 같다고 가정하지 않습니다

필요할 때 아래의 **개인 상황·판단을 서술한 구간**을 참고합니다

- [환경변수 관리](../src/content/essays/challenge/docker-compose-env-management.md): “처음엔 dev/prod 2개만”과 환경을 나눈 이유
- [weAlist 마이그레이션 1편](../src/content/logs/challenge/challenge2-wealist-migration-part1.md): 빈 과제 대신 팀 프로젝트를 선택한 배경
- [CI/CD 전략](../src/content/essays/cicd/multi-repo-cicd-strategy.md): 서비스별 저장소와 배포 구조 때문에 생긴 고민
- [Service 트러블슈팅](../src/content/logs/kubernetes/pod-service-troubleshooting.md): 확인 결과를 보고 다음 점검으로 넘어가는 흐름

이 글들의 이모지, 면접 질문, 고정 섹션, “실무 90%” 같은 출처 없는 비율은 모방하지 않습니다
같은 시리즈의 기존 글은 구조와 기술적 연결을 참고하되 문체까지 무조건 따라 쓰지 않습니다

## 줄일 표현과 판단 기준

| 유형 | 점검할 예 | 편집 방향 |
|---|---|---|
| 과장 | 완벽한 자족성을 선물합니다, 경이로운 수준, 절대적 동력, 역사적 실타래가 풀립니다 | 무엇이 가능해지고 어떤 작업이 줄었는지 조건과 함께 설명합니다 |
| 직역·추상화 | 가장 뜨거운 엔티티, 유일한 실시간 진실, 설계와 운영의 삼중 미정렬 | 요청이 집중되는 데이터, 현재 상태의 기준, 실제로 어긋난 설정처럼 구체화합니다 |
| 근거 없는 단정 | 실무 사용률 95%, 무조건, 유일한 해법, 비교표가 증명합니다 | 출처·측정 범위·전제 확인 후 그 범위 안에서만 말합니다 |
| 반복 안내 | 풀어 설명하겠습니다, 표에서 눈에 띄는 점은, 이것이 핵심입니다 | 다음 문장과 정보가 겹치면 지우고 내용부터 설명합니다 |
| 내부 맥락 누락 | 설명 없는 SDD-0005, D0~D7, wiring, Exit criteria | 독자에게 필요한 역할·행동을 먼저 풀고 식별자는 추적에 필요할 때만 남깁니다 |

이 표는 자동 치환용 금칙어 목록이 아닙니다
`source of truth`, `work stealing`, `hot path` 같은 기술 용어는 정확하게 쓰고 첫 등장에 뜻을 설명합니다
은행·식당 같은 비유도 이해를 도울 때 사용할 수 있습니다. “청구서”, “대가”를 포함해 한 비유를 여러 절에 반복하거나 원래 기술 설명을 대신하게 만들지 않습니다

### 근거와 확신

- 실측에는 가능한 범위에서 환경·조건·기간·지표를 함께 적습니다. 목표값, 예시값, 관측값을 섞지 않습니다
- 초안에 이미 있는 수치도 자동으로 사실로 승인하지 않습니다. 근거가 없으면 확인 필요 항목으로 남기고, 다른 숫자나 “대부분” 같은 일반화로 바꿔 숨기지 않습니다
- 원본과 확인된 자료가 뒷받침하는 범위에서만 “확인했습니다”라고 씁니다. 해석은 “~로 보입니다”, 미확인은 “확인하지 못했습니다”처럼 구분합니다
- 비교표는 근거를 정리하는 도구입니다. 표를 작성했다는 이유로 성능·인과관계가 “증명됐다”고 쓰지 않습니다
- 실제로 시도하거나 검토한 대안만 선택 과정으로 적습니다. 결과를 매끄럽게 보이게 하려고 실패·가설·결정 이유를 창작하지 않습니다

### 표·다이어그램·섹션

- 표나 그림만으로 이해하기 어려운 기전, 조건, 선택 이유, 예외를 본문에서 설명합니다
- **문단 수를 채우지 않습니다.** 바로 앞에서 이미 설명했거나 요약표 자체로 충분하면 뒤에 같은 설명을 반복하지 않습니다
- 표의 모든 행을 산문으로 다시 읽지 않습니다. 독자가 놓칠 관계나 판단 근거에 분량을 씁니다
- 매 절에 도입 문장과 결론 문장을 붙이지 않습니다. 한 줄 요약·배운 점·면접 질문·다음 편 예고도 새로운 정보나 실제 연결이 있을 때만 둡니다
- 구체성을 위해 수치를 만들지 않습니다. 자료가 없으면 확인된 조건과 기전을 풀어서 설명합니다

## 편집 예시

아래는 표현 비교용입니다. 실제 글에 적용할 때는 해당 원본의 사실과 조건이 일치하는지 확인합니다

**입력**

> 처음엔 dev/prod 2개만 하려고 했습니다
> 그런데 실제로 작업하다 보니 EC2에서 개발 테스트하는 환경이 필요했습니다

**피할 변환**

> 환경별 요구사항의 다차원적 차이를 해소하기 위해 배포 환경의 전략적 세분화를 수행했습니다

**보존할 형태**

> 처음에는 dev와 prod만 나누려고 했습니다
>
> 그런데 작업하다 보니 EC2에서 개발 테스트를 할 환경도 필요했습니다
> 그래서 ec2-dev를 따로 나눴습니다

“이게 귀찮으면”을 격식체로 다듬을 때도 “이 작업이 번거롭다면” 정도면 충분합니다
개인적인 판단을 없애거나 명사화된 보고서 문장으로 바꿀 필요는 없습니다

## 작성·검토 절차

작성 전 원본에서 상황, 제약, 행동, 결과, 판단 이유와 미확인 항목을 구분합니다
없는 항목을 채워 넣지 않습니다. 기존 글 편집은 요청한 범위에서 최소한으로 고칩니다
탈고 때는 다음을 문맥으로 확인합니다

1. 글쓴이의 선택과 생각이 바뀐 이유가 남아 있는가
2. 문체 교정으로 원본의 조건·기전·한계를 지우거나 경험을 만들지 않았는가
3. 과장·직역·반복 안내를 빼도 의미가 같다면 덜어냈는가
4. 수치·보편적 단정에 근거가 있고, 미확인 내용은 구분했는가
5. 표·본문·요약이 같은 설명을 반복하지 않는가
6. 프로젝트에 처음 온 독자도 내부 용어의 역할을 이해할 수 있는가

검토 결과는 `파일:행 — [말투/과장/직역/근거/반복/맥락] 원문 → 문제 이유 → 최소 수정안`으로 씁니다
근거가 확인되지 않았다는 이유만으로 창작이라고 판정하지 않습니다. 정정 근거 없이 원본의 사실·조건을 바꾼 경우는 필수 수정, 출처 확인이 필요한 주장은 확인 필요, 문체 개선은 권장으로 구분합니다
“AI 같다”만 적거나 작성 주체·AI 사용 비율을 추정하지 않습니다
자동 lint는 형식 검사일 뿐 이 판단을 대신하지 않습니다. 통과하지 않은 검토를 통과했다고 보고하지 않습니다
