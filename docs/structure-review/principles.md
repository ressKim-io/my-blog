# 설명 순서를 판단하는 기준

이번 검토는 Pod·Deployment 등을 사용해 봤지만 해당 내부 원리는 처음 배우는 독자를 기준으로 합니다
API 사용 경험만으로 FIFO 구현, storage codec, 커널 통계의 집계 단위까지 알고 있다고 가정하지 않습니다
심화 글에서는 필요한 선행 개념을 짧게 연결하되 모든 기초 내용을 다시 설명하지 않습니다

## 독자가 풀고 있는 질문을 유지합니다

각 글의 제목이 던진 질문을 한 문장으로 정하고, 기본 사례에서 그 답을 먼저 완성합니다
새 절은 앞에서 남은 질문이나 방금 본 동작의 이유를 설명해야 합니다
단지 관련된 기술이라는 이유만으로 다른 추상화 수준의 설명을 중간에 끼우지 않습니다

예를 들어 PVC 글에서는 StorageClass를 지정한 요청이 볼륨과 연결되는 과정을 이해한 다음, 여러 PVC의 경쟁을 설명하며 claimRef 기록 순서를 다룹니다
informer 글에서는 컨트롤러가 사본을 읽는 이유와 초기화·갱신 과정을 이해한 다음, 큐 구현별 차이를 다룹니다

## 기본 사례와 세부 조건을 배치합니다

- Linux·기본 경로·특정 요청 종류처럼 설명의 적용 범위를 정하는 조건은 해당 설명 앞에 둡니다
- 기본 사례의 결과를 바꾸는 중요한 예외는 관련 동작 바로 옆에 둡니다. 모든 예외를 끝으로 보내지 않습니다
- 과거 구현과의 비교, 세부 계산식, 특정 버전의 gate 표는 그 차이를 알아야 하는 이유를 설명한 뒤 배치합니다
- 정상 흐름·장애 진단·소스 탐색이 한 글에 함께 있으면 정상 흐름을 이해한 뒤 진단과 구현을 찾아볼 수 있게 합니다
- 하나의 절에서 설명 수준이 바뀌면 무엇을 더 알아보려는지 한 문장으로 연결합니다

## 지워서 쉬워 보이게 만들지 않습니다

기술 사실·한계·불확실성·가정·소스 버전은 보존합니다
구현상의 조건을 뒤로 옮길 때는 주장을 무조건적인 보장으로 바꾸지 않고, 필요한 짧은 한정과 연결을 남깁니다
실측 없는 소스 해설에 실험 결과나 개인 경험을 추가하지 않습니다
가정 예제는 가정이라고 표시하고 기존 원문이 설명하는 조건 안에서만 구성합니다

문장별 말투는 [공통 말투와 편집 기준](../writing-voice.md)을 따릅니다
블로그 본문을 일괄 템플릿으로 바꾸거나, 모든 절에 질문·요약·비유를 붙이지 않습니다
검토서의 공통 형식은 후속 작업을 찾기 위한 형식이며 블로그 글의 고정 목차가 아닙니다

## 유지할 흐름도 명시합니다

이미 제목의 의문에 답하는 예제, 앞의 결과에서 자연스럽게 이어지는 예외, 역할을 구분하는 그림은 유지합니다
각 글의 변경 강도는 문맥을 읽고 정합니다. 글마다 문제 개수나 이동할 절 수를 맞추지 않습니다
숫자 점수와 lint 결과로 학습 가능성을 판정하지 않습니다

## 독자 관점의 검토

각 절을 읽은 뒤 다음 내용을 확인합니다

1. 독자는 방금 어떤 질문의 답을 얻었는가
2. 다음 절을 읽어야 할 이유가 앞의 내용에서 생겼는가
3. 다음 설명에 필요한 용어·상태·주체를 이미 배웠는가
4. 예제가 중간에 바뀌었다면 그 이유와 대응 관계가 설명됐는가
5. 오류나 조건의 목록이 앞의 기본 동작과 연결되는가

예를 들어 구현 이름은 알지만 입력·출력·역할을 설명할 수 없다면 구성 보완이 필요합니다
원문의 주장을 검사한 기술 검토와 읽는 순서를 검사한 구조 검토를 구분합니다
