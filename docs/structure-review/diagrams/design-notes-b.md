## 1. Conntrack — 요청 목적지와 응답 출발지가 달라지는 한 연결

대상: `src/content/essays/kubernetes/k8s-theory-netfilter-conntrack.md`

새 자산: `public/diagrams/k8s-theory-netfilter-conntrack-3.svg`

### 학습 질문과 기존 그림의 역할

새 질문은 “Service로 보냈는데 백엔드에서 온 응답을 어떻게 같은 연결로 찾고 Service 주소로 돌려주는가”입니다
기존 1번은 hook별 패킷 경로, 2번은 kube-proxy 체인의 백엔드 선택입니다. 새 그림에는 hook·체인 도식을 다시 그리지 않습니다

### 삽입 위치와 연결문

`## Conntrack은 같은 연결을 양방향 키로 찾습니다`의 끝에 넣습니다
바로 앞 문장은 `NAT 설정의 nf_nat_setup_info는 실제 변환을 반영해 reply 튜플을 수정합니다`이며, 다음 절은 `## 후속 패킷은 유지 중인 NAT 바인딩을 재사용합니다`입니다

앞에 추가할 문장: `같은 주소 예시에서 요청의 목적지와 응답의 출발지가 어떻게 바뀌는지 나란히 놓으면 다음과 같습니다`

이미지 alt: `추가 SNAT이 없는 연결에서 요청은 Service 목적지에서 백엔드 목적지로 바뀌고, 백엔드 응답은 같은 conntrack 기록을 찾아 Service 출발지로 바뀌는 주소 대응|tall`

### ASCII 목업

560 × 약 1180, 위에서 요청 → 공유 상태 → 응답 순으로 읽습니다. 숫자 주소는 두 줄 SRC/DST로 분리해 모바일에서 한 줄에 두 주소를 몰아넣지 않습니다

```text
┌────────────────────────────────────────────┐
│    요청과 응답이 공유하는 NAT 기록          │
│    IPv4 · 같은 프로토콜 · 추가 SNAT 없음    │
│                                            │
│  ① 클라이언트가 보낸 요청                   │
│  ┌──────────────────────────────────────┐  │
│  │ SRC  10.244.1.5:33445                 │  │
│  │ DST  10.96.0.10:80     [Service]      │  │
│  └──────────────────────────────────────┘  │
│              │ 목적지 DNAT                 │
│              ▼                             │
│  ┌──────────────────────────────────────┐  │
│  │ SRC  10.244.1.5:33445  [그대로]       │  │
│  │ DST  10.244.2.9:8080   [백엔드]       │  │
│  └──────────────────────────────────────┘  │
│                                            │
│  ╭────── 하나의 conntrack 연결 기록 ─────╮  │
│  │ Original 키                           │  │
│  │   SRC 10.244.1.5:33445                 │  │
│  │   DST 10.96.0.10:80                    │  │
│  │ ────────────────────────────────────  │  │
│  │ Reply 키                              │  │
│  │   SRC 10.244.2.9:8080                  │  │
│  │   DST 10.244.1.5:33445                 │  │
│  │              + NAT 상태               │  │
│  ╰───────────────────────────────────────╯  │
│                                            │
│  ② 백엔드가 보낸 응답                      │
│  ┌──────────────────────────────────────┐  │
│  │ SRC  10.244.2.9:8080   [백엔드]       │  │
│  │ DST  10.244.1.5:33445                 │  │
│  └──────────────────────────────────────┘  │
│              │ 같은 NAT 상태로 역변환      │
│              ▼                             │
│  ┌──────────────────────────────────────┐  │
│  │ SRC  10.96.0.10:80     [Service]      │  │
│  │ DST  10.244.1.5:33445  [그대로]       │  │
│  └──────────────────────────────────────┘  │
│                                            │
│  키는 두 방향 · 연결 객체는 하나           │
└────────────────────────────────────────────┘
```

주소 카드의 요청 전 SRC/DST 쌍에 O, 응답 전 SRC/DST 쌍에 R 배지를 붙이고, 중앙 기록의 Original·Reply에도 같은 배지를 둡니다
요청·응답이 중앙 기록 안으로 물리적으로 들어가는 패킷 경로처럼 보이지 않게 합니다. 외곽의 가는 조회 연결선 또는 동일 배지로 “같은 기록을 찾는다”는 대응만 보입니다
DNAT에서 바뀐 DST와 응답에서 바뀐 SRC를 emerald 테두리로 강조합니다. 클라이언트는 cyan, 중앙 상태는 violet, 보조 라벨은 slate를 사용합니다

### 보존해야 할 조건

- 원문에 있는 IP·포트 3쌍을 그대로 사용합니다. 프로토콜 종류를 임의로 TCP로 확정하지 않습니다
- 요청의 출발지는 바뀌지 않습니다. 응답 출발지의 역변환을 별도의 추가 masquerade/SNAT 설정으로 그리지 않습니다
- 두 키는 단순 역순 사본이 아니며 하나의 연결 객체에 대응합니다
- 표시 주소 외에도 주소군·netns·zone·프로토콜이 조회를 구분한다는 기존 문단을 유지합니다
- 그림은 패킷 전후 주소와 조회 관계입니다. 커널 내 정확한 hook 순서나 모든 필터 처리를 표현하는 그림이라고 주장하지 않습니다
- 후속 패킷도 조회·변환은 필요하다는 다음 절의 설명을 유지합니다

## 2. Overlay — 1500바이트 안에서 헤더가 차지하는 공간

대상: `src/content/essays/kubernetes/k8s-theory-overlay-native-routing.md`

새 자산: `public/diagrams/k8s-theory-overlay-native-routing-2.svg`

### 학습 질문과 기존 그림의 역할

새 질문은 “VXLAN의 50/70바이트는 무엇이며, 1450/1430은 어떤 패킷의 크기인가”입니다
기존 1번은 Overlay와 native routing의 주소·경로 차이입니다. 새 그림은 VXLAN 패킷 단면과 MTU의 측정 경계를 보여줍니다

### 삽입 위치와 연결문

`## MTU의 50바이트 계산에는 바깥 주소군 조건이 있습니다`에서 IPv4/IPv6 비교표와 그 아래 내부 IP·TCP 헤더 설명까지 읽은 뒤 넣습니다
바로 앞 문장: `암호화나 추가 헤더가 있으면 해당 공간도 별도로 계산해야 합니다`
바로 뒤 절: `### 인터페이스 MTU와 경로 MTU가 같은 값일 필요는 없습니다`

앞에 추가할 문장: `1500바이트의 경계 안에는 바깥 IP부터 내부 IP 패킷까지 들어가며, 바깥 Ethernet 헤더는 이 경계 밖에 있습니다`

이미지 alt: `underlay IP MTU 1500에서 VXLAN 바깥 IPv4 헤더 묶음 50바이트와 IPv6 헤더 묶음 70바이트를 제외해 내부 IP 예산 1450·1430을 구분한 단면|tall`

### ASCII 목업

560 × 약 1080, 같은 구성의 IPv4/IPv6 단면을 위아래로 놓습니다. 각 단면의 왼쪽 괄호가 IP MTU 경계를 표시하고, 오른쪽 괄호가 오버헤드 합을 묶습니다
헤더별 얇은 구간은 가독성을 위해 확대하므로 그림 상단에 `헤더 구간 확대 · 길이 비례 아님`을 명시합니다

```text
┌────────────────────────────────────────────┐
│    VXLAN이 내부 IP 공간을 차지하는 방식    │
│    가정: underlay MTU 1500                 │
│    추가 암호화·IP 옵션 없음                │
│    헤더 구간 확대 · 길이 비례 아님         │
│                                            │
│  바깥 IPv4                                │
│       ┌──────────────────────────────┐     │
│       │ 바깥 Ethernet   [MTU 밖]     │     │
│       └──────────────────────────────┘     │
│  ┌    ┌──────────────────────────────┐ ┐   │
│  │    │ 바깥 IPv4             20 B   │ │   │
│  │    ├──────────────────────────────┤ │   │
│  │    │ UDP                    8 B   │ │50B│

│  │    │ VXLAN                  8 B   │ │   │

│  │    │ 내부 IP 패킷          1450 B │     │

│                  1500 - 50 = 1450          │
│                                            │
│  바깥 IPv6                                │
│       ┌──────────────────────────────┐     │
│       │ 바깥 Ethernet   [MTU 밖]     │     │
│       └──────────────────────────────┘     │
│  ┌    ┌──────────────────────────────┐ ┐   │
│  │    │ 바깥 IPv6             40 B   │ │   │
│  │    ├──────────────────────────────┤ │   │
│  │    │ UDP                    8 B   │ │70B│
│1500 B ├──────────────────────────────┤ │   │
│  │    │ VXLAN                  8 B   │ │   │
│  │    ├──────────────────────────────┤ │   │
│  │    │ 안쪽 Ethernet         14 B   │ ┘   │
│  │    ╞══════════════════════════════╡     │
│  │    │ 내부 IP 패킷          1430 B │     │
│  └    └──────────────────────────────┘     │
│                  1500 - 70 = 1430          │
│                                            │
│  내부 IP 패킷 안에도 헤더가 있습니다       │
│  ┌───────────┬─────────────┬────────────┐   │
│  │ IP 헤더   │ TCP 등 헤더 │ 앱 데이터  │   │
│  └───────────┴─────────────┴────────────┘   │
│  바깥 주소군별 계산 · 추가 헤더는 별도     │
│  앱 데이터 크기나 Pod eth0 MTU 확정 아님  │
└────────────────────────────────────────────┘
```

오버헤드 amber, 내부 IP emerald, MTU 밖 Ethernet slate를 사용합니다. 단면을 감싸는 괄호는 “1500 B”를 수평 글자로 읽을 수 있도록 배치합니다
IPv6의 바깥 IP 40바이트는 원문의 70바이트와 기존 기본 IPv6 헤더 조건에서 유도한 값이며 실측이 아닙니다

### 보존해야 할 조건

- 1500은 원문에 이미 명시된 계산 가정입니다. 캡처 결과나 인터페이스 실측으로 표시하지 않습니다
- 바깥 Ethernet은 1500의 IP MTU 예산 밖, 안쪽 Ethernet14바이트는 VXLAN 운반 공간 안입니다
- 그림의 IPv4/IPv6는 바깥 주소군입니다. Pod의 내부 주소군을 가정하지 않습니다
- 내부 IP 1450/1430은 TCP 애플리케이션 데이터의 최대 길이가 아닙니다. 내부 IP·전송 헤더 공간이 또 필요합니다
- 모든 Pod `eth0` MTU가 1450/1430이라는 뜻이 아닙니다. 이어지는 DeviceMTU/RouteMTU 설명을 그대로 둡니다
- Geneve, 암호화, IP 옵션, 다른 부가 헤더에 숫자를 일반화하지 않습니다

## 3. CRD pruning — 보존되는 가지와 다시 잘리는 가지

대상: `src/content/essays/kubernetes/k8s-theory-crd-schema-pruning.md`

새 자산: `public/diagrams/k8s-theory-crd-schema-pruning-3.svg`

### 학습 질문과 기존 그림의 역할

새 질문은 “보존 확장이 있는 JSON 안에서도 왜 어떤 필드는 남고 어떤 필드는 없어지는가”입니다
기존 1번은 생성 요청의 필드 처리 단계, 2번은 본체/status/scale의 저장소 공유입니다. 새 그림은 한 JSON 조각의 구체적인 필드 변화만 다룹니다

### 삽입 위치와 연결문

`### 하위 구조를 선언한 곳에서는 가지치기가 다시 적용됩니다`에서 확장 YAML과 이어지는 네 문장을 읽은 뒤 넣습니다
바로 앞 문장: `스키마가 모르는 보존 데이터는 CEL에서 접근할 수 없습니다`
바로 뒤 문장: `CRD 전체의 옛 spec.preserveUnknownFields와 이 노드별 확장은 구분해야 합니다`

앞에 추가할 문장: `아래는 json에서 미선언 값을 보존하되, 그 안의 typed에는 enabled만 선언한 가정 예시입니다`

이미지 alt: `Ignore 또는 Warn으로 처리하는 가정 예시에서 루트의 미선언 필드는 제거하고 json의 임의 데이터는 보존하되 구조를 다시 선언한 typed 아래 extra는 제거하는 가지치기 범위|tall`

### 목업에서 사용할 가정

게시할 실행 예제 코드를 새로 추가하는 것이 아니라 그림 안의 데이터 조각을 위한 가정입니다
원문의 `json`과 `someRandomField: 42`를 재사용하고, 보존 범위 설명에 필요한 최소 하위 이름만 더합니다

- 루트는 object이고 `json`만 선언합니다. `someRandomField`는 미선언입니다
- `json`은 object이며 `x-kubernetes-preserve-unknown-fields: true`입니다
- `json.properties.typed`는 object이며 `enabled` boolean만 선언합니다
- `json.loose`와 `json.typed.extra`는 미선언입니다. loose는 보존 범위에 있고 typed.extra는 구조를 다시 선언한 범위에 있습니다
- object metadata·apiVersion·kind 등 문맥과 무관한 부분은 생략한 JSON 조각입니다
- mutating admission의 추가 패치나 기본값은 이 그림에서 다루지 않습니다

### ASCII 목업

560 × 약 1120, 스키마 경계 설명 → 입력 트리 → 결과 트리로 진행합니다. 삭제 필드는 입력에서 붉은 취소선/잘린 가지, 결과에서는 실제로 제거된 모양으로 나타냅니다

```text
┌────────────────────────────────────────────┐
│    보존 범위 안에서도 가지치기가 바뀝니다  │
│    설명을 위한 JSON 조각 · 가정 스키마     │
│                                            │
│  스키마 경계                               │
│  root: object                              │
│    └─ json: object  [미선언 값 보존]        │
│         └─ typed: object [구조 다시 선언]  │
│              └─ enabled: boolean           │
│                                            │
│  ① 요청의 JSON 조각                       │
│  {                                         │
│    someRandomField: 42     ✂ 미선언        │
│    json: {                                 │
│    ╭──────────── 보존 범위 ────────────╮   │
│    │ loose: "keep"                     │   │
│    │ typed: {                          │   │
│    │ ┌────── 다시 선언한 구조 ──────┐ │   │
│    │ │ enabled: true                │ │   │
│    │ │ extra: "drop"    ✂ 미선언   │ │   │
│    │ └──────────────────────────────┘ │   │
│    │ }                                │   │
│    ╰───────────────────────────────────╯   │
│    }                                       │
│  }                                         │
│                  │                         │
│       Ignore / Warn으로 진행하는 경우      │
│                  ▼                         │
│  ② 가지치기 결과의 개념 예시               │
│  {                                         │
│    json: {                                 │
│      loose: "keep",      [보존]            │
│      typed: {                              │
│        enabled: true     [선언한 필드]      │
│      }                                     │
│    }                                       │
│  }                                         │
│                                            │
│  Strict: 이 결과로 진행하지 않고 400 거절  │
│  저장된 etcd 바이트 자체를 그린 것은 아님  │
└────────────────────────────────────────────┘
```

실제 SVG에서는 JSON 키와 문자열에 따옴표를 써서 데이터 조각을 보여주거나, 중괄호 대신 동일 필드를 가진 JSON 트리로 통일합니다. 도형 설명과 유효 JSON 표기를 애매하게 혼합하지 않습니다
보존 범위 violet, 선언된 구조 emerald, 제거/Strict rose, 경계 slate로 구분합니다
길이가 긴 실제 확장 키는 작은 글자로 줄여 넣지 않고 `desc`와 앞 본문 YAML에 남깁니다. 그림에는 `json: 미선언 값 보존` 라벨을 사용합니다

### 보존해야 할 조건

- 이 그림은 `fieldValidation=Ignore/Warn`으로 해당 unknown-field 요청이 진행하는 경우입니다. 성공 보장이 아니라 가지치기 범위의 예시입니다
- Strict 요청은 같은 결과를 저장하는 경로가 아니라 HTTP400 거절입니다. 현재 kubectl 기본 strict에 관한 앞 문단을 그대로 둡니다
- 스키마에서 보존하는 미선언 데이터와 Strict에서 오류로 다루는 미선언 필드를 동일시하지 않습니다. 이 예시는 루트 someRandomField와 typed.extra가 거절·제거 대상입니다
- `json.loose` 보존은 `typed` 아래까지 무조건 보존한다는 뜻이 아닙니다
- `properties` 또는 `additionalProperties`로 다시 구조를 선언한 범위에서 pruning이 적용된다는 원칙을 유지합니다
- “저장 전·저장 후”, “etcd에 저장된 실제 값”이라는 제목을 쓰지 않습니다. 읽기·변환·같은 GVK 저장 분기 때문에 실제 저장 바이트는 별도 판정입니다
- CEL에서 미선언 보존 필드를 참조할 수 없다는 문단과 null/defaulting 조건을 삭제하지 않습니다

## 4. Snapshot — API 객체와 저장 실물, 복원으로 생기는 새 볼륨

대상: `src/content/essays/kubernetes/k8s-theory-volume-expansion-snapshots-ephemeral.md`

새 자산: `public/diagrams/k8s-theory-volume-expansion-snapshots-ephemeral-3.svg`

### 학습 질문과 기존 그림의 역할

새 질문은 “VolumeSnapshot과 Content 중 실제 데이터는 어디에 있으며, 복원하면 어느 볼륨이 달라지는가”입니다
기존 1번은 볼륨 확장, 2번은 두 임시 볼륨의 수명입니다. 새 그림은 원본·스냅샷·새 복원 볼륨의 대응 관계입니다

### 삽입 위치와 연결문

`### 복원은 새 PVC를 채우는 요청입니다`의 dataSource YAML과 이어지는 복원 설명 뒤에 넣습니다
바로 앞 문장: `현재 getSnapshotSource는 바인딩 참조·드라이버 일치·readyToUse·snapshot handle 등을 확인합니다`
바로 뒤 문장: `dataSource는 VolumeSnapshot과 PVC를 받을 수 있고, dataSourceRef는 더 넓은 non-core 소스도 표현합니다`

앞에 추가할 문장: `API 오브젝트와 스토리지 안의 실물을 나눠 보면, 스냅샷을 참조하는 새 PVC가 원본과 다른 볼륨에 연결되는 관계가 드러납니다`

이미지 alt: `원본 PVC·PV와 원본 볼륨, VolumeSnapshot·VolumeSnapshotContent와 실제 스냅샷, dataSource로 복원한 새 PVC·PV와 새 볼륨의 대응 관계|tall`

### ASCII 목업

560 × 약 1180, 왼쪽 API/오른쪽 스토리지 실물의 두 열을 유지하되 세 단계는 아래로 흐릅니다
API 열의 긴 이름은 VolumeSnapshot / Content 두 줄처럼 줄바꿈합니다. 상단의 작은 범례로 이름을 축약하지 않아도 읽힐 공간을 확보합니다
API 간 바인딩/참조는 화살촉 없는 연결선 + 명시 라벨, 실제 작업은 화살촉 있는 굵은 선 + RPC 이름으로 구분합니다

```text
┌────────────────────────────────────────────┐
│       스냅샷으로 새 볼륨을 준비합니다      │
│       동적 생성 → 같은 namespace 복원     │
│                                            │
│       Kubernetes API     스토리지 실물     │
│                                            │
│  ① 원본                                   │
│  ┌───────────────┐                         │
│  │ 원본 PVC      │                         │
│  └───────┬───────┘                         │
│       바인딩                               │
│  ┌───────┴───────┐        ╭─────────────╮  │
│  │ 원본 PV       │─대응───│ 원본 볼륨   │  │
│  └───────────────┘        ╰─────────────╯  │
│                            snapshot 생성  │
│                                  │         │
│  ② 스냅샷                       ▼          │
│  ┌────────────────┐                       │
│  │ VolumeSnapshot │ source-snapshot        │
│  │ (namespace)    │                       │
│  │ source: 원본 PVC│                       │
│  └────────┬───────┘                       │
│        바인딩                              │
│  ┌────────┴───────┐        ╭─────────────╮  │
│  │ VolumeSnapshot │─handle─│ 실제         │  │
│  │ Content        │  대응  │ 스냅샷       │  │
│  │ (cluster)      │        ╰─────────────╯  │
│  └────────────────┘               │        │
│  snapshot-controller: 생성·바인딩   │        │
│  csi-snapshotter → driver: CreateSnapshot   │
│                                   │        │
│  ③ 복원                           │        │
│  ┌──────────────────┐             │        │
│  │ 새 PVC            │        스냅샷을 소스로│
│  │ dataSource:       │        CreateVolume │
│  │ source-snapshot   │             ▼        │
│  └────────┬──────────┘      ╭─────────────╮  │
│        바인딩               │ 새 볼륨     │  │
│  ┌────────┴──────────┐      │             │  │
│  │ 새 PV             │─대응─│             │  │
│  └───────────────────┘      ╰─────────────╯  │
│  external-provisioner → driver: CreateVolume│
│                                            │
│  바인딩·driver·readyToUse·handle 확인 필요  │
│  원본을 되감지 않고 새 볼륨을 준비         │
└────────────────────────────────────────────┘
```

VolumeSnapshot의 source에서 원본 PVC로, 새 PVC의 dataSource에서 VolumeSnapshot으로 올라가는 두 참조선은 API 열 왼쪽 여백으로 우회하고 각각 `source 참조`, `dataSource 참조`를 표시합니다. 이 선과 데이터 생성 화살표가 섞이지 않게 분리합니다
원본 볼륨과 새 볼륨은 원통, 실제 스냅샷은 원통 위에 정지된 사본 표식을 붙이거나 겹친 판 형태로 그려 API 사각형과 구별합니다
API emerald, 스토리지 violet, controller/RPC 라벨 amber, 범위/참조 slate를 사용합니다
VolumeSnapshotClass는 이 그림의 생성 경로에서 `driver·매개변수`를 제공하는 작은 상단 보조 카드로 넣을 수 있지만, 원본/스냅샷/복원 대응의 가독성을 해치면 앞 본문 표에 맡깁니다. 클래스가 실제 데이터라는 오해를 만들지 않습니다

### 보존해야 할 조건

- 그림은 동적 스냅샷 생성 뒤 같은 namespace의 Snapshot으로 복원하는 예시입니다. 정적 등록 경로는 앞 본문에 그대로 둡니다
- VolumeSnapshot과 Content는 API 오브젝트이며 실제 데이터 저장 실물은 스토리지 백엔드에 따로 있습니다
- 원본 PVC를 스냅샷의 source로 지정하는 참조와 새 PVC의 dataSource 참조를 서로 다른 선으로 표시합니다
- 공통 snapshot-controller가 Content 생성·바인딩을 조정하고 csi-snapshotter가 드라이버에 CreateSnapshot을 요청합니다
- 복원 CreateVolume의 요청 주체는 external-provisioner입니다. snapshot-controller가 새 볼륨을 직접 만드는 것처럼 그리지 않습니다
- 새 PVC/새 PV/새 볼륨과 원본을 시각적으로 분리합니다. 제자리 롤백 화살표를 그리지 않습니다
- readyToUse·driver·바인딩·handle 조건은 그림 안에도 짧게 남깁니다
- 컨트롤러 설치·드라이버 capability와 애플리케이션 일관성 조건은 본문을 유지합니다. 그림에서 즉시 완료·완전 복사·애플리케이션 일관성을 보장하지 않습니다
- 스토리지 구현의 copy-on-write·물리 복사 방식이나 크기·시간은 가정하지 않습니다
- deletionPolicy와 finalizer까지 한 장에 넣지 않습니다. 원본의 삭제 조건 설명은 별도로 유지합니다
