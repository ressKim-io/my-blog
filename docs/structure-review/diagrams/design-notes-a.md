## 1. init·sidecar·앱의 실행 구간과 요청 집계

대상: src/content/essays/kubernetes/k8s-theory-resource-accounting-scoring.md

새 경로: public/diagrams/k8s-theory-resource-accounting-scoring-3.svg

### 기존 그림과 새 질문

기존 -1은 RuntimeClass overhead가 Pod 요청과 Filter·Score로 이어지는 절차이고, -2는 노드 A/B의 균형 점수 비교입니다
새 그림은 “왜 모든 init을 더하지 않으며, sidecar는 뒤 단계의 요청에도 계속 더하는가?”를 설명합니다
실행 막대의 겹침과 같은 구간의 요청 합계를 수직으로 맞추는 것이 핵심입니다

### 정확한 삽입 위치

`## Pod 요청은 실행 시점별로 계산합니다`에서 다음 문장 뒤에 넣습니다

> sidecar를 일반 init처럼 최대값 하나로만 계산하거나, 모든 init을 동시에 실행하는 것처럼 더하면 이 계산과 달라집니다

바로 다음 `기본 활성인 PodLevelResources를 사용하는 호출에서는...` 문단은 그대로 이어집니다
새 그림은 컨테이너 수준 집계까지만 보여 주고 Pod-level 대체와 overhead는 이 기존 문단이 설명합니다

### 목업: 약 560 × 760

```text
실행이 겹치는 구간의 요청을 더합니다
가정: init A → sidecar S → init B → 앱 C·D

                     실행 단계 →
               ①        ②        ③        ④
             A 실행    S 시작    B 실행    앱 실행

일반 init A  [=======]
sidecar S              [==========================>
일반 init B                       [=======]
앱 C                                       [======>
앱 D                                       [======>

             ┆         ┆         ┆         ┆
단계별 요청   A         S        S+B      S+C+D
             └─────────┴─────────┴─────────┘
                              ↓
                자원 하나씩 최댓값 선택
               max(A, S, S+B, S+C+D)

       CPU와 메모리의 최대 단계는 다를 수 있음

범례: 문자 = 각 컨테이너의 해당 자원 request
막대 = 함께 실행될 수 있는 구간, 시간·사용량 축척 아님
범위: 컨테이너 수준 집계
```

실제 SVG에서는 각 행 왼쪽의 이름과 막대를 연결하고, 동일 단계의 수직 가이드를 옅게 표시합니다
sidecar 막대는 amber, 앱 두 줄은 emerald, 일반 init은 slate로 구별합니다
최댓값 결과 영역에 특정 단계 하나를 강조하지 않습니다
그림에 수치를 넣지 않으므로 CPU·메모리 모두 동일 단계를 선택한다는 인상을 만들지 않습니다

### 조건·오해 방지

- S는 `restartPolicy: Always`인 restartable init이며 이 배치 순서는 설명을 위한 가정입니다
- A와 B는 동시에 실행하는 것으로 그리지 않습니다
- S가 시작된 이후의 B·앱 구간에만 S를 더합니다
- 단계 ②의 S 단독 값도 표시해 시작 단계를 누락하지 않습니다
- 막대는 실제 실행 기록·보장된 연속 가동 시간·사용량이 아닙니다
- 자원별 최댓값을 고르는 기본 집계이며 최종 Pod 요청의 모든 조건을 구현한 그림이 아닙니다
- Pod-level request의 해당 자원별 대체와 이후 overhead 추가는 인접한 기존 본문에 남깁니다

### 최소 연결문·alt

그림 앞 한 문장:

> 다음은 일반 init A 뒤에 sidecar S, 일반 init B, 앱 C·D를 두는 가정입니다

alt 초안:

> 일반 init A·B의 순차 실행과 sidecar S의 후속 구간 겹침을 비교하고 각 단계의 요청 합계에서 자원별 최댓값을 고르는 예시

## 2. HPA의 이동하는 축소 안정화 창

대상: src/content/essays/kubernetes/k8s-theory-hpa-scale-subresource.md

새 경로: public/diagrams/k8s-theory-hpa-scale-subresource-3.svg

### 기존 그림과 새 질문

기존 -1은 지표에서 목표 쓰기까지의 전체 절차, -2는 HPA Update·GitOps Apply와 같은 Deployment 저장 객체의 관계입니다
새 그림은 “새 추천이 3인데 왜 최근 추천 7이 계속 영향을 주며, 시간이 지나면 무엇이 달라지는가?”를 설명합니다
같은 시간축 위에서 안정화 창의 위치만 오른쪽으로 이동한 두 장면을 위아래로 놓습니다

### 정확한 삽입 위치

`## 안정화 창은 과거의 추천값을 기억합니다`에서 다음 예시 직후입니다

> 예를 들어 창 안에 추천 7과 3이 남아 있다면 7을 선택하므로 낮아진 추천 3에 바로 맞추지 않습니다

다음 `기본 scale up 창은 0초입니다` 문단과 기본값 표는 유지합니다

### 목업: 약 560 × 720

```text
축소 판단은 창 안의 가장 큰 추천을 봅니다
표시한 숫자 = 제한 적용 전 추천값

① 추천 7과 3이 모두 창 안에 있음

과거                                      이후 →
   ┌────────── 축소 안정화 창 ──────────┐
───┼────●────────────────●─────────────┼───────
   │    7                3             │
   └───────────────────────────────────┘
                                      현재 A
                창 안 최댓값: 7

                    시간 경과 ↓

② 오래된 7이 창 밖으로 나감

과거                                      이후 →
               ┌────── 축소 안정화 창 ─────────┐
────────●──────┼─────────●────────────────────┼
        7      │         3                    │
      창 밖    └──────────────────────────────┘
                                             현재 B
                창 안 최댓값: 3
         가정: 창 안에 더 큰 새 추천이 없음

범례: ● 추천 이력 / 음영 영역: 이번 판단에 쓰는 창
선택된 추천은 실제 replica 수·Ready Pod 수가 아님
이후 변경 정책과 min/max 등도 평가
```

두 장면의 시간축 위치와 창의 폭을 일치시키며, 창의 좌우 경계를 같은 양만큼 이동시킵니다
목업의 문자 폭 때문에 생기는 차이는 실제 SVG 좌표에서 바로잡습니다
추천 점은 slate, 현재 포함된 창은 amber 옅은 면, 최댓값 표시는 같은 amber 강조를 씁니다
창 밖의 7은 점선 윤곽·`창 밖` 라벨을 함께 사용하며 삭제된 실제 Pod 모양으로 표현하지 않습니다

### 조건·오해 방지

- 7·3은 원문의 가정 예시에 있는 추천값이며 실제 replica 이력이 아닙니다
- 두 번째 장면은 더 큰 새 추천이 없고 3이 창 안에 남는 경우만 보여 줍니다
- “300초 후 7개→3개”라는 고정 시간 전환이나 확정된 Pod 축소를 그리지 않습니다
- 그림은 scale down의 창 안 최댓값 규칙에 한정합니다
- scale up 창의 최솟값 규칙과 0초 기본값은 바로 뒤 기존 문단에 남깁니다
- 최종 저장 목표·현재 replica·Ready 개수를 같은 숫자로 표시하지 않습니다
- behavior 유무와 이후 변경 속도·min/max 조건을 이 작은 그림에 모두 옮겨 새 절차도로 만들지 않습니다

### 최소 연결문·alt

기존 예시 문장만으로 삽입 이유가 충분해 별도의 도입 문장은 추가하지 않습니다
그림의 두 번째 장면에 `창 안에 더 큰 새 추천이 없음`이라는 가정 라벨을 넣습니다

alt 초안:

> 축소 안정화 창 안에 추천 7과 3이 함께 있을 때는 7을 고르고 오래된 7이 창 밖으로 나간 뒤 더 큰 추천이 없으면 3을 고르는 두 시점

## 3. usage에서 working set을 계산하는 회계 그림

대상: src/content/essays/kubernetes/k8s-theory-page-cache-reclaim-oom.md

새 경로: public/diagrams/k8s-theory-page-cache-reclaim-oom-3.svg

### 기존 그림과 새 질문

기존 -1은 커널의 할당·회수와 kubelet 축출의 별도 경로, -2는 부모·자식 cgroup 한도와 중복 회계입니다
새 그림은 “usage에서 inactive_file을 빼면 그 메모리가 비어 있는가?”를 설명합니다
같은 메모리 상태에서 표시하는 양만 바뀐다는 것을 해칭이 남아 있는 두 막대로 보여 줍니다

### 정확한 삽입 위치

`## working set과 available은 회계 모델입니다`의 다음 코드 블록 직후입니다

> working set = max(usage - inactive_file, 0)

뒤의 `여기서 제외된 캐시도 회수와 재접근에 비용이 듭니다` 문단은 그대로 유지합니다
계산 공식·그림·회수 비용 순서로 읽힙니다

### 목업: 약 560 × 640

```text
working set은 사용량에서 계산한 값입니다
같은 메모리 상태를 두 방식으로 표시

usage: 이 범위에서 이미 사용 중인 양
┌──────────────────────────┬─────────────────┐
│ 계산에 남는 몫           │//// inactive_file│
│                          │//// 사용 중 캐시 │
└──────────────────────────┴─────────────────┘
             │                         │
             │                  통계 계산에서 뺌
             ▼                         ▼
working set에 포함                포함하지 않음
┌──────────────────────────┬ · · · · · · · · ┐
│ working set              │//// 캐시는 남음 │
└──────────────────────────┴ · · · · · · · · ┘

          max(usage - inactive_file, 0)
          계산 결과의 하한은 0

범례: //// = 사용 중인 inactive_file 캐시
       점선 = working set 집계에서 제외
빈 메모리로 바뀌었다는 뜻이 아님

확인 범위: cAdvisor/lib v0.60.5 · cgroup v2
inactive_file 항목이 있는 계산 경로
폭은 축척 아님
```

상단 usage 바는 전체 테두리, 하단 working set 바는 집계한 부분만 실선 테두리로 강조합니다
하단 오른쪽에도 상단과 같은 해칭을 남겨 “통계에서 뺐음”을 “해제했음”으로 읽지 않게 합니다
하단 오른쪽은 막대 합계를 구성하는 두 번째 지표가 아니라 같은 상태를 설명하는 보조 잔상입니다
실제 SVG는 짧은 인접 라벨 `집계 제외 / 메모리는 사용 중`으로 이 점을 설명합니다
메모리 집계 영역은 violet, 캐시는 slate 해칭, 범위 설명은 slate를 사용합니다

### 조건·오해 방지

- 그림은 inactive_file이 usage 이하인 개념 예시입니다
- 일반식의 `max(..., 0)`를 그대로 표시하고 어떤 경우에도 음수 working set을 그리지 않습니다
- inactive_file 전체가 즉시 무료로 회수되거나 새 요청에 바로 할당될 수 있다고 표현하지 않습니다
- 실제 물리 RAM 전체의 분할도, memory.stat 모든 항목의 합산도 아닙니다
- `limit - working set`을 실제 빈 메모리라고 표시하지 않습니다
- limit 선을 추가해 그 아래가 안전하거나 OOM이 없다는 인상을 만들지 않습니다
- cAdvisor/lib v0.60.5 cgroup v2의 해당 항목이 있는 경로임을 표시하며 모든 런타임의 공통식으로 일반화하지 않습니다
- 비율을 계산할 원문 수치는 없으므로 용량·퍼센트는 넣지 않습니다

### 최소 연결문·alt

기존 설명과 공식이 충분하므로 새 본문 문장은 추가하지 않습니다
그림 자체에 계산 경로와 비축척 조건을 넣고 기존 회수 비용 문장을 바로 이어 둡니다

alt 초안:

> 사용 중인 usage에서 inactive_file을 계산상 제외해 working set을 표시하지만 제외한 캐시는 여전히 메모리를 사용 중이라는 회계 관계

## 4. 한 서버 안의 NUMA별 CPU·메모리·장치 배치

대상: src/content/essays/kubernetes/k8s-theory-device-resource-allocation.md

새 경로: public/diagrams/k8s-theory-device-resource-allocation-4.svg

### 기존 그림과 새 질문

기존 -1은 기본 device plugin 단계, -3은 DRA 단계, -2는 manager들의 NUMA 힌트 병합입니다
새 그림은 “한 Kubernetes Node 안에 NUMA node가 여러 개 있다는 말은 실제로 어떤 배치인가?”를 설명합니다
서버 외곽과 내부의 두 하드웨어 영역을 그려, 단어를 아는 독자만 이해할 수 있었던 기존 manager 그림의 전제를 보완합니다

### 정확한 삽입 위치

`## NUMA 정렬은 개수 검사 뒤의 노드 내부 판단입니다`에서 다음 문장 뒤에 삽입합니다

> Pod를 실행할 서버를 나타내는 Kubernetes Node와 다르며 한 Kubernetes Node 안에 여러 NUMA node가 있을 수 있습니다

이후 `CPU가 어느 위치의 메모리나 장치에 접근하는지에 따라 접근 거리와 비용이 달라집니다` 문단과 기존 -2 manager 그림을 그대로 유지합니다
물리 배치 → 위치가 중요한 이유 → 이를 판단하는 manager 순서입니다

### 목업: 약 560 × 760

```text
서버 한 대 안에도 자원 위치가 나뉩니다
가정: NUMA 두 곳에 GPU가 하나씩 있는 배치

┌────────── Kubernetes Node: 서버 한 대 ────────┐
│                                              │
│  ┌── NUMA A ──────┐     ┌── NUMA B ──────┐   │
│  │                │     │                │   │
│  │  [CPU 칩 A]    │     │  [CPU 칩 B]    │   │
│  │      │         │     │                │   │
│  │ 같은 위치 접근 │     │                │   │
│  │      ▼         │     │                │   │
│  │ [메모리 뱅크 A]│     │ [메모리 뱅크 B]│   │
│  │                │     │                │   │
│  │  [GPU 카드 A]  │     │  [GPU 카드 B]  │   │
│  └────────────────┘     └────────────────┘   │
│          │                         ▲         │
│          └ - - 다른 위치 접근 - - ┘         │
│          (CPU A에서 GPU B로 가는 예시)        │
│                                              │
└──────────────────────────────────────────────┘

         장치 수량: GPU 2개
         위치: 서로 다른 NUMA 영역

한 NUMA에 CPU·메모리·장치를 맞출 수 있는지는
수량과 별도로 확인

범례: 실선 = 같은 NUMA 위치의 관계
       점선 = 다른 NUMA 위치에 접근하는 관계
도형·선 길이는 실제 거리·지연 수치가 아님
```

실제 SVG에서는 CPU를 핀 있는 칩, 메모리를 여러 칸의 뱅크, GPU를 커넥터 있는 카드 모양으로 그립니다
외곽 서버는 amber, 메모리 뱅크는 violet, CPU·GPU는 amber 또는 slate로 제한합니다
점선의 시작점은 반드시 CPU A 칩에서 출발하도록 연결해 GPU A→GPU B의 통신으로 오해하지 않게 합니다
모바일에서 관계선이 이름 위를 지나지 않도록 CPU A에서 중앙 여백으로 선을 빼고 GPU B로 이어집니다

### 조건·오해 방지

- NUMA 두 곳과 GPU 한 개씩은 개념 설명을 위한 가정이며 실제 장비 구조를 측정한 결과가 아닙니다
- 그림은 하드웨어 위치를 설명하며 특정 자원이 현재 free인지, 전용 할당됐는지는 표시하지 않습니다
- CPU A의 두 접근 관계는 가능한 위치 차이를 보여 주는 예시이며 특정 요청의 실제 I/O 추적이 아닙니다
- Kubernetes Node 두 대 또는 Pod 두 개처럼 그리지 않습니다
- GPU 수량 충분만으로 NUMA 정렬 성공을 뜻하지 않습니다
- 떨어진 배치라는 이유만으로 모든 정책에서 admission 실패를 뜻하지 않습니다
- `none`·`best-effort`·`restricted`·`single-numa-node` 판단은 기존 정책 표에 유지하며 그림에 실패 X를 찍지 않습니다
- GPU를 요청하면 CPU·Memory Manager의 전용 할당이 자동으로 주어진다는 표시를 넣지 않습니다
- 기본 device plugin의 수량 검사와 DRA의 선택 조건을 하나의 스케줄러 기능으로 섞지 않습니다

### 최소 연결문·alt

본문은 기존 정의와 이유 문단으로 충분하므로 별도 도입 문장은 추가하지 않습니다
그림 안 첫 문장에 가정 배치임을 밝힙니다

alt 초안:

> 한 Kubernetes Node 안의 두 NUMA 영역에 CPU·메모리·GPU가 나뉘어 있고 같은 위치 접근과 다른 위치 접근이 구분되는 하드웨어 배치 가정

## 추가 기록

새 파일 네 경로가 기존 SVG와 충돌하지 않는 것을 파일 목록으로 확인했습니다
현재 목업은 해당 글의 고정 소스 범위에서 설명한 관계를 시각화하며 외부 기술 재확인을 새로 수행한 결과는 아닙니다
검토서의 항목을 다시 구현하거나 기존 기술 주장·버전·조건을 바꾸는 제안은 포함하지 않았습니다
