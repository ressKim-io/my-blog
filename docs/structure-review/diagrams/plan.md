# Kubernetes 이론 글: 추가 그림 8장 목업

상태: 사용자가 8장 목업을 승인했으며 제작·독립 검토를 완료했습니다
최종 결과는 [그림 목록](README.md)과 [실행 검증](verification.md)에 기록했습니다

기존 71편의 SVG 145장에 다음 8장을 추가합니다
각 그림은 실행 구간, 주소 변화, 메모리 회계, 물리 배치 등 기존 그림이 자세히 보여주지 않는 관계를 설명합니다
아래 ASCII는 디자인 검토용이며 게시 본문에는 SVG를 사용합니다

## 제작 범위와 검증

- 제작 A: 자원 계산·HPA·페이지 캐시·NUMA 4편
- 제작 B: conntrack·MTU·CRD 가지치기·스냅샷 4편
- 별도 검토자: 그림과 본문 연결, 기술 조건, 모바일·데스크톱 렌더링 검토
- 변경: 새 SVG 8개, 대상 본문 8편의 삽입·필요한 짧은 연결 설명, 이 작업 기록
- 그림: 기존 Cocoon 색상, 폭 560px 안팎, 한글 라벨, title·desc·alt 포함
- 확인: 375px 화면의 본문 폭과 데스크톱 렌더링, XML·링크·MDX·본문 보존·lint·정적 빌드

세부 배치와 삽입 위치는 [제작 A 상세](design-notes-a.md), [제작 B 상세](design-notes-b.md)에 있습니다
기술 조건은 [독립 검토 기준](review-checklist.md)에 기록합니다

## 1. 자원 계산: 함께 실행되는 구간

삽입: 「Pod 요청은 실행 시점별로 계산합니다」의 기본 집계 설명 뒤

```text
                 실행 단계 →
               ①      ②       ③        ④
일반 init A   [====]
sidecar S            [====================>
일반 init B                  [====]
앱 C·D                                 [==>

단계별 요청    A       S      S+B      S+C+D
                         ↓
              자원별로 가장 큰 합계 선택
```

문자는 해당 자원의 request, 막대는 겹치는 실행 구간입니다
실측 시간·사용량 그래프가 아니며 CPU와 메모리가 서로 다른 단계에서 최대가 될 수 있습니다
Pod-level 대체와 overhead는 인접한 기존 본문에서 이어 설명합니다

## 2. HPA: 움직이는 축소 안정화 창

삽입: 「안정화 창은 과거의 추천값을 기억합니다」의 추천 7·3 예시 뒤

```text
시간 →
A  [      ● 7            ● 3       ] 현재 A
                 창 안 최댓값 7

B         ● 7 [         ● 3              ] 현재 B
          창 밖          창 안 최댓값 3
```

두 창의 폭은 같고 위치만 이동합니다
숫자는 제한 적용 전 추천값이며 두 번째 장면은 더 큰 새 추천이 없는 가정입니다
선택한 추천과 실제 Pod 수를 구분하고 이후 정책·min/max 평가도 남깁니다

## 3. 페이지 캐시: 통계에서 제외한 메모리

삽입: working set 계산식 뒤

```text
usage       [ 계산에 남는 몫 | //// inactive_file ]
                     같은 메모리 상태
working set [ 집계에 포함   ] //// 집계에서 제외
                              캐시는 사용 중

           max(usage - inactive_file, 0)
```

해칭을 두 줄 모두에 남겨 통계의 뺄셈이 메모리 해제를 뜻하지 않도록 합니다
원문의 cAdvisor/lib·cgroup v2 계산 범위를 표시하고 막대 폭에 실측 비율을 부여하지 않습니다

## 4. NUMA: 서버 한 대 안의 자원 위치

삽입: NUMA node와 Kubernetes Node의 차이를 설명한 직후

```text
┌──────── Kubernetes Node 한 대 ────────┐
│  NUMA A              NUMA B          │
│  [CPU 집합]          [CPU 집합]       │
│  [메모리]            [메모리]         │
│  [GPU A]             [GPU B]          │
│       같은 위치 / 다른 위치 접근     │
└──────────────────────────────────────┘
        GPU 개수와 위치 조건을 구분
```

가정한 배치이며 NUMA 영역이 언제나 소켓이나 CPU 칩 하나와 일치한다고 표현하지 않습니다
자원 위치 그림과 정책별 admission 결과를 분리하며, 기존 정책 표와 manager 흐름도는 이어 둡니다

## 5. Conntrack: 양방향 주소가 바뀌는 한 연결

삽입: Original·Reply 키와 NAT 상태를 설명한 절의 끝

```text
요청  클라이언트 → Service
                 ↓ 목적지 DNAT
      클라이언트 → backend

      [Original 키 / Reply 키 / NAT 상태]
                  연결 기록 하나

응답  backend → 클라이언트
                 ↓ 같은 NAT 상태로 역변환
      Service → 클라이언트
```

실제 그림에는 원문의 IP·포트를 그대로 표시합니다
IPv4·추가 SNAT 없음의 가정이며, 키 조회 관계와 패킷의 이동 화살표를 구별합니다

## 6. MTU: 패킷 안의 헤더 공간

삽입: MTU 1500 가정의 IPv4·IPv6 비교와 내부 헤더 설명 뒤

```text
바깥 Ethernet                              MTU 밖
┌──────────── underlay IP MTU 1500 ────────────┐
│ IPv4: IP20 + UDP8 + VXLAN8 + 안쪽 Ethernet14 │
│       추가 공간 50 | 내부 IP 패킷 1450       │
└─────────────────────────────────────────────┘
┌──────────── underlay IP MTU 1500 ────────────┐
│ IPv6: IP40 + UDP8 + VXLAN8 + 안쪽 Ethernet14 │
│       추가 공간 70 | 내부 IP 패킷 1430       │
└─────────────────────────────────────────────┘
```

SVG에서는 헤더별 단면을 세로로 쌓고 MTU 경계를 괄호로 표시합니다
바깥 주소군별 가정이며 추가 암호화·IP 옵션이 없습니다
1450·1430은 내부 IP 패킷 예산이고, 헤더 폭은 가독성을 위해 비례 없이 확대합니다

## 7. CRD: 남는 필드와 제거되는 필드

삽입: 보존 노드 안에서 하위 구조를 선언하면 가지치기가 재개된다는 설명 뒤

```text
가정 스키마: json은 미선언 값 보존
             json.typed에는 enabled만 선언

입력                           가지치기 결과
someRandomField: 42  [제거]
json                           json
 ├ loose: keep      [보존]      ├ loose: keep
 └ typed                       └ typed
    ├ enabled: true [선언]         └ enabled: true
    └ extra: drop   [제거]
```

실제 그림은 스키마 경계와 입력·결과를 위아래로 배치합니다
Ignore/Warn으로 진행하는 가지치기 단계의 개념 예이며, Strict 거절과 최종 저장 바이트는 별도로 구분합니다

## 8. 스냅샷: API 오브젝트와 저장소 실물

삽입: 새 PVC의 dataSource와 복원 조건 설명 뒤

```text
Kubernetes API                      스토리지
원본 PVC — PV                      원본 볼륨
                                      ↓ 생성
VolumeSnapshot — Content           실제 스냅샷
       ↑ dataSource 참조               ↓ 복원 소스
새 PVC — 새 PV                     새 볼륨
```

참조·바인딩 선과 실제 생성 작업의 화살표를 구분합니다
같은 namespace의 동적 스냅샷·복원 예이며 처리 주체와 readyToUse 등 조건을 짧게 표시합니다
스토리지의 복사 구현이나 애플리케이션 일관성을 보장하는 그림으로 만들지 않습니다

## 제작 순서

목업 승인 후 두 제작자가 담당 파일이 겹치지 않게 구현합니다
별도 검토자가 수정 본문과 렌더링한 SVG를 보고 문제를 제작자에게 반송합니다
재확인 뒤 메인이 8장 사이 표현의 일관성과 실행 검증 결과를 확인합니다
