# 후속 모델의 구조 편집 지침

현재 채팅의 결과물은 개선안입니다. 실제 블로그 수정은 사용자가 다음 작업에서 요청한 범위에만 적용합니다
이 지침이 commit·push·배포나 71편 일괄 수정을 자동으로 허가하지 않습니다

## 한 번에 읽을 문서

1. 저장소 `AGENTS.md`와 [공통 말투 기준](../writing-voice.md)
2. [구조 판단 기준](principles.md)
3. [작업 목록](index.md)에서 고른 글별 검토서
4. 해당 원문 전문과 인접 그림, 필요한 선행 글의 해당 절

파일 해시가 [manifest.json](manifest.json)과 다르면 원문이 바뀐 것입니다
기존 행 번호대로 기계적으로 이동하지 말고 인용 문구·헤더와 현재 문맥을 다시 대조합니다

## 실제 편집

- 먼저 대상 글의 권장 순서를 원문 절·문단에 대응시킵니다
- 지적 사항은 편집 판단입니다. 무조건 전부 적용하거나 모든 글을 같은 모양으로 만들지 않습니다
- 기본 사례를 먼저 완성하되 결과를 바꾸는 조건은 해당 설명 옆에 남깁니다
- 심화로 이동할 문단을 삭제하지 않습니다. 분리 게시·새 글 생성·시리즈 재정렬은 별도 요청이 있을 때 결정합니다
- 구조 예시와 연결 문장은 복사할 완성 원고가 아닙니다. 원문 사실·가정·현재 용어에 맞게 씁니다
- source URL, 코드, 수치, 버전과 불확실성을 보존합니다. 변경이 필요하면 기술 검증 항목으로 분리합니다
- slug·date·series·category와 기존 자산을 임의로 바꾸지 않습니다
- 사용자 경험과 실측 결과를 만들지 않습니다
- 그림은 설명하는 문단과 함께 이동할 수 있습니다. 그림 내용이나 사이트 레이아웃 변경이 필요하면 적용되는 디자인 규칙을 확인합니다

## 검증과 보고

편집 후 원문과 대조해 누락된 사실·조건·코드·출처·이미지 참조를 확인합니다
각 글의 검토서에 적힌 독자 확인 질문에 본문만으로 답할 수 있는지 읽습니다
단락 이동으로 깨진 지시어·절 참조·링크도 확인합니다
MDX·빌드 검증은 렌더링 확인에 사용하며 설명 품질의 근거로 대신하지 않습니다
사용 가능한 명령은 현재 package.json과 저장소 지침에서 확인하고 실제 실행 결과만 보고합니다

처음에는 PVC 또는 informer 한 편을 편집하고 원문과 새 전개를 비교하는 방식을 권합니다
한 편의 기준이 잡히면 작은 묶음으로 진행하고, 완료한 편과 남은 편을 따로 기록합니다
[편집 묶음](batches.md)은 71편을 1~3편 단위로 배정했고, [시리즈별 연결](series-map.md)은 상세 설명을 어느 글이 맡는지 정리합니다

`verify.py`는 이 검토 시점의 원문이 보존됐는지 검사합니다
후속 작업에서 본문을 실제로 편집하면 원문 해시·인용 행 검사가 실패하는 것이 정상이며, 통과시키려고 기준 해시를 임의로 덮어쓰지 않습니다
편집 검증은 변경 전후의 내용 보존과 MDX·링크·빌드 결과로 별도 기록합니다

## 다음 채팅에 전달할 요청 예

```text
docs/structure-review/README.md부터 읽고, index.md에서 내가 지정한 글의 검토서와 원문 전문을 확인해줘
이번 대상은 [slug 목록]이야
권장 순서를 원문에 대응시켜 구조를 개선하되, 기본 사례의 결과를 바꾸는 조건·기술 사실·버전·출처·코드·가정은 보존해줘
모든 글에 같은 템플릿을 강제하지 말고, 검토서의 독자 확인 질문으로 설명 흐름을 다시 읽어줘
범위 밖 글·메타데이터·자산·사이트 코드는 수정하지 마
실제 실행한 검증, 적용한 변경, 남은 기술 확인 항목을 구분해서 보고해줘
commit과 push는 하지 마
```
