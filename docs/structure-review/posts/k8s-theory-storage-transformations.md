## 원문 근거와 개선점

### L44 키 교체의 전체 과정 전에 저장 바이트 분류로 들어갑니다

> ## 접두사가 변환 방식과 읽을 키를 알려 줍니다

제목은 새 키를 넣어도 기존 값이 남는 이유인데 provider 접두사·중첩 목록·identity 구현을 먼저 배워야 합니다

수정 방향: 옛 값 읽기·새 키 쓰기·기존 값 재기록의 세 상태를 먼저 보여주고 접두사를 그 상태를 구분하는 방법으로 설명합니다

### L277 암호화가 보호하는 대상이 마지막에 정리됩니다

> ## API로 읽을 권한과 저장 암호화의 역할은 다릅니다

Secret을 API로 읽으면 평문 데이터가 반환되는 이유를 끝에서야 설명합니다. 암호화와 RBAC의 범위를 먼저 알면 전체 경로를 정확히 읽을 수 있습니다

수정 방향: 도입에 저장 파일/백업 보호와 인가된 API 읽기의 차이를 짧게 앞당깁니다

## 권장 설명 순서

1. 저장 암호화가 보호하는 위치를 API 권한·직렬화와 구분합니다
2. 옛 키 데이터가 남은 상태에서 새 키를 설정하는 사례로 읽기 후보와 쓰기 대상을 설명합니다
3. 읽기만으로 재기록되지 않으며 stale을 가진 Update가 새 키로 쓰는 과정을 완성합니다
4. 접두사·provider/키 목록·identity를 앞의 읽기/쓰기 선택 근거로 풉니다
5. 여러 API 서버의 키 배포와 백업의 옛 키 필요를 설명합니다
6. KMS 내부 상태·AAD·자동 reload·손상 LIST 조건을 각각 심화하고 오류 경계로 정리합니다

## 연결 문장 예시

아래는 구성 예시이며 실행 결과나 새로운 경험이 아닙니다

새 키를 맨 앞에 두면 다음 쓰기에 사용할 키가 바뀝니다
이미 저장된 값은 그대로이므로 옛 키로 읽을 수 있는 동안 새 키로 다시 기록해야 합니다

## 유지할 내용과 조건

- stale은 복호화 성공 후 재기록 필요 신호이며 GET 자체는 재기록하지 않음
- 키 배포 순서·옛 백업의 키 필요·동시성 검사는 유지
- KMS 캐시와 쓰기 상태, provider별 AAD, reload 성공 조건·gate 차이
