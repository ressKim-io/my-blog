## 독자와 중심 질문

Pod가 노드에 배치된 다음, 런타임은 CNI에 무엇을 주고 어떤 결과를 받아 네트워크 준비를 마칠까요?

선행 개념: Pod sandbox와 network namespace의 뜻은 한 문장으로 소개합니다. CRI는 kubelet과 런타임 사이의 인터페이스라는 수준이면 충분합니다

- L74: CNI는 환경 변수와 JSON으로 실행 파일을 호출합니다

## 원문 근거와 개선점

### L59 호출을 보기 전에 버전 축부터 늘어납니다

> ### 규격 버전과 라이브러리 릴리스는 다릅니다

kubelet에서 런타임으로 넘어가는 도입은 좋습니다. 다만 CNI가 실제로 받는 입력을 아직 보지 않은 상태에서 여러 프로젝트의 버전을 대조하면 각 버전이 무엇을 제한하는지 판단하기 어렵습니다

수정 방향: 환경 변수·JSON 입력과 ADD 결과로 한 번의 호출을 먼저 보여줍니다. 버전 표는 CHECK·STATUS·GC의 지원 조건을 설명하는 절 앞으로 옮깁니다

### L74 한 attachment의 성공과 정리를 중심으로 명령을 묶습니다

> CNI는 환경 변수와 JSON으로 실행 파일을 호출합니다

호출 형식 뒤에 명령 목록·플러그인 체인·IPAM·실패 정리가 이어집니다. 정보는 연결되지만 기본 ADD 한 번과 여러 플러그인의 합성이 빠르게 겹칩니다

수정 방향: 단일 ADD의 입력·주소 준비·결과 반환을 먼저 완결합니다. IPAM 위임은 그 내부 역할로, 체인은 여러 ADD의 합성으로 확장하고 실패 뒤 DEL 정리를 붙입니다. 나머지 관리 명령은 별도 후반 절로 묶습니다

## 권장 설명 순서

1. Pod 배치만으로 통신할 수 없는 이유와 Kubernetes가 요구하는 통신 조건을 짧게 제시합니다
2. kubelet의 CRI 요청을 받은 런타임이 준비된 network namespace를 CNI에 넘기는 책임 경계를 설명합니다
3. 한 attachment의 ADD를 따라 환경 변수·stdin JSON·플러그인의 작업·stdout 결과를 연결합니다
4. 주소를 고르는 IPAM 위임을 설명하고, prevResult로 연결하는 플러그인 체인으로 확장합니다
5. 중간 ADD 실패 뒤 DEL을 통한 정리와 역순 실행을 보여주며 원자적 rollback과 구분합니다
6. 규격·라이브러리·플러그인 버전을 구분한 뒤 CHECK·STATUS·GC와 containerd 설정의 적용 조건을 정리합니다
7. 런타임 준비 상태·Node 상태·Pod 이벤트를 각각 어느 단계의 증거로 읽을지 연결합니다

## 연결 문장 예시

아래는 구성 예시이며 실행 결과나 새로운 경험이 아닙니다

런타임은 준비한 network namespace와 네트워크 설정을 ADD 호출에 넘깁니다
먼저 이 호출 하나가 성공하는 과정을 본 뒤, 여러 플러그인을 연결하거나 중간에 실패했을 때의 처리를 보겠습니다

## 유지할 내용과 조건

- CNI가 NetworkPolicy나 특정 데이터 경로까지 보장하는 계약은 아니라는 범위를 보존합니다
- IPAM 위임과 체인의 다음 플러그인, Kubernetes nodeipam을 구분합니다
- ADD 실패 뒤 DEL은 원자적 rollback이 아니며 명령 지원·자동 호출 여부는 규격과 구현에 따라 다름을 보존합니다
- 실제 실행·지연 측정 결과가 아니라 문서와 소스 분석이라는 한계를 유지합니다
