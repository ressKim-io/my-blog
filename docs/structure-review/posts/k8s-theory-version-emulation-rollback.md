## 독자와 중심 질문

바이너리를 되돌리는 것만으로 저장 데이터와 기능 호환성이 되돌아가지 않는 이유를 이해합니다

선행 개념: 서빙·저장 버전, feature gate

## 원문 근거와 개선점

### L41 세 버전의 효과를 보기 전에 범위 계산이 나옵니다

> ## 하한과 기본값은 함께 계산합니다

binary/emulated/min compat 정의 직후 허용 범위와 플래그 표를 읽지만 이 값을 다르게 두면 어떤 결과가 달라지는지 사례는 분산돼 있습니다

수정 방향: 현재 본문의 같은 바이너리·다른 emulated 사례와 저장 데이터가 남는 사례를 짧게 먼저 보여주고 범위 표로 확장합니다

### L213 도입의 롤백 질문에 대한 핵심 답이 늦습니다

> ## min compat 변경은 저장 데이터에도 영향을 줍니다

gate·서빙·OpenAPI·저장 후보 탐색·CEL을 다 읽어야 설정을 낮춰도 데이터가 역변환되지 않는다는 결론이 나옵니다

수정 방향: 도입 뒤에 이 원리를 먼저 답하고 각 선택 알고리즘이 왜 필요한지 설명하는 근거로 사용합니다. 구체적 롤백 절차를 새로 만들지는 않습니다

## 권장 설명 순서

1. 새 바이너리를 내렸어도 새 데이터가 남는 기존 질문에 먼저 답합니다
2. 세 버전의 역할과 관계를 한 예로 구분합니다
3. emulated가 gate·서빙 API를 고르고 min compat이 저장·검증 호환에 관여함을 비교합니다
4. 허용 범위·기본값·컴포넌트 적용 범위를 설명합니다
5. 저장 후보 두 번 탐색과 CEL의 새/기존 표현식 환경을 각 호환 문제에 연결합니다
6. forward-compatible 설정·OpenAPI·statusz 차이를 보충하고 되돌릴 설정과 이미 남은 데이터를 따로 확인합니다

## 유지할 내용과 조건

- 전체 컴포넌트 버전 자동 조정이 아님
- 저장 버전 선택의 min compat 예외와 현재 구현 범위
- 문서 삭제/KEP 상태와 실제 플래그 구현 구분, 자동 역마이그레이션 비보장
