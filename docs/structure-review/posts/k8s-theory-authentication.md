## 독자와 중심 질문

Pod의 토큰 파일이 어떤 과정을 거쳐 API 요청의 이름·그룹으로 바뀌는지 설명합니다

선행 개념: API 요청의 인증·인가 구분, Pod·ServiceAccount

## 현재 전개

- L24: 토큰 파일과 요청의 신원은 서로 다른 주체가 만든다

- L61: 파일이 갱신되면 요청의 토큰도 바뀔까
- L114: Secret 기반 legacy token은 어디서 갈라지나
- L125: Pod bound token은 서명만 맞으면 유효한가

## 원문 근거와 개선점

### L61 서버의 기본 검증보다 갱신의 세부 조건이 먼저 등장

> ## 파일이 갱신되면 요청의 토큰도 바뀔까

신원 전달 뒤 곧바로 3607초 연장·client-go 캐시·legacy token으로 깊어지고, 토큰에 무엇이 담기며 왜 유효한지는 뒤에서 배웁니다

수정 방향: 발급·제시·claim 검증·user.Info의 기본 흐름을 먼저 연결한 뒤 파일 갱신과 앱 재읽기를 설명합니다

### L209 Pod 사례와 사람 인증의 범위 확장

> ## 사람의 이름과 그룹은 어디서 오나

중심 사례의 마무리 없이 인증 방식 전체로 넓어지면 동일 흐름의 어느 부분이 교체되는지 불분명합니다

수정 방향: 자격증명은 달라도 최종 user.Info가 인가의 입력이라는 공통점을 전환 문장으로 먼저 명시합니다

## 권장 설명 순서

1. 현재 도입과 발급·파일·요청·신원 역할 그림을 유지합니다
2. prod/web 토큰의 주요 claim과 서버 검증을 user.Info 예시에 연결합니다
3. 유효한 토큰도 동작 권한은 별도라는 점으로 요청 한 건을 완성합니다
4. 시간이 지나 파일이 갱신되는 사례에서 앱 재읽기와 캐시·연장 조건을 설명합니다
5. Pod 삭제·재생성과 외부 TokenReview/오프라인 검증의 차이를 다룹니다
6. 사람 인증·legacy·인증기 체인과 익명 분기를 비교 경로로 설명합니다

## 연결 문장 예시

아래는 구성 예시이며 실행 결과나 새로운 경험이 아닙니다

지금까지는 토큰 한 개를 제시했을 때 신원이 만들어지는 과정을 봤습니다
Pod가 오래 실행되면 이 토큰을 교체해야 하므로, 이제 파일 갱신과 요청의 자격증명이 함께 바뀌는지 확인하겠습니다

## 유지할 내용과 조건

- admission의 명세 변경, kubelet의 TokenRequest와 파일 제공, 서버 검증 주체를 보존합니다
- 80%·24시간·jitter, 연장 경로의 전체 조건과 client-go 캐시 조건을 그대로 유지합니다
- 60초를 전역 폐기 완료 보장으로 바꾸지 않고 Pod bound와 Node bound 검증을 구분합니다
