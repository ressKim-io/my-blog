## 독자와 중심 질문

같은 logs 요청에서 사용자와 API 서버 클라이언트의 권한 검사가 어떻게 나뉘는지 이해합니다

선행 개념: API 인증·인가, Pod가 실행되는 Node

## 원문 근거와 개선점

### L65 접속 주소의 예외가 두 번째 인가의 세부보다 먼저 나옵니다

> ### 주소를 보고한 노드와 주소의 소유자는 같다고 보장되지 않습니다

첫 그림에서 경로를 잡은 뒤 주소 선택·주소 검증·인증서 조건이 길어져 제목의 주체 변화와 권한 매핑 설명으로 돌아오기까지 거리가 깁니다

수정 방향: 기본 주소 선택·TLS 양쪽 신원까지만 먼저 묶고 nodes/proxy 매핑과 두 번째 판단을 완성합니다. 주소 소유 검증과 transport 예외는 후반 보충으로 둡니다

### L150 판정 방식과 권한 매핑 사이에 설정 이력이 끼어듭니다

> ## 설정 파일과 기존 명령행의 기본값이 다릅니다

TokenReview·SAR 위임을 배운 다음 무엇을 물을지 보기 전에 네 기본값·우선순위를 읽습니다

수정 방향: HTTP 경로→권한 속성을 위임 설명과 붙이고, 설정 파일/플래그·읽기 전용 포트는 실제 적용 설정을 확인하는 한 단위로 묶습니다

## 권장 설명 순서

1. 기존 kubectl logs 그림으로 사용자 pods/log와 API 서버 클라이언트 nodes/proxy를 먼저 구분합니다
2. Node 접속 정보와 TLS의 클라이언트/서버 인증서를 최소 조건으로 연결합니다
3. kubelet 인증·SAR 위임·경로의 권한 매핑을 연속해서 설명합니다
4. 세분화 권한의 proxy 폴백과 metrics-server 직접 접속을 비교합니다
5. 실제 설정 우선순위·캐시·readOnlyPort로 권한 변경과 노출 범위를 보충합니다
6. Konnectivity·다른 포트 transport·주소 검증 조건을 설명하고 실패 단계별 진단으로 마칩니다

## 연결 문장 예시

아래는 구성 예시이며 실행 결과나 새로운 경험이 아닙니다

사용자의 pods/log 검사가 끝난 뒤에는 API 서버가 새 클라이언트가 됩니다
따라서 kubelet이 거절한 권한은 원래 사용자가 아니라 이 두 번째 요청자의 권한일 수 있습니다

## 유지할 내용과 조건

- 첫 logs 경로와 두 주체를 나눈 그림은 유지
- HTTPS와 서버 신원 검증의 차이, kubeadm Binding과 기본 역할 정의의 차이
- 세분화 권한 폴백 범위, 설정 기본값·인가 cache·transport 조건
