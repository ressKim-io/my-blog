## 독자와 중심 질문

Pod X에서 Pod Y로 새 연결을 만들 때, 어떤 정책이 어느 방향을 제한하고 여러 정책의 허용은 어떻게 합쳐질까요?

선행 개념: namespace·Pod 라벨·새 연결과 응답 트래픽의 구분을 전제합니다. 격리는 해당 방향이 허용 규칙의 제한을 받는 상태로 설명합니다

## 원문 근거와 개선점

### L72 방향 모델은 좋지만 정상 규칙 예시보다 생략 규칙이 먼저 나옵니다

> ## policyTypes를 생략하면 ingress가 기본으로 들어갑니다

Pod별·방향별 격리와 허용 합집합은 중심 질문에 잘 맞습니다. 이어 policyTypes 기본값과 빈 목록의 여러 형태를 먼저 읽으면 아직 정상 규칙을 해석하지 못한 독자에게 문법 예외가 기준이 됩니다

수정 방향: 방향을 명시한 정상 ingress 또는 egress 규칙 하나를 적용 대상·허용 상대·포트 순으로 먼저 해석합니다. 그 뒤 필드를 생략하거나 빈 목록으로 바꾸면 무엇이 달라지는지 비교합니다

### L118 같은 selector 이름의 역할을 더 일찍 연결합니다

> ## selector는 적용 대상과 허용 상대를 구분해서 읽습니다

최상위 selector와 peer selector를 나누는 설명은 유용합니다. 다만 빈 peer의 검증 오류가 먼저 등장해 어떤 대상을 고르는 필드인지 이해하기 전에 허용·거절을 외우게 될 수 있습니다

수정 방향: 정상 규칙 예시 안에서 적용 Pod와 통신 상대를 먼저 표시합니다. 같은 peer의 AND와 여러 peer의 OR를 설명한 다음 빈 selector·빈 peer·빈 규칙 목록을 비교표로 모읍니다

## 권장 설명 순서

1. 정책 저장과 실제 집행의 차이를 짧게 밝히고 X에서 Y로 가는 새 연결을 중심 사례로 둡니다
2. X의 egress와 Y의 ingress를 각각 판단하며 격리 여부·허용 합집합·응답 트래픽을 설명합니다
3. 방향을 명시한 정상 규칙에서 적용 Pod·허용 상대·포트를 순서대로 해석합니다
4. namespaceSelector와 podSelector의 같은 peer AND·별도 peer OR를 비교합니다
5. policyTypes 생략과 빈 규칙·빈 조건·빈 selector의 차이를 앞 예시의 변화로 설명합니다
6. ipBlock·포트 지원·로컬 노드 예외·NAT·기존 연결·hostNetwork를 기본 모델의 적용 조건으로 묶습니다
7. 구현의 집행 위치와 확장 정책을 구분한 뒤 지원·대상·방향·합집합·데이터 경로 순으로 확인합니다

## 연결 문장 예시

아래는 구성 예시이며 실행 결과나 새로운 경험이 아닙니다

먼저 방향과 상대를 모두 적은 규칙 하나를 읽어보면 각 필드의 역할을 구분할 수 있습니다
그다음 값을 생략하거나 빈 목록으로 바꿀 때 격리 여부와 허용 범위 중 무엇이 달라지는지 비교하겠습니다

## 유지할 내용과 조건

- 같은 방향의 허용은 합집합이며 새 연결의 양쪽 끝이 모두 허용돼야 한다는 현재 설명을 유지합니다
- default-deny가 다른 정책의 허용까지 취소하지 않는다는 구분을 보존합니다
- 로컬 노드·자기 자신·hostNetwork·ICMP·NAT·기존 연결의 범위를 단순한 전면 차단으로 축약하지 않습니다
- 정책 API 저장 성공과 집행 구현의 지원·반영은 별개라는 구분을 유지합니다
