## 독자와 중심 질문

이미 만든 볼륨을 변경하거나 복제하고 Pod 수명에 맞춰 정리할 때, API 요청 이후 어떤 주체의 작업이 남을까요?

선행 개념: PVC·PV·StorageClass와 CSI의 Controller·Node 호출 책임을 전제합니다. 각 기능은 기본 볼륨 사용 경로를 변형하는 별도 요구로 안내합니다

## 원문 근거와 개선점

### L234 볼륨 변경 질문이 임시 볼륨 뒤에서 다시 등장합니다

> ## VolumeAttributesClass는 크기와 다른 속성을 바꿉니다

앞에서 용량 확장과 resizer를 설명한 뒤 스냅샷·임시 볼륨을 지나 다시 기존 PVC의 속성 변경으로 돌아옵니다. 같은 변경 주체와 상태를 멀리 떨어져 비교해야 합니다

수정 방향: VolumeAttributesClass를 용량 확장·복구 뒤에 배치해 크기 변경과 성능 속성 변경을 한 단위에서 비교합니다. 이어 복제·복원, Pod 수명에 따른 정리라는 다음 질문으로 넘어갑니다

### L151 스냅샷의 생성과 복원 사이에 설치 세부가 끼어 있습니다

> ### CRD와 controller 설치는 드라이버의 RPC 지원과 별개입니다

요청·Content·드라이버의 역할을 설명한 다음 CRD 배포와 승인 어노테이션을 읽어야 복원 방식이 나옵니다. 스냅샷을 무엇에 쓰는지 확인하기 전에 설치 메타데이터로 시선이 이동합니다

수정 방향: 스냅샷 요청·생성·준비 상태·새 PVC 복원을 먼저 연결합니다. CRD 설치·capability·승인 어노테이션은 이 흐름을 사용할 전제로 뒤에 붙입니다

## 권장 설명 순서

1. 기존 볼륨 변경, 스냅샷에서 새 볼륨 생성, Pod 수명에 따른 정리라는 세 요구를 짧게 안내합니다
2. 10Gi에서 20Gi로 확장하는 가정 예시에서 요청 검증·resizer·필요한 Node 작업·상태 반영을 따라갑니다
3. capability·온라인/오프라인·Block·실패 요청 감소 조건을 붙이고 VolumeAttributesClass의 별도 속성 변경과 비교합니다
4. VolumeSnapshot·Content·Class와 controller·sidecar의 역할을 설명하고 준비된 스냅샷에서 새 PVC를 만드는 복원까지 연결합니다
5. 설치·지원·일관성 조건을 정리한 뒤 generic ephemeral과 CSI inline의 생성·사용·정리를 같은 기준으로 비교합니다
6. 임시 볼륨의 소유 참조·이름 충돌·권한·쿼터 차이를 붙이고 관측 상태를 호출 주체와 연결합니다

## 연결 문장 예시

아래는 구성 예시이며 실행 결과나 새로운 경험이 아닙니다

용량과 드라이버 속성은 기존 볼륨을 바꾸는 요청이지만, 스냅샷 복원은 새 PVC에 데이터를 준비하는 요청입니다
같은 저장소 작업이라도 변경 대상과 완료 상태가 달라지므로 각 흐름을 따로 따라가겠습니다

## 유지할 내용과 조건

- ControllerExpand·NodeExpand의 호출 조건과 모든 노드 작업의 완료를 PVC 숫자 하나로 확정하지 않는 설명을 유지합니다
- 실패한 요청량을 낮추는 것과 실제 볼륨 축소를 구분합니다
- 스냅샷이 앱 일관성을 자동 보장하지 않으며 복원이 제자리 되감기가 아님을 보존합니다
- generic ephemeral·CSI inline의 PVC·쿼터·권한·정리 주체와 Retain 예외를 구분합니다
