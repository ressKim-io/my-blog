## 독자와 중심 질문

여러 API 서버가 같은 Service 주소를 고르더라도 중복 확보를 어떻게 막고, 주소 확보와 Service 저장 사이에 실패하면 누가 기록을 맞출까요?

선행 개념: Service ClusterIP의 용도, API Create의 이름 유일성, informer 캐시와 실제 쓰기의 차이를 전제합니다

## 현재 전개

- L22: 주소 확보와 Service 저장은 별도의 쓰기입니다
- L40: 정규형 주소 이름에 대한 Create가 중복을 판정합니다
- L90: 동적 할당은 캐시로 후보를 고르고 쓰기로 확정합니다
- L117: ServiceCIDR는 주소를 공급하는 범위와 수명을 드러냅니다
- L165: 삭제는 고아 주소 검사와 전파 유예를 거칩니다
- L191: bitmap 이중 쓰기는 현재 실행 경로와 구분합니다
- L221: repair는 주소 기록을 고치며 Service의 주소를 바꾸지 않습니다
- L255: 생성 충돌과 저장 뒤의 불일치는 다른 문제입니다
- L272: 참고 자료

## 원문 근거와 개선점

### L221 도입에서 연 두 쓰기의 실패 질문이 너무 뒤에서 닫힙니다

> ## repair는 주소 기록을 고치며 Service의 주소를 바꾸지 않습니다

주소 확보와 Service 저장이 원자적이지 않다는 도입은 좋은 학습 출발점입니다. 그런데 불일치 복구를 보기 전에 동적 구간·ServiceCIDR 변경·삭제·bitmap 이행까지 지나야 합니다

수정 방향: IPAddress Create로 중복을 막는 기본 경로 다음에 Service 저장 실패와 해제·repair를 배치합니다. 성공·실패의 한 주기를 마친 뒤 대역 관리와 과거 이행으로 확장합니다

### L117 대역 역할은 앞에서 짧게 정의하고 상세 관리는 뒤로 모읍니다

> ## ServiceCIDR는 주소를 공급하는 범위와 수명을 드러냅니다

도입에는 ServiceCIDR가 있지만 후보를 고르는 절을 지나서야 Ready·삭제 상태·계열별 할당기의 관계가 나옵니다. 주소 후보가 어느 공급 범위에서 왔는지와 그 범위의 전체 생명주기를 한꺼번에 알아야 하는 부담이 있습니다

수정 방향: 정상 할당 시작점에 ServiceCIDR가 준비된 후보 범위를 제공한다는 정의만 둡니다. CIDR 추가·주소군 변경·Ready 버전 조건·삭제 보호는 뒤의 대역 관리 단위에서 연결합니다

## 권장 설명 순서

1. ClusterIP를 쓰기 전에 주소를 확보해야 한다는 질문과 ServiceCIDR·IPAddress의 최소 역할을 제시합니다
2. 준비된 대역에서 후보를 고르고 정규형 주소 이름으로 IPAddress를 Create한 뒤 Service를 저장하는 흐름을 설명합니다
3. 동시 Create 충돌과 낡은 캐시를 연결해 최종 배타성 판단이 어디에서 일어나는지 보여줍니다
4. Service 저장 실패 시 해제 시도와 repair의 양방향 대조·유예·보정 한계를 설명합니다
5. 동적 할당 구간과 수동 지정의 관계를 확장하고 ServiceCIDR 추가·주소군·Ready·삭제 보호를 묶습니다
6. bitmap과의 과거 이중 쓰기를 현재 경로와 구분한 뒤 생성 충돌·대역 부족·기록 불일치의 진단으로 마칩니다

## 연결 문장 예시

아래는 구성 예시이며 실행 결과나 새로운 경험이 아닙니다

IPAddress 생성에 성공해도 Service 저장은 별도의 쓰기입니다
두 번째 쓰기가 실패하면 확보한 주소 기록이 남을 수 있으므로, 중복 방지와 별개로 해제와 정합성 복구가 필요합니다

## 유지할 내용과 조건

- parentRef가 ownerReferences가 아니며 자동 GC와 같은 의미가 아니라는 구분을 보존합니다
- 캐시는 후보 선택을 돕고 API Create가 확보를 확정한다는 설명을 유지합니다
- 해제 호출 종료만으로 삭제 성공을 증명할 수 없는 원문 구현 조건을 보존합니다
- repair는 Service 주소를 임의로 교체하지 않으며 유예 시간은 전체 복구 시간 보장이 아님을 유지합니다

## 편집 후 독자 확인

- 대역 삭제 보호를 ownerReferences 기반 GC로 오해하지 않나요?
