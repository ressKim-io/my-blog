## 독자와 중심 질문

since와 previous 옵션을 써도 기대한 과거 로그가 나오지 않는 이유를 파일·인스턴스 수명으로 이해합니다

선행 개념: 컨테이너 stdout/stderr, kubelet과 런타임, 재시작

## 현재 전개

- L25: 경로는 CRI의 두 필드로 전달합니다
- L71: 경로 계약과 읽을 수 있는 형식은 구분해야 합니다
- L122: 회전은 현재 파일을 바꾸고 런타임에 다시 열도록 요청합니다
- L169: kubectl logs는 선택한 인스턴스의 현재 파일을 읽습니다
- L212: API 서버는 파일을 저장하지 않고 해당 노드에 중계합니다
- L243: 로그가 없거나 짧을 때 구분할 위치
- L261: 확인한 근거

## 원문 근거와 개선점

### L46 과거 로그 조회의 답 전에 시작 번호 복구로 샙니다

> ### 파일 이름은 restart count를 복구할 때도 사용합니다

경로 소개 직후 재부팅 시 restart count 복구와 호환 symlink를 읽고 형식·회전으로 넘어갑니다. 도입의 한 시간 로그 질문은 오래 뒤에 답합니다

수정 방향: 선택한 인스턴스의 현재 파일만 읽는다는 기본 경로를 먼저 끝내고 이름 복구는 파일 관리 보충으로 옮깁니다

### L212 조회 대상의 위치를 후반에 설명합니다

> ## API 서버는 파일을 저장하지 않고 해당 노드에 중계합니다

kubectl logs의 한계를 이해하려면 API 서버가 이력을 보관하는 곳이 아니라 노드로 중계한다는 관계가 먼저 필요합니다

수정 방향: 도입 그림과 함께 사용자 요청→API 서버→kubelet→현재 파일의 읽기 경로를 앞쪽에 둡니다

## 권장 설명 순서

1. since 1h가 보존 기간을 보장하지 않는다는 기존 질문에 현재 파일 범위로 답합니다
2. kubectl→API 서버 중계→노드 kubelet→선택 인스턴스 파일의 경로를 설명합니다
3. kubelet이 CRI 경로를 정하고 runtime이 기록하는 역할을 연결합니다
4. CRI 로그 형식의 바깥 timestamp와 partial/full 레코드를 풉니다
5. rename→ReopenContainerLog 회전과 follow·previous·컨테이너 GC를 비교합니다
6. restart count 복구·symlink·종료 메시지 발췌를 보충하고 외부 보관과 구분합니다

## 연결 문장 예시

아래는 구성 예시이며 실행 결과나 새로운 경험이 아닙니다

since는 남아 있는 파일 안에서 읽을 시간을 고르는 조건입니다
파일 회전으로 그 구간이 현재 파일에서 빠졌다면 조회 옵션만으로 과거 내용을 다시 만들 수 없습니다

## 유지할 내용과 조건

- 현재 파일·회전본·이전 컨테이너 인스턴스의 구분
- 회전 rename과 열린 fd·Reopen 관계, 실패 복구의 비원자성
- 최신 파일 제한의 설계 이유는 확인 못함, 종료 메시지는 제한된 발췌
