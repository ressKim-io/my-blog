## 원문 근거와 개선점

### L61 요청 처리 도중 과부하 제어의 내부 구현으로 전환

> APF(API Priority and Fairness)는 요청을 분류해 우선순위별로 동시에 처리할 수 있는 양을 관리합니다

기본 경로를 따라가던 독자가 FlowSchema·외부 인가 비용·429·필터 조립 순서까지 읽어야 디코딩으로 진행할 수 있습니다

수정 방향: 그 위치에는 신원을 바탕으로 처리량을 제어한다는 역할만 남기고 상세 APF 설명은 정상 저장 경로 뒤의 심화로 이동합니다

### L212 요청 경로를 읽는 배경이 후반에 등장

> GVK(Group-Version-Kind)는 오브젝트의 타입을 식별합니다

앞에서는 group·resource로 인가를 읽고, 후반에서 URL과 타입의 대응을 다시 배웁니다

수정 방향: 도입 예제에 종류·URL 대상·본문의 구분을 짧게 보강합니다. GVK/GVR 전체 분류와 discovery 캐시 조건은 뒤에 유지합니다

## 권장 설명 순서

1. dev가 prod의 Deployment web을 생성하는 가정과 요청의 대상·본문을 소개합니다
2. 인증·처리량 제어·인가·디코딩·변경·검증·저장을 한 요청으로 끝까지 따라갑니다
3. 변경 뒤 검증하는 이유를 같은 replicas·사이드카 사례로 설명합니다
4. 저장 성공 뒤 ReplicaSet·Pod 생성이 별도 요청이라는 경계를 연결합니다
5. 단계별 오류와 audit로 확인할 수 있는 범위를 앞의 경로에 대응시킵니다
6. APF 내부, 다른 요청 종류, discovery와 dry-run 조건을 심화로 묶습니다

## 유지할 내용과 조건

- 내장 resource의 일반 CREATE라는 범위와 APF의 실제 위치를 보존합니다
- 기본값·mutating·타입 검증·validating의 순서와 실패 조건을 보존합니다
- 상태코드만으로 원인을 확정하지 않으며 dry-run은 후속 성공을 예약하지 않는다는 조건을 유지합니다
