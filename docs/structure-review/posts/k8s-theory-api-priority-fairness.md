## 독자와 중심 질문

서로 비용이 다른 API 요청을 APF가 분류하고 제한하며 대기시키는 과정을 이해합니다

선행 개념: API 요청·인증 신원, GET/LIST/watch의 차이

## 원문 근거와 개선점

### L169 상한 계산이 상한의 기반보다 먼저 나옵니다

> `NominalCL`은 그 수준의 기본 동시성 몫이며 뒤에서 계산합니다

LIST의 수준별 상한 수식에서 아직 설명하지 않은 NominalCL과 handSize가 필요합니다. 뒤의 전체 몫 계산과 큐 선택까지 갔다가 다시 읽어야 합니다

수정 방향: 서버 전체 자리 → 우선순위 수준의 몫 → 큐/흐름을 먼저 설명하고, 요청별 폭 추정 및 수준별 상한 수식을 그다음에 배치합니다

### L102 큐를 나누는 목적보다 해시 구현이 먼저 나옵니다

> 서버는 FlowSchema 이름과 구분자 사이에 0 바이트 구분자를 넣어 SHA-256으로 해시하고, 앞 8바이트를 큐 후보 선택에 사용합니다

flow를 처음 정의한 자리에서 byte 구성까지 소개하지만 왜 큐 후보를 고르는지는 뒤에 있습니다

수정 방향: ByUser로 흐름을 나누는 효과까지만 먼저 설명합니다. 해시와 확률 계산은 shuffle sharding의 목적과 사례 뒤에 둡니다

## 권장 설명 순서

1. 작은 GET과 큰 LIST를 비교해 요청 한 건과 처리 자리의 차이를 제시합니다
2. 요청 하나가 FlowSchema → priority level → 실행/대기/거절로 가는 경로를 먼저 끝냅니다
3. 서버 전체 한도·수준별 기본 몫·차용을 설명합니다
4. 흐름 분리와 후보 큐 선택을 그림으로 설명하고 handSize의 역할을 정합니다
5. LIST·쓰기 후속 비용·watch 초기화의 폭과 시간 추정을 계산 예로 풉니다
6. 버전별 추정기·상한·예외와 기본 구성 자동 갱신을 보충합니다
7. 429의 분류 헤더·reason·자리 사용량을 앞의 단계와 대응합니다

## 연결 문장 예시

아래는 구성 예시이며 실행 결과나 새로운 경험이 아닙니다

우선순위 수준의 몫을 정했더라도 요청마다 같은 자리를 쓰지는 않습니다
이제 큰 LIST와 변경 이벤트를 만드는 쓰기가 그 몫을 얼마나 차지한다고 추정하는지 살펴보겠습니다

## 유지할 내용과 조건

- 자리와 CPU/메모리 실측은 다름
- 추정 경로와 실제 저장 경로 차이, 현재 크기 기반 gate와 과거 객체 수 설명 구분
- watch 전체 수명 미점유, 후속 시간은 응답 sleep이 아님, shuffle sharding 격리 비보장
