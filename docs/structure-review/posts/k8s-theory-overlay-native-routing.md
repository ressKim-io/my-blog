## 독자와 중심 질문

노드 간 Pod 패킷을 전달하는 방식과 Pod 주소를 공급하는 방식은 어떻게 다르고, 각각 어디에서 실패할까요?

선행 개념: Pod마다 주소가 있고 CNI가 네트워크 attachment를 준비한다는 점, 라우팅의 다음 홉이라는 뜻을 전제합니다

## 원문 근거와 개선점

### L93 전달 방식의 비용을 확인하기 전에 주소 공급으로 전환합니다

> ## nodeipam은 노드별 주소 범위를 기록합니다

Overlay와 native routing의 대비는 명확합니다. 다만 비교표에서 제시한 MTU 비용을 풀기 전에 nodeipam·CIDR 플래그·ENI를 거쳐 뒤에서 캡슐화 문제로 돌아옵니다

수정 방향: Overlay·native routing 비교 뒤에 MTU 계산과 큰 패킷 실패를 붙여 전달 방식 질문을 완결합니다. 이후 주소는 어디서 오는지라는 새 질문으로 IPAM 단위를 시작합니다

### L117 주소 공급의 일반 관계보다 한 구현의 설정이 먼저 나옵니다

> ## 범위가 기록돼도 플러그인이 반드시 쓰지는 않습니다

nodeipam의 마스크·플래그 제약을 먼저 읽은 뒤에야 모든 플러그인이 Node CIDR을 쓰지는 않는다는 관계가 나옵니다. 독자가 앞의 설정을 필수 구성으로 받아들일 수 있습니다

수정 방향: IPAM 절의 첫머리에 Node CIDR·Cilium 주소 풀·AWS ENI의 공급자 비교를 둡니다. 그중 Node CIDR을 사용하는 한 경로로 nodeipam과 kubelet 전달을 설명하고 플래그 제약을 바로 아래에 둡니다

## 권장 설명 순서

1. 다른 노드의 Pod까지 가야 한다는 상황과 전달 방식·주소 공급이라는 두 질문을 제시합니다
2. 같은 Pod 패킷을 Overlay로 보낼 때 바깥 노드 주소가 붙고 목적지에서 벗겨지는 과정을 보여줍니다
3. 같은 패킷을 native routing으로 보낼 때 필요한 노드·underlay 경로를 대비하고 선택 조건을 정리합니다
4. 캡슐화의 MTU 비용, 주소군별 계산 예, interface MTU와 route MTU, 큰 패킷 실패를 이어 설명합니다
5. Pod 주소의 공급자로 질문을 전환해 IPAM 모드 표를 먼저 보여주고 nodeipam·플러그인 소비 경로를 풉니다
6. VPC ENI 주소 공급의 서브넷·인터페이스 한도를 설명하고 전달 실패와 주소 부족을 나눈 진단표로 마칩니다

## 연결 문장 예시

아래는 구성 예시이며 실행 결과나 새로운 경험이 아닙니다

여기까지는 이미 주소를 가진 Pod의 패킷이 다른 노드로 가는 경로를 봤습니다
이제 그 Pod 주소를 누가 공급하는지 살펴보면, 주소가 부족한 문제와 전달 경로가 끊긴 문제를 구분할 수 있습니다

## 유지할 내용과 조건

- VPC 주소 공급을 Overlay·native routing과 동급의 세 번째 전달 방식으로 분류하지 않습니다
- 두 축을 구분하더라도 모든 IPAM·전달 방식 조합이 가능한 것은 아니라는 지원 조건을 보존합니다
- MTU 수치는 주소군·헤더 조건이 붙은 계산 예이며 실측 성능 비교가 아니라는 설명을 유지합니다
- Node CIDR을 기록하는 작업이 개별 Pod IP 할당이나 데이터 경로 설치와 같지 않음을 보존합니다
