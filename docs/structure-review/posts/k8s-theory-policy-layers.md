## 독자와 중심 질문

요청을 거절할지, 들어온 값을 바꿀지, 저장된 자원을 나중에 고칠지에 따라 정책의 실행 위치·실패 영향·소유권은 어떻게 달라질까요?

선행 개념: admission 순서, SSA의 필드 소유권, controller의 별도 API 쓰기를 전제합니다. 도구별 기능은 이 세 실행 시점에 대응시킵니다

## 원문 근거와 개선점

### L52 실행 시점 비교를 끝내기 전에 버전·설정 표가 커집니다

> ### 현재 API와 기본값을 구분합니다

동기 admission과 저장 후 controller를 나눈 도입은 좋습니다. 그러나 세 방식의 실제 결과를 보기 전에 API 버전·failurePolicy·reinvocation 필수값과 CEL 입력 범위를 읽게 됩니다

수정 방향: 거절·요청 중 변경·저장 후 변경의 결과를 각각 짧게 보여주고 관련 도구를 대응시킵니다. 버전·기본값은 각 방식의 실패 처리나 재실행을 설명할 위치에 붙입니다

### L155 정책 제거 예외가 검증과 변경의 대비를 끊습니다

> ## 정책을 지우는 요청도 적용 범위를 확인해야 합니다

규칙 위반·오류·기록 위치를 읽은 뒤 자기 정책 Kind의 제외 범위로 이동하고, 그 후 admission 변경과 field manager를 설명합니다. 중심 비교의 세 축을 다 보기 전에 복구 예외가 삽입됩니다

수정 방향: 검증 정책, 변경 정책, 배경 검사·변경을 각각 완결하고 GitOps 영향까지 연결합니다. 자기 정책 삭제와 순환 의존은 마지막 운영·복구 단위에 모읍니다

## 권장 설명 순서

1. 거절·요청 중 변경·저장 후 별도 쓰기를 실행 시점과 저장 결과로 비교하고 PSA·VAP·MAP·webhook·정책 엔진의 위치를 표시합니다
2. 검증 흐름에서 매칭·CEL 입력·규칙 위반·평가/설정 오류와 Deny·Warn·Audit의 차이를 설명합니다
3. 변경 흐름에서 MAP·webhook의 패치, field manager와 기존 소유권, 재호출·멱등성을 연결합니다
4. 저장 후 검사 보고와 실제 수정·생성을 구분하고 Gatekeeper audit·mutate existing·generate를 대응시킵니다
5. GitOps에서 필드 값·소유권·오브젝트 존재 여부가 각각 경쟁하는 조건과 diff 설정의 범위를 설명합니다
6. 정책 자체 삭제의 제외 범위·추가 구성요소·복구 경계를 정리하고 요구별 선택 기준으로 마칩니다

## 연결 문장 예시

아래는 구성 예시이며 실행 결과나 새로운 경험이 아닙니다

요청 중에 붙인 필드와 저장 뒤 별도 controller가 바꾼 필드는 쓰기 경로가 다릅니다
따라서 GitOps의 차이를 볼 때도 값만 비교하지 말고 어느 시점의 누가 보낸 쓰기인지 확인해야 합니다

## 유지할 내용과 조건

- Warn 전용 바인딩에서도 파라미터 설정 오류로 직접 거절될 수 있는 원문 조건을 보존합니다
- admission이 만든 새 독립 필드와 기존 소유 필드의 변경을 모두 무소유로 일반화하지 않습니다
- audit의 위반 보고와 실제 수정, generate의 오브젝트 수명 관리가 다른 동작임을 유지합니다
- 도구 버전·지원·캐시 지연·실제 설치 설정과 문서 간 불일치의 확인 필요를 보존합니다

## 편집 후 독자 확인

- 설정 기본값을 외우기 전에 세 실행 시점의 저장 결과와 실패 영향을 비교할 수 있나요?
