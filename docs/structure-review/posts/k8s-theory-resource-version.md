## 독자와 중심 질문

오래된 조회 결과로 다른 작성자의 변경을 덮지 않으려면 resourceVersion을 어떻게 사용해야 하는지 이해합니다

선행 개념: 객체 조회와 Update, API 서버와 저장소의 구분

## 원문 근거와 개선점

### L69 쓰기 충돌 설명 중 읽기 커서로 이동합니다

> ## 객체의 번호와 LIST의 번호는 다릅니다

두 작성자 사례 뒤 etcd 번호를 설명한 다음 LIST로 옮겼다가 다시 Update 생략·CAS로 돌아옵니다. 도입의 충돌 해결이 아직 끝나지 않은 상태에서 번호의 다른 용도가 끼어듭니다

수정 방향: Update 조건·생략 위험·CAS를 먼저 묶고, 객체와 LIST 번호는 watch로 이어지는 두 번째 단위로 이동합니다

### L196 동시성 설명에서 TTL 관리 세부로 넓어집니다

> ## etcd lease와 Kubernetes Lease는 다릅니다

Lease 객체의 경쟁 갱신은 주제와 연결되지만 Event TTL·lease 재사용 카운트는 그 이해에 필요하지 않습니다. 마지막 watch 연결까지 다시 멀어집니다

수정 방향: Lease의 충돌 예만 짧게 남기고 TTL·재사용은 Event 또는 저장소 심화 읽기로 분리합니다. 정보를 삭제하기보다 옮길 위치를 명시합니다

## 권장 설명 순서

1. A·B가 같은 버전을 읽은 기존 사례와 올바른 재조회·재계산을 유지합니다
2. 번호 생략이 안전한 충돌 해결이 아님을 Deployment/CR 비교로 설명합니다
3. API 검사 뒤에도 경쟁이 남는 이유로 etcd CAS와 서버 재시도를 소개합니다
4. 번호가 연속하지 않는 이유를 etcd revision으로 보충하고 API가 보장하는 비교 범위를 구분합니다
5. 객체 번호와 LIST snapshot 번호를 비교하며 읽기·watch 커서로 용도를 확장합니다
6. 409·422와 이력 만료 410을 분리해 정리하고 watch 글로 연결합니다

## 유지할 내용과 조건

- 최신 번호만 덧붙이면 다른 변경을 덮을 수 있다는 경고
- v1.35 이후 같은 group·resource의 순서 비교 조건과 이전 opaque 설명의 구분
