## 독자와 중심 질문

반복 장애 횟수와 kubectl에서 보이는 Event 개수·count가 왜 일치하지 않는지 이해합니다

선행 개념: controller의 관측과 Event 객체, 로컬 메모리와 서버 저장

## 현재 전개

- L25: Eventf가 호출돼도 바로 서버에 쓰지는 않는다
- L40: 같은 관측으로 묶는 키부터 다르다
- L61: core 기록기는 집계, 카운트, 필터 순으로 처리한다
- L127: events 기록기는 셋째 관측부터 증가분을 메모리에 둔다
- L167: 큐 입구의 대기와 처리기 채널의 드롭은 다른 문제다
- L197: kubectl describe의 숫자는 두 기준 중 하나다
- L235: 전송을 기다리는 제한과 서버에서 거절하는 제한도 있다
- L253: Event의 수명은 관측 시각이 아니라 저장 쓰기와 연결된다
- L284: Event가 없다는 사실만으로 사건의 부재를 판단하지 않는다

## 원문 근거와 개선점

### L40 관찰 예보다 긴 키 목록이 먼저 나옵니다

> ## 같은 관측으로 묶는 키부터 다르다

도입의 같은 실패 반복이라는 현상은 좋지만 곧 다수 필드 조합을 읽습니다. message가 달라지는 관측 하나를 보면 두 기록기의 구분을 더 쉽게 이해할 수 있습니다

수정 방향: 같은 실패 반복/설명 숫자만 변경이라는 가정 예를 먼저 두고, 각 기록기가 같은 건으로 보는 기준을 키 표로 확인합니다

### L167 입구에서 잃는 관측을 집계 설명 뒤에 만납니다

> ## 큐 입구의 대기와 처리기 채널의 드롭은 다른 문제다

core 집계와 events series를 이미 따라간 뒤 앞단 큐로 돌아갑니다. 어디까지 도착한 관측을 셌는지 다시 생각해야 합니다

수정 방향: 입구·처리기 채널은 기본 경로에서 먼저 소개하되 숫자/정책 비교는 뒤에 둡니다. 이후 집계·전송·저장·표시 순서를 유지합니다

## 권장 설명 순서

1. 반복 관측 수, 서버 Event 객체 수, 화면 count는 다른 값임을 가정 사례로 보여줍니다
2. Eventf → 로컬 전달 → 묶기 → 전송 → 저장 → kubectl 표시의 전체 경로를 제시합니다
3. 입구/처리기에서 전달되지 않을 수 있는 조건을 설명합니다
4. core의 집계·카운트·필터와 events의 시리즈 갱신을 각각 같은 관측 예로 끝까지 비교합니다
5. 클라이언트 rate limit·서버 admission·실제 저장과 TTL을 잇습니다
6. 조회 API와 기록기 구현을 구분하고 describe 숫자·누락 원인을 정리합니다

아래는 구성 예시이며 실행 결과나 새로운 경험이 아닙니다

같은 Event 객체가 남아 있어도 그 안의 count가 모든 관측을 즉시 반영하는 것은 아닙니다
이제 관측이 서버에 도착하기 전에 어디서 묶이거나 멈추는지 따라가겠습니다

## 유지할 내용과 조건

- core 집계·카운트·spam filter 순서와 서로 다른 키
- events 셋째 이후 메모리 누적 및 프로세스 종료 손실
- 조회 그룹과 기록기 차이, TTL은 실제 저장 쓰기와 연결, 주기는 지연 상한 아님
