## 독자와 중심 질문

PVC 요청은 어떻게 하나의 PV와 연결되며, 여러 요청이 같은 PV를 고를 수 있는 상황에서 claimRef를 먼저 쓰는 이유는 무엇일까요?

선행 개념: Pod가 PVC 이름으로 저장소를 요청한다는 점을 전제합니다. PVC·PV·StorageClass·provisioner의 역할을 도입에서 짧게 구분합니다

## 원문 근거와 개선점

### L28 첫 바인딩을 보기 전에 기본값·호환 분기가 앞섭니다

> ## 클래스 미지정과 빈 문자열은 다른 요청입니다

도입은 요청과 연결을 구분하지만 첫 본문이 nil·빈 문자열·기본 클래스 소급 지정·옛 어노테이션으로 시작합니다. 아직 정상 연결을 모르는 독자에게 클래스 선택의 예외가 먼저 쌓입니다

수정 방향: 클래스를 명시한 일반 PVC와 준비된 PV의 연결을 먼저 설명합니다. 클래스 생략·빈 문자열·소급 지정은 기본 요청의 변형으로 뒤에 모읍니다

### L106 제목의 핵심 질문까지 가는 조건 목록을 줄입니다

> ## 바인딩은 PV 쪽 참조를 먼저 기록합니다

claimRef 선기록의 이유는 글의 중심인데, 일반 매칭 조건 뒤에도 속성 클래스·용량 status 예외·PV 지목 분기를 지나야 합니다

수정 방향: 대표 매칭 조건만 설명하고 곧바로 claimRef·PV 상태·PVC 참조·PVC 상태의 별도 쓰기를 보여줍니다. UID·경쟁·부분 실패 재처리까지 완결한 뒤 특수 매칭과 spec 변경 예외를 붙입니다

### L156 공급과 바인딩의 전체 관계를 먼저 안내합니다

> ## StorageClass는 공급 방식과 시점을 정합니다

기존 PV를 고르는 흐름과 새 PV를 공급하는 흐름이 긴 바인딩 설명 뒤에서 만납니다. PVC를 만들었는데 PV가 없는 일반 동적 공급 사례의 독자는 자기 상황이 어디에 속하는지 늦게 알게 됩니다

수정 방향: 도입에서 기존 PV 선택 또는 provisioner의 새 PV 공급 뒤 바인딩으로 합류한다는 두 경로를 안내합니다. 상세 동적 공급과 WFFC는 바인딩 기본 원리를 이해한 뒤 확장합니다

## 권장 설명 순서

1. PVC·PV·StorageClass의 역할과 기존 PV 선택·새 PV 공급이라는 두 진입 경로를 제시합니다
2. 클래스를 명시한 PVC가 용량·접근 방식 등 기본 조건에 맞는 기존 PV를 고르는 사례를 설명합니다
3. PV claimRef부터 PVC Bound까지의 별도 쓰기, UID로 구분하는 신원, 경쟁과 중간 실패의 재처리를 연결합니다
4. StorageClass와 external-provisioner의 동적 공급을 붙이고 Immediate·WFFC의 배치 순서를 비교합니다
5. 클래스 생략·빈 문자열·예약 PV·volumeName·접근 모드·spec 불변성 등 변형을 해당 기본 경로와 비교합니다
6. PVC 삭제 뒤 Released와 회수 정책·삭제 보호를 구분하고 Pending의 남은 결정을 찾는 순서로 마칩니다

## 유지할 내용과 조건

- PV·PVC의 바인딩은 하나의 원자적 트랜잭션이 아니며 claimRef UID만으로 전체 완료를 확정하지 않는다는 설명을 보존합니다
- nil·빈 문자열·예약·직접 지목의 실제 차이를 삭제하거나 하나의 기본값으로 합치지 않습니다
- WFFC의 캐시 가정·API 쓰기·관측 완료 조건과 nodeName 우회의 영향을 유지합니다
- Bound·mount 완료·실제 쓰기 보호·Released·재사용 가능을 서로 구분합니다
