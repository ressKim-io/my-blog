## 독자와 중심 질문

드라이버가 보고한 노드별 볼륨 개수 상한을 스케줄러는 어떻게 사용하고, 그 값이 낡아 attach가 실패하면 어떤 갱신과 재생성이 이어질까요?

선행 개념: CSINode의 등록 정보, 스케줄러 Filter, VolumeAttachment의 역할을 전제합니다. 개수 상한과 용량 바이트를 구분합니다

## 원문 근거와 개선점

### L56 일반 숫자 상한의 계산보다 특수값이 앞섭니다

> ## CSI의 0과 CSINode의 0은 다릅니다

드라이버→kubelet→CSINode→Filter의 도입은 명확합니다. 하지만 실제로 무엇을 세는지 보기 전에 0·nil·음수·다른 API 작성자라는 변형을 읽어야 합니다

수정 방향: 일반 양수 상한에서 기존 볼륨 키와 새 요구를 비교하는 과정을 먼저 설명합니다. 그다음 상한을 보고하지 않거나 0을 기록한 경우가 계산을 어떻게 바꾸는지 표로 제시합니다

### L116 계산에서 갱신으로 넘어가는 중심 흐름을 유지합니다

> ## 상한 검사와 드라이버 설치 확인은 별도입니다

세는 단위와 중복 제거를 설명한 뒤 설치 확인 기능과 Autoscaler 설정으로 이동하고, 다시 낡은 상한 갱신으로 돌아옵니다. 도입에서 제기한 배치 통과 후 attach 실패 질문의 답이 늦어집니다

수정 방향: 기본 Filter 계산 다음에 주기 재조회와 ResourceExhausted 반응을 붙입니다. 설치 확인·옵트인·과거 자원 키는 이 계산과 갱신의 적용 조건으로 후반에 정리합니다

## 권장 설명 순서

1. 배치는 통과했지만 attach가 실패할 수 있다는 상황과 드라이버·kubelet·스케줄러의 정보 전달을 제시합니다
2. 양수 상한에서 볼륨 키·기존 수·새 수를 계산하는 기본 Filter를 설명하고 Pod 수·publish target 수와 구분합니다
3. 값이 낡을 수 있는 이유와 같은 드라이버에 다시 묻는 주기 갱신을 연결합니다
4. 대기 실패 뒤 숫자 ResourceExhausted 코드를 확인하는 조건, 재조회, Pod 실패, 워크로드 컨트롤러의 대체를 이어갑니다
5. 0·nil·음수 변환, 중복 계산의 예외, 설치 확인 옵트인과 항목 변경 범위를 정리합니다
6. 현재 CSINode 경로와 옛 Node 자원 키를 구분하고 개수·바인딩·위치 실패의 진단으로 마칩니다

## 연결 문장 예시

아래는 구성 예시이며 실행 결과나 새로운 경험이 아닙니다

스케줄러는 보고된 상한을 사용하므로 실제 attach 시점의 여유와 차이가 날 수 있습니다
이 차이를 줄이는 주기 갱신과, attach 실패 뒤 고갈 코드를 확인해 다시 묻는 경로를 이어서 보겠습니다

## 유지할 내용과 조건

- 모든 자료를 하나의 집합으로 합쳐 완전히 중복 제거한다는 설명으로 단순화하지 않습니다
- CSI의 0과 CSINode count: 0의 차이, 음수 입력에 대한 현재 구현을 보존합니다
- 재조회·상한 갱신 성공·Pod 실패가 하나의 원자적 작업이 아니며 같은 Pod를 이동시키는 동작이 아님을 유지합니다
- 주기 설정이 반응 갱신 경로에도 관여하고 실제 재배치 성공은 보장하지 않는 조건을 보존합니다
