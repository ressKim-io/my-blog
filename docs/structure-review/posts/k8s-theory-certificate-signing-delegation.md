## 독자와 중심 질문

인증서 발급과 요청 신원 변경에 왜 실제 조회 객체가 없는 권한 이름을 사용하는지 이해합니다

선행 개념: 인증·인가, RBAC의 resource/verb/name

## 현재 전개

- L24: 인증서와 impersonation은 적용되는 요청 범위가 다릅니다
- L39: CSR은 요청 내용과 요청자 신원을 함께 저장한다
- L84: CSR 생성, 자동 승인, 서명은 서로 다른 권한이다
- L139: signers는 필드 조건을 리소스 이름 조건으로 바꾼다
- L167: 첫 인증서 전에는 bootstrap token으로 인증한다
- L208: 갱신 시점과 발급 수명은 서로 다른 설정이다
- L244: CA 신뢰 배포와 Pod 인증서 발급도 구분해야 한다
- L261: impersonation은 인증 후, 실제 작업의 인가 전에 적용된다
- L363: 멈춘 지점에 따라 확인할 권한도 달라진다

## 원문 근거와 개선점

### L167 발급을 시작하는 자격증명이 발급 권한 설명보다 늦습니다

> ## 첫 인증서 전에는 bootstrap token으로 인증한다

새 노드의 CSR 생성·승인·서명을 이미 따라간 뒤 처음 인증 방법을 배웁니다. 독자는 인증서가 없는데 CSR API를 어떻게 호출했는지 앞부분을 재해석해야 합니다

수정 방향: bootstrap token의 최소 역할을 발급 사례 시작에 둡니다. 토큰 형식·만료와 인증서 갱신 수명은 기본 발급 경로 다음에 보충합니다

### L139 두 큰 주제를 묶는 공통 이유가 늦습니다

> ## signers는 필드 조건을 리소스 이름 조건으로 바꾼다

발급과 impersonation을 함께 다루는 이유는 조회 대상이 아닌 권한 속성을 만드는 모델입니다. 이 원리가 CSR 세부를 읽은 뒤에야 등장하고 impersonation은 훨씬 뒤에서 새로 시작합니다

수정 방향: 도입에서 실제 endpoint와 authorizer에 묻는 속성의 차이를 짧게 제시합니다. 발급·사칭을 독립된 두 사례로 구분하고 끝에서 같은 모델로 비교합니다

## 권장 설명 순서

1. 발급 자격증명과 한 요청의 impersonation은 적용 범위가 다름을 유지합니다
2. 실제 API 객체와 합성 인가 이름의 차이를 간단히 예고합니다
3. bootstrap 인증 → CSR 생성 → 요청자 승인 자격 → 승인 기록 → 서명 → 인증서 사용을 한 번에 설명합니다
4. signers·nodeclient 권한의 의미를 그 경로의 각 판단과 연결합니다
5. 갱신·서빙 인증서·CA 신뢰 배포·Pod 발급 API를 별도 확장 사례로 둡니다
6. impersonation의 원래 사용자 인증 → 사칭 권한 → 신원 교체 → 실제 작업 인가를 설명하고 제한 사칭·기존 권한 폴백을 붙입니다

승인 컨트롤러는 요청자의 자격을 별도의 권한 속성으로 다시 묻습니다

## 유지할 내용과 조건

- CSR 생성·approve·sign의 분리, 인증서와 CA 신뢰는 별개
- legacy signer 서빙 여부와 현재 gate 조건
- 제한 사칭에 넓은 기존 권한이 남을 때의 폴백, 사칭과 실제 작업 권한은 별개
