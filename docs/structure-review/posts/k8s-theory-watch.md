## 독자와 중심 질문

LIST 이후 로컬 상태를 유지하다 연결이나 이력을 잃었을 때 어떻게 현재 상태를 복구하는지 이해합니다

선행 개념: 객체와 LIST의 resourceVersion, snapshot

## 현재 전개

- L24: 목록의 번호로 이후 변경을 이어 받습니다
- L43: 410 이후 번호만 건너뛰면 삭제된 객체가 남을 수 있습니다
- L56: watch의 빈 번호와 양수 번호는 의미가 다릅니다
- L78: 최근 변경 이력은 API 서버마다 따로 유지합니다
- L104: 75초는 모든 이벤트의 보존을 보장하는 시간이 아닙니다
- L128: LIST가 요구하는 최신 상태를 캐시에서도 제공할 수 있습니다
- L179: 410이 발생한 층은 오류 문구로 구분할 수 있습니다
- L195: Reflector는 오류가 난 요청에 따라 다시 읽는 방법을 고릅니다
- L227: BOOKMARK는 변경이 없어도 재개 번호를 앞으로 옮깁니다

## 원문 근거와 개선점

### L78 복구 흐름 중 서버 메모리 구조로 전환합니다

> ## 최근 변경 이력은 API 서버마다 따로 유지합니다

410 때 snapshot을 다시 받아야 한다는 설명은 좋습니다. 그러나 이후 번호 옵션·캐시 용량·이력 시간·LIST 구현을 거쳐야 Reflector 복구가 나옵니다

수정 방향: LIST → 변경 반영 → 끊김/410 → snapshot 교체를 클라이언트 관점에서 먼저 완성한 뒤 watch cache의 비용과 한계를 풉니다

### L227 BOOKMARK의 필요성이 시간 상수보다 늦습니다

> ## BOOKMARK는 변경이 없어도 재개 번호를 앞으로 옮깁니다

앞에서 60초·75초·15초 관계를 읽을 때 어떤 클라이언트가 오래된 커서에 머무는지 사례가 없습니다. 마지막 app=web 사례가 이를 잘 설명합니다

수정 방향: app=web 사례와 BOOKMARK의 역할을 먼저 옮기고, 시간 상수는 캐시 이력 유지의 구현 설명에 붙입니다

## 권장 설명 순서

1. 같은 범위의 LIST snapshot과 그 번호로 여는 watch를 먼저 따라갑니다
2. ADDED·변경·삭제를 로컬 사본에 반영하며 양수 번호 watch에는 초기 객체가 없음을 설명합니다
3. 관심 객체가 안 바뀌는 예로 BOOKMARK를 소개하고 전달 주기 비보장을 붙입니다
4. 410에서 삭제 객체가 남는 기존 사례로 전체 snapshot 복구와 Reflector의 실제 폴백을 연결합니다
5. streaming list를 초기 snapshot을 같은 스트림에서 받는 방식으로 비교합니다
6. 서버 watch cache·etcd 이력·LIST 최신성 옵션과 문서/구현 차이를 심화 단위에서 설명합니다

## 유지할 내용과 조건

- 복구 대상은 모든 과거 이벤트가 아니라 현재 상태
- legacy watch의 빈 번호에 관한 문서/구현 차이와 server/client gate 이력
- LIST 폴백·GET 경로 차이, 60초·75초는 보장이 아님, 서로 다른 두 이력의 410
