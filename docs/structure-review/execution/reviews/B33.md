# B33 독립 검토 — review_a

## 첫 독해 기록

글별 검토서보다 먼저 수정본 두 편의 전문을 읽었습니다

- policy-layers: 요청 거절/요청 변경/저장 뒤 변경의 차이를 도입에서 설명하고 실행 위치와 입력을 비교합니다. 매칭·평가·정상 위반의 경계를 표로 읽은 다음 소유권/재실행·배경 처리·GitOps 필드/존재 충돌로 연결됩니다. VAP 오류의 세부는 많지만 비교 대상인 정상 false 결과를 표의 첫 행에 먼저 두며 별도 직접 거절을 예외로 나눕니다. 제품 이름을 동작 보장으로 읽지 않도록 버전·설치 미확인과 범위를 유지합니다. 첫 독해에서 필수 수정 발견하지 않음
- extension-failure-boundaries: 네 가정 요구(통신·이미지·기본 정책·외부 큐)가 서로 다른 집행 위치로 연결됩니다. 큐 접수와 준비 완료의 차이에서 진행 상태 필요를 바로 설명하고, 이후 장애·복구 설정·데이터/설정 제거·사용자가 읽는 결과로 확장합니다. Conversion과 discovery 조건은 이미 다룬 CRD/controller와 aggregation을 비교하는 보충으로 읽히며, 개별 선행 글 링크를 열지 않아도 영향 범위를 이해할 정의가 함께 있습니다. 첫 독해에서 필수 수정 발견하지 않음

## 원문 대조와 판정

두 baseline 전문과 글별 검토서를 대조했습니다. 정책 계층은 버전·기본값 표와 정책 자체 삭제 예외를 후반에 두어 검증→변경→배경 변경/검사→GitOps 비교가 끊기지 않습니다. 첫 독해에서 필요한 failurePolicy와 CEL 정의도 사용 지점에 추가됐습니다. VAP Warn/Audit 직접 거절 조건·코드 422/403/401/413, PSA Pod/template, API 기반/manifest 기반 제외 범위, MAP의 atomic 제한/field manager/재호출 조건, Gatekeeper 60초/20개와 totalViolations, Kyverno 비동기 기본1시간·생성물 동기화/문서 불일치·라벨/UID 조건, Argo 버전 및 annotation 예제·비교 범위가 모두 보존됐습니다

장애 범위 글은 기존 네 사례와 큰 순서를 유지하는 판단이 적절합니다. 큐 사례에서 사용자가 읽을 진행·준비·실패 경로를 먼저 짚고 마지막에 네 요구의 결과를 회수합니다. Condition 상세는 삭제하지 않고 선택한 경우의 보충 절로 나눠 전체 마무리를 상세 필드로 끝내지 않습니다. 요청 저장/실제 준비 차이와 상태 노후화, finalizer 저장 책임, VAP 오류·conversion 필요/DELETE 조건·discovery의 부분 처리 및 Pod 우선 조건, 정적 정책 제외 예외, pruning/보존 예외와 storedVersions 실제 이행 한계, managedFields 비복원, APIService 제거 후 데이터 잔존과 Condition 필수/선택/헬퍼 한계를 보존했습니다

front matter·버전/수치·코드·출처 및 내부 링크·그림을 대조했고 두 편 완료·미해결 0입니다. 외부 기술 재검증 및 빌드·테스트 실행 안 함(검토 범위). SHA는 동반 JSON에 기록합니다
