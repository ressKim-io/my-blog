## R1 — VolumeAttributesClass의 역할을 먼저 구분하면 좋습니다

- 구분: 권장
- 상태: 수정 담당에게 반송 후 보완 확인 / 해결
- 위치: 1차 검토본 L176~182, `기존 PV를 고르는 세부 조건과 직접 지목의 차이`
- 인용: `volumeAttributesClassName | 일치. nil·빈 값은 빈 이름으로 비교`, `VolumeAttributesClass는 v1.34 GA이며…`, `볼륨 속성 클래스도 현재 짝짓기 조건에 포함됩니다`
- 독자가 막히는 이유: 앞에서 StorageClass가 공급 방식을 정한다고 배웠지만, 여기서는 새 클래스의 역할보다 이름 일치와 버전 조건을 먼저 만납니다. 이름이 비슷한 두 클래스가 왜 따로 필요한지 처음 읽는 독자는 알기 어렵습니다
- 수정 방향: 기존 근거에서 역할을 확인한 뒤, 표에 들어가기 전이나 첫 등장 바로 옆에 StorageClass와의 역할 차이를 한 문장으로 설명합니다. nil·빈 값의 비교와 버전 조건은 그대로 유지합니다
- 범위 판단: 원문부터 있던 짧은 설명 부족입니다. 정상 바인딩 흐름 전체를 막는 필수 결함으로 판정하지는 않았지만, 메인 검토에서 이번 선행 개념 보완 범위로 채택했습니다

### R1 재검토

최종본은 매칭 표 앞에 다음 설명을 추가했습니다

> StorageClass가 공급 방식과 시점을 정한다면, **VolumeAttributesClass**는 드라이버별 처리량 같은 볼륨 속성을 표현하는 별도 오브젝트입니다
> PV를 고를 때는 이 속성 클래스의 이름도 PVC의 요청과 비교합니다

WFFC의 재배치·capacity 한계가 끝나는 부분부터 세부 매칭 절과 accessModes 선택 순서, 1Gi·100Gi 예제, 직접 지목과 spec 불변성 절까지 앞뒤를 다시 읽었습니다. 속성 클래스의 역할을 배운 뒤 이름 매칭 조건을 만나므로 R1을 해결로 판정합니다. 뒤의 버전 조건, nil·빈 값 비교, 조합별 최소 PV 선택 조건은 유지됐습니다

보완 설명은 기존 `k8s-theory-volume-expansion-snapshots-ephemeral.md`의 L234~253에 있는 VolumeAttributesClass 설명과 대조했습니다. 그 글을 읽어야 하는 연결 문장을 새로 넣지 않았으며 B02 안에서 필요한 역할을 알 수 있습니다. 이 대조는 기존 근거와의 일관성 확인이며 외부 소스 전체 재검증은 아닙니다

## 원문 보존 대조

원문과 수정본 전문을 대조했고, 아래 내용의 누락이나 의미 변경을 찾지 못했습니다

- Kubernetes v1.37.1과 고정 소스 ref, website 저장본 ref, external-provisioner v6.4.0, 클러스터 실행 미포함 한정
- claimRef·PV Bound·PVC volumeName/완료 어노테이션·PVC Bound의 별도 쓰기와 이미 같은 값일 때 생략 가능성
- UID 없는 이름 예약과 UID를 포함한 신원의 차이, UID만으로 전체 완료를 확정하지 못하는 조건
- API 충돌·재처리, 기본 15초 주기가 완료 상한이 아니라는 점, 컨트롤러 예약과 수동 예약의 되돌림 차이
- StorageClass 필드의 기본값과 512개 키 한도, 실제 드라이버 지원 조건, 외부 공급 이벤트 해석과 PV 이름 옵션
- WFFC의 예약 PV 예외, Reserve와 PreBind의 구분, 기본 600초·1초 관측 주기, 직접 GET이 아닌 캐시 관측, 마지막 PVC phase와 다른 완료 조건
- Unreserve가 성공한 API 쓰기 전체를 되돌리지 않는다는 점, nodeName 우회, 재배치 조건, capacity 정보가 낡을 수 있다는 한정
- 세부 매칭 조건, 모드 수가 적은 조합부터 선택하는 범위, 1Gi·100Gi 사례와 spec/status 구분, pre-resize 용량 예외
- volumeName 직접 지목에서 검사하는 조건과 생략하는 selector/nodeAffinity, Pod 스케줄링의 별도 위치 제약, PVC spec 불변성의 조건부 예외
- nil·명시적 빈 문자열·옛 어노테이션, 기본 클래스 소급 지정 분기, 여러 기본 클래스의 생성 시각·이름 순서
- RWO·ROX·RWX·RWOP의 의미와 실제 지원 범위, 쓰기 보호·attach 검사와의 차이, RWOP와 VolumeBinding의 스케줄 실패 상태 구분, CSI Block/Mount와 접근 모드의 차이
- Released·Lost·Retain·Delete·deprecated Recycle과 서로 다른 삭제 보호 finalizer, 외부 공급자의 finalizer 추가 조건
