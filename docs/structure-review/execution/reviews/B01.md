## 독립 독해

글별 검토서·수정 기록을 읽기 전에 수정본 전문 266줄을 처음부터 끝까지 읽었습니다. 이후 baseline 원문 전문과 글별 검토서를 대조했습니다. 수정 기록은 읽지 않았습니다

- dev·prod·Deployment web 가정이 전체 기본 흐름의 기준으로 유지됩니다. 도입에서 종류와 URL resource·API group·본문을 구분해 인가 속성 표를 먼저 이해할 수 있습니다
- 인증·APF·인가·디코딩·defaulting·mutating·타입 검증·validating·저장 순서가 먼저 나오고, APF의 FlowSchema와 필터 조립은 후반으로 옮겨졌습니다
- replicas -1과 limits 없는 사이드카 예제는 각각 타입 검증과 변경 후 정책 검증을 설명하기 위한 것으로 전환 이유가 있습니다
- Deployment 저장 뒤 ReplicaSet·Pod의 별도 생성 요청이 이어진다는 점을 읽은 뒤 오류 응답과 audit 한계로 넘어갑니다
- 후반 GVK/GVR은 동일 Deployment 예제로 URL을 분석하며 core pods 경로와 비교합니다. 기본 CREATE의 URL 예제가 갑자기 바뀐 것으로 제시하지 않습니다
- dry-run의 비저장·동일 인가·quota 비예약·webhook 부작용 책임 구분이 앞의 요청 흐름에 연결됩니다

## R1 — webhook 역할 정의가 첫 사용보다 늦습니다

- 구분: 권장 / 요청된 선행 개념 보완 범위
- 상태: editor_pilot에게 반송 후 해결 확인
- 위치: 수정본 L67, L90, L194
- 인용: `뒤의 mutating webhook이 받는 것은 사용자가 작성한 YAML 원문이 아니라 AdmissionReview에 담긴 오브젝트입니다`
- 막히는 이유: APF 절을 뒤로 옮기며 그 절에 있던 webhook의 일반 정의도 L194로 이동했습니다. 첫 등장에서는 admission 내부 플러그인과 외부 webhook의 관계를 아직 알 수 없고, L90의 validating webhook 설명에 이르러서야 외부 판단을 추정하게 됩니다
- 수정 방향: 기존의 외부 HTTP 호출 역할 설명을 첫 webhook 등장 부근으로 옮기거나 mutating webhook의 역할을 짧게 보완합니다. 후반 APF의 중복 정의는 조정합니다

재검토에서는 디코딩·defaulting 절의 첫 webhook 등장 바로 전에 외부 HTTP 호출 역할 설명이 놓였고, 후반 APF의 중복 정의는 제거된 것을 확인했습니다. 디코딩 앞뒤와 APF 앞뒤를 다시 읽었으며 기존 설명의 이동으로 역할을 먼저 알 수 있어 해결로 판정합니다
