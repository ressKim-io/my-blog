# B32 독립 검토 — review_a

## 첫 독해 기록

글별 검토서보다 먼저 aggregated-api-server 수정본 전문을 읽었습니다. CRD의 고정 저장 경로와 metrics-server의 메모리/배경 수집 예를 먼저 구분해 별도 서버를 둘 이유를 잡습니다. APIService의 경로 등록→신원 전달과 양방향 TLS 신뢰→확장 서버의 원래 사용자 인가를 마친 뒤 가용성·discovery·Namespace 삭제로 장애 범위를 넓힙니다. APIService의 등록/Available과 실제 자원 성공이 같은 뜻이 아님을 각 단계에서 구분합니다. 표본 계산·수집 주기는 마지막 확장으로 돌아오며 앞의 last/prev 맵과 연결됩니다. 첫 독해에서 필수 수정 발견하지 않음

## 원문 대조와 판정

baseline 전문과 글별 검토서를 대조했습니다. 필요성/메모리 표본 사례를 앞당기되 표본 계산·배포 인자 등의 상세는 후반에 두었으며, discovery 정렬도 APIService 기본 필드에서 분리해 목록 설명으로 옮겼습니다. Discovery와 OpenAPI 정의 문장을 해당 두 절로 나눠 각각의 도입에 놓았습니다. 매핑 경로/기본 필드, subresource 동사 분류 및 bind/escalate 예외는 누락 없이 남았습니다

로컬 위임 예외·코어 /api, UID gate와 신원 헤더/Authorization 제거, 두 CA 신뢰 방향과 CN 조건, 위임 인가 예외/캐시, EndpointSlice Ready·포트 조건, 5개 병렬/5초/6초·HTTP200~299·일반 사용자 검사 아님, Available과 프록시503의 경계가 보존됐습니다. discovery Stale/nil 및 부분 오류, OpenAPI1분, Namespace Pod 우선 삭제·오류시 finalizer 보류, metrics-server 메모리 last/prev·표본 제외·60초/15초/최소10초/90% 조건과 버전 구분도 유지합니다

front matter·수치·출처 URL·그림 및 모든 기술 조건을 대조했고 완료·미해결 0입니다. 외부 기술 재검증 및 빌드·테스트 실행 안 함(검토 범위). SHA는 동반 JSON에 기록합니다
