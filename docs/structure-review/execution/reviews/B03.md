## 첫 독해와 독자 흐름

글별 검토서·수정 기록보다 먼저 수정본 전문 253줄을 읽고, 이후 baseline 원문 전문과 구조 검토서를 대조했습니다. 수정 기록 Markdown은 읽지 않았습니다

- 도입이 빈 캐시와 실제 부재를 구분하며 현재 사본으로 재판단한다는 목적을 제시합니다. Reflector·변경 큐·Indexer·이벤트 핸들러·작업 큐·워커의 순환을 먼저 읽을 수 있습니다
- 초기 snapshot과 이후 watch를 배운 뒤 cache sync, handler sync, 최신성의 차이를 이해할 수 있습니다. 소스 로그는 실측이 아니라고 인접 문장에서 명시합니다
- Pod 이벤트에서 부모 ReplicaSet 키를 찾는 기본 단계 뒤에 고아 Pod의 add/update/delete 차이와 Deployment의 2단계 UID 검사를 놓아 예외의 이유가 생깁니다
- 현재 상태 재판단을 설명한 뒤 Indexer의 부모·고아 키를 읽게 돼 키가 필요한 이유를 알 수 있습니다. `default/ReplicaSet/web/aaa` 가정과 삭제 복구용 a/b/c 가정은 각각 별도 목적을 밝힙니다
- RealFIFO·AtomicFIFO·DeltaFIFO 차이는 기본 사용 흐름 뒤에 있습니다. 큐의 초기 반영 판정과 processDeltas 콜백 변환도 이 구현 설명에 붙어 앞의 동기화 의미를 가로막지 않습니다
- 삭제 c를 새 snapshot에서 찾는 사례가 tombstone·낡은 소유 관계·resync의 차이로 이어집니다. resync 표는 API 재조회가 아니라는 차이를 비교하며 본문이 표 전체를 불필요하게 재진술하지 않습니다
- shared factory·느린 handler 버퍼와 마지막 진단 표는 앞의 저장·알림 단계를 근거로 읽을 수 있습니다. watch·identity·reconcile 링크를 따라가지 않아도 이 글의 핵심 판정은 가능합니다
