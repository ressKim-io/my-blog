# B10 독립 검토 — review_a

## 첫 독해 기록

글별 검토서보다 먼저 수정본 두 편을 처음부터 끝까지 읽었습니다

- serialization-version-conversion: 요청→메모리→저장 기본 경로와 기본값 적용을 먼저 설명하고 hub·Scheme·출력 협상으로 범위를 넓힙니다. CRD의 내부 Go 타입 부재와 hub 사용 가능성을 구분한 후 Event 사례를 지나 KEP-6164로 넘어갑니다. 이때 “KEP-6164가 내장 타입의 향후 구조를 설명할 때 CRD를 참고하는 이유도 이 구분에 있습니다”의 “이 구분”이 바로 앞 Event 사례와 맞지 않아 재탐색이 필요합니다. 원문과 이동 내역을 대조합니다
- version-emulation-rollback: binary/emulated/minCompatibility 정의와 한 예를 먼저 제시하므로 feature gate·API 노출·저장 버전·CEL 각 범위로 넘어갈 때 용어를 다시 추측하지 않아도 됩니다. 되돌리기 제한을 설명한 뒤 허용 범위/옵션/문서 차이를 보충합니다. 이 첫 독해에서 필수 수정 발견하지 않음

## 원문 대조와 판정

두 baseline 전문과 글별 검토서를 읽고 대조했습니다. serialization의 L238은 원문에서 CRD의 내부 타입/hub 구분 바로 뒤에 있던 문장이 Event 절을 건너 KEP로 이동한 결과입니다. 제목에서 구분을 짐작할 수 있으나 CRD를 참고한 이유를 설명하는 지시가 멀어졌습니다. 원위치로 돌리거나 현재 자리에서 구분을 직접 적도록 메인에 반송했습니다. 다른 변경은 순서·헤더 수준 조정이며 defaulting 예외, 출력 타입별 protobuf 지원, CBOR 읽기 조건, KEP 진행 상태, continue 토큰의 snapshot·410 조건을 보존했습니다

version-emulation은 초반에 설정을 낮춰도 이미 기록한 바이트가 역변환되지 않는다는 답을 두고, gate/서빙/저장/CEL에서 그 영향을 따라갑니다. 범위·forward compatibility·OpenAPI 세부를 뒤로 옮겨도 전제·예외·문서와 구현의 차이는 빠지지 않았습니다. “앞 글의 StorageVersion” 의존을 현재 절의 저장 버전 선택 문제로 풀었습니다. 미해결 0으로 완료합니다

두 글의 front matter·코드·출처 및 내부 링크·그림이 보존됐습니다. 외부 기술 재검증 및 빌드·테스트 실행 안 함(검토 범위). SHA는 동반 JSON에 기록합니다

## 반송

- serialization-version-conversion L238: “KEP-6164가 내장 타입의 향후 구조를 설명할 때 CRD를 참고하는 이유도 이 구분에 있습니다” — CRD에서 Event를 건너 이동해 이유의 지시 대상을 재탐색해야 함. 기존 CRD 설명 옆으로 되돌리거나 별도 내부 타입 없이 버전이 있는 타입을 hub로 사용할 수 있음을 명시할 것. 해결


## 재확인

editor_pilot의 수정 뒤 저장 코덱 절 끝부터 CRD·Event·KEP 전체와 continue 도입(L195~260)을 다시 읽었습니다. L238이 “KEP-6164가 CRD를 참고하는 이유는 별도 내부 타입 없이도 버전이 있는 타입을 hub로 사용할 수 있기 때문입니다”로 바뀌어 Event 사례를 건너서도 참고 이유를 직접 이해할 수 있습니다. 두 단계/현재 목표/실제 내부 타입의 구분도 이어집니다. 반송 1건 해결, 두 글 완료·미해결 0. 최종 SHA는 동반 JSON에 갱신했습니다
