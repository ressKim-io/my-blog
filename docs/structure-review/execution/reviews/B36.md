첫 독해에서 mount의 경로 연결과 bind의 기존 트리 재사용 결과를 먼저 설명합니다. VFS 표는 같은 데이터와 별도 경로 연결이라는 이미 생긴 질문을 풉니다. 이어 재귀 여부→stage/publish의 가정 사례·정리→열린 참조/umount로 한 경로의 수명을 완결하고, namespace와 전파·읽기 전용을 확장 조건으로 읽습니다. umount 뒤에서 설명하는 shared/slave를 먼저 요구하지 않도록 해제 사건 전파 문단이 전파 표 뒤에 붙어 있습니다

원문 대조에서 다음을 확인했습니다

- mount에 가려진 내용 비삭제·bind 비복사/비포맷/비문자열 링크·동시 쓰기 보장 아님, VFS 네 객체와 inode 없는 dentry·vfsmount/path·clone_mnt의 하위 루트 재사용
- 비재귀 bind의 가려진 하위 디렉터리 노출·MS_BIND/MS_REC·unbindable 제외·현재 하위 mount 복제와 향후 사건 전파 구분
- stage capability와 생략, kubelet 경로와 실제 syscall 주체, 같은 노드 다중 target 허용 전제·staging 1+Pod 수의 제한된 집계·블록/전파/runtime 예외·멱등 재시도·모든 unpublish 후 unstage
- struct file의 f_path·기존 열린 파일과 경로 탐색 차이·EBUSY 참조/하위 mount/전파·MNT_DETACH 뒤 실제 자원과 외부 볼륨 완료 비보장
- namespace 목록 복사와 파일 데이터 비복제·mount별 전파·shared/slave 동시 관계·사건과 데이터 구분
- 별도 CSI namespace의 방향 전제·같은 namespace 등 예외, None rprivate/rslave fallback·HostToContainer/Bidirectional·재귀 속성 변경과 재귀 bind 차이, privileged 요구의 컨테이너 범위·권장 볼륨 타입
- 기존 mount API의 MS_RDONLY 미적용/원본 속성·remount 범위·보존할 플래그, mount_setattr/AT_RECURSIVE 및 호출 조건·하위 mount 쓰기 가능성, recursiveReadOnly의 readOnly/전파 검증·Linux 5.12/CRI/OCI·Enabled 실패와 IfPossible fallback 범위

두 그림의 가정과 본문 참조, 선행 글 없이 이해 가능한 stage/publish 최소 역할, 수치·버전·출처·실측 미수행 조건을 확인했습니다. 이유 없는 예제 변경이나 불필요한 반복 안내를 찾지 못했습니다. front matter·코드 fence·모든 링크 보존, 이미지 존재, 최종 SHA 일치를 보조 검사했습니다. 빌드·전체 테스트 실행 안 함. 원문 기술 주장 전체를 외부 자료로 새로 검증하지 않았습니다
