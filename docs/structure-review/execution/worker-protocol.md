# 이번 실행의 에이전트 작업 규칙

이 문서는 사용자 요청을 실제 수정·검토 기록에 적용하는 작업 안내입니다
설명 품질을 문서 형식이나 자동 검사 통과로 대신 판정하지 않습니다

## 수정 담당

- 본인 배정표의 본문과 `edits/{batch}.md`, `edits/{batch}.json`만 수정합니다
- 다른 담당자와 동시에 작업하며, 타인의 변경을 덮어쓰거나 되돌리지 않습니다
- 한 번에 1~3편 묶음을 처리합니다. 각 글 원문 전문과 해당 검토서를 읽고 문단 연결 계획을 기록한 뒤 편집합니다
- 헤더·요약만 읽고 일괄 변환하거나 검토서 권장 목차를 기계적으로 구현하지 않습니다
- 기본 흐름을 완결하되 결과를 바꾸는 조건은 주장 가까이에 둡니다. 자연스러운 기존 사례는 유지합니다
- 기술 사실·조건·버전·소스 ref·코드·수치·가정·출처·이미지 참조·불확실성을 보존합니다
- front matter 전체는 변경하지 않습니다. 자산·사이트 코드·기준 manifest도 변경하지 않습니다
- 필요한 용어의 역할이 빠졌다면 기존 본문과 근거를 먼저 확인하고 최소 설명을 보완합니다
- 새 실험·경험·성능 결과를 만들지 않습니다. 기술 재확인은 구조 수정과 별도로 기록합니다
- 각 묶음이 끝나면 메인에 알려 독립 검토로 넘기고, 승인 대기 없이 다음 배정 묶음을 진행합니다
- 반송이 오면 해당 글을 수정하고 변경 위치·새 SHA256을 알립니다

수정 Markdown 기록에는 글별 전문 독해, 편집 전 연결 계획, 실제 변경, 미채택 제안과 이유, 보존 대조, 기술 확인 사항을 남깁니다
JSON은 상태 집계를 위한 보조 기록이며 설명 검토를 대신하지 않습니다

```json
{
  "batch": "B00",
  "editor": "담당자",
  "posts": [{"slug": "대상", "edit_status": "completed", "sha256": "수정본 SHA256"}]
}
```

## 독립 검토 담당

- 본문을 직접 고치지 않습니다. 소유 범위는 `reviews/{batch}.md`, `reviews/{batch}.json`입니다
- 글별 검토서와 수정 기록을 읽기 전에 수정된 본문 전문을 처음부터 끝까지 읽습니다
- 첫 독해에서 막히는 위치와 이유를 기록한 뒤 편집 전 원문 전문과 글별 검토서를 대조합니다
- 원문은 `/tmp/k8s-structure-20261025-baseline/`의 같은 상대 경로에 있습니다
- 설명 이유가 앞 문맥에서 생기는지, 미설명 개념에 의존하는지, 기본 사례 전 구현·예외로 빠지는지 확인합니다
- 뒤에서야 배울 개념, 개념·설정·구현·관측 전환, 사례와 관점 변경, 지시어·그림·표·코드·절 참조를 확인합니다
- 선행 글 링크 없이 핵심을 이해할 수 있는지, 요약·예고·반복 안내가 늘어나지 않았는지 확인합니다
- 원문 대조에서 내용·조건·출처·코드·수치·버전·불확실성 누락을 확인합니다
- 발견한 문제는 위치·인용·막히는 이유·수정 방향과 함께 메인과 담당 수정자에게 보냅니다
- 수정 뒤 변경 부분과 앞뒤 흐름을 다시 읽은 다음 최종 SHA256 기준으로 판정합니다
- 필수 수정이 남은 글을 완료로 표시하지 않습니다. 권장 사항도 실제 처리·유지 이유를 기록합니다

```json
{
  "batch": "B00",
  "reviewer": "담당자",
  "posts": [{"slug": "대상", "review_status": "completed", "sha256": "검토본 SHA256", "open_findings": 0}]
}
```

## 공통 제한

commit·push·배포·새 의존성 추가를 하지 않습니다
원문 기술적 주장의 정확성을 새로 검증하지 않았다면 검증 완료라고 쓰지 않습니다
한 묶음이 끝나도 배정 전체가 끝나기 전에는 전체 완료라고 보고하지 않습니다
