# 메인 에이전트의 글 사이 연결 검토

이 기록은 각 글의 독립 검토와 별개입니다
완료된 수정본의 연결부·관련 절을 읽고 시리즈별 역할, 중복, 선행 글 의존 여부를 확인합니다
2026-10-25 최종 확인: 71편이 속한 모든 시리즈의 연결부·관련 절 대조를 마쳤습니다
글별 전문 독해와 원문 대조는 독립 검토 기록에, 실행 검증은 [검증 결과](verification.md)에 구분해 남깁니다

## PVC와 뒤의 CSI·스토리지 글

PVC 파일럿의 원문 전문과 수정본 변경 구간, 최종 독립 검토 결과를 확인했습니다
이 글은 PV·PVC의 참조와 상태를 맞추는 바인딩을 설명하며, attach·mount 완료와 구분합니다
WFFC의 완료 관측도 PVC의 마지막 phase 쓰기와 같다고 하지 않으므로 뒤의 CSI·attach 글에서 다른 완료 대상을 설명할 여지가 유지됩니다
VolumeAttributesClass는 이 글에서 후보 이름을 비교하는 데 필요한 역할만 설명하고, 생성·기존 볼륨 수정의 세부 기능은 확장·스냅샷 글이 맡습니다
후속 스토리지 글과의 최종 대조 결과는 아래 ‘PVC에서 CSI 준비로 이어지는 흐름’과 ‘스토리지 수명·변경·배치의 단위’에 기록했습니다

## API 생성 요청과 후속 API 글

B01 수정 본문 전문을 읽었습니다
내장 resource CREATE 요청이라는 범위를 먼저 고정하고, 인증·인가·admission·저장까지의 지도를 제공합니다
필드 정책은 admission, 신원은 인증, 동작 허용은 인가가 맡는다고 본문 안에서 짧게 설명하므로 다른 글 링크가 핵심 설명을 대신하지 않습니다
저장 성공과 컨트롤러의 ReplicaSet·Pod 생성은 별도 요청으로 구분합니다
APF 상세와 400/422 분류, 요청 종류·GVK/GVR·dry-run은 기본 저장 흐름 이후에 배치되어 심화 글과의 역할 경계를 유지합니다
후속 인증·인가·admission·APF·reconcile 수정본도 아래 관련 절에서 같은 경계를 확인했습니다

## 배치 판단과 노드 실행의 연결

B14·B15 수정본의 도입·기본 설명과 관련 글 링크 문단·마무리를 읽었습니다
스케줄링 사이클 글은 Filter/Score·assume·API Binding의 역할, 제약 글은 노드 필수 조건과 선호, preemption 글은 희생자 선정과 Eviction API의 PDB 검사를 나눕니다
스케줄링의 PostFilter 성공을 바인딩 성공으로 확대하지 않으며, PDB 글은 일반 DELETE와 eviction 서브리소스의 차이를 본문 안에서 설명합니다
kubelet 글은 이 삭제 요청을 실제 런타임 종료 요청과 연결하고, Running·Ready·PodScheduled를 구분합니다
CRI 글은 kubelet/런타임/shim/runc의 책임을 설명하며 sandbox 성공과 앱 컨테이너 준비를 합치지 않습니다
격리 글은 API/PSA 허용과 노드의 지원·설정 적용을 분리합니다. CRI 링크 앞뒤에서 필요한 차이를 설명하므로 링크 완독을 요구하지 않습니다
이 세 묶음의 짧은 단계 설명은 각 글의 전제를 세우는 데 필요하며, 전체 구현 표를 다른 글에 반복한 중복으로 보지 않았습니다

## 인증·인가·admission·확장·APF의 역할

B04·B05 수정본의 도입과 기본 사례, 다른 글로 연결하는 모든 문단을 대조했습니다
인증 글이 Pod의 ServiceAccount 토큰에서 `user.Info`를 만드는 흐름을 설명하고, 인가 글은 같은 `prod`/`web` 신원의 Pod 목록 요청을 받아 권한 범위를 설명합니다
Admission 글은 본문 값이 허용되는지라는 별도 질문과 Pod 생성 사례를 명시하므로 인증의 목록 요청이 이유 없이 생성 요청으로 바뀌지 않습니다
ServiceAccount admission의 명세 주입은 인증 글의 발급·파일 전달과 구분되며, 생략한 상세를 링크에만 맡기지 않고 해당 책임 차이를 본문에 남깁니다
Webhook 글은 AdmissionReview 응답 성공과 원래 요청 허용을 구분하고, 확장 지점 글은 CRD 등록·API 서빙·플러그인 활성·실제 매칭을 구분합니다
APF 글의 일반 인가 전 위치와 impersonation 인가 예외는 CREATE 지도 글의 적용 범위와 충돌하지 않습니다
필드 소유권·캐시·storage codec 등의 세부 설명을 이 묶음의 공통 소개에 다시 넣지 않아 각 후속 글의 역할을 유지합니다

## 버전·watch·informer

B06 두 글과 B03 informer의 도입·기본 사례·글 사이 연결 문단을 읽었습니다
resourceVersion 글은 오래된 PUT 충돌과 현재 상태로 다시 계산할 책임을 설명하고, watch 글은 같은 번호를 변경 이력의 커서로 사용하는 별도 질문을 시작합니다
watch는 LIST와 watch의 리소스 범위·selector 일치를 설명한 뒤 이력 소실과 전체 상태 복구를 다룹니다
informer는 커서 정책 전체를 반복하지 않고 Reflector→변경 큐→Indexer→핸들러의 역할과 초기 snapshot·이후 지연을 설명합니다
streaming list를 먼저 시도할 수 있는 현재 client-go 기본값은 일반 LIST/watch 설명과 구분하고 폴백 조건을 남깁니다
번호를 최신값으로 바꾸는 일, 초기 동기화가 끝난 일, 최신 상태를 항상 읽는 일을 서로 같은 보장으로 연결하지 않습니다

## 자원 계산·실행 제어·종료

B16·B17 수정본의 도입과 다른 글 연결 문단을 읽었습니다
QoS 글은 request가 배치 계산뿐 아니라 CPU 가중치에도 쓰인다는 연결을 남기고, 별도 자원 계산 글은 init/sidecar/overhead의 계산과 Score 선택을 맡습니다
swap은 kubelet 기동 허용·컨테이너 정책·스케줄러 allocatable을 별개로 설명합니다
Eviction/OOM과 Node heartbeat는 각각 자원 압박과 연락 두절이라는 다른 출발점을 유지합니다
두 글 모두 PDB를 집행하는 Eviction API와 자체 종료·DELETE를 구분하며, OOM 컨테이너 종료와 Pod 삭제도 합치지 않습니다
Node Ready Unknown과 Pod phase Unknown의 차이는 kubelet 글과 일관되고, 이 차이 자체가 본문에 있어 링크를 열지 않아도 오해를 피할 수 있습니다

## 신원·삭제·필드 소유권과 조정

B07~B09의 도입·핵심 사례와 글 사이 연결 문단을 확인했습니다
UID는 같은 이름의 다른 개체, resourceVersion은 조회 이후 변경, SSA는 필드 관리 범위를 구분합니다
삭제 글은 외부 자원 정리와 Pod 유예 종료가 서로 다른 기다림임을 본문 안에서 시작합니다
SSA 인계 글은 HPA 생성과 실제 replica 쓰기를 구분하고, reconcile은 API 쓰기 성공과 캐시 관측의 시차에서 출발합니다
이 연결에서 소유권·신원·버전을 같은 의미의 이름으로 줄이거나, 초기 동기화가 이후 최신성을 보장한다고 쓰지 않습니다

## 관측·로그·진단과 워크로드 목표

B18·B19의 도입·관련 글 연결부를 읽었고 HPA의 필드 소유권 절도 함께 대조했습니다
관측 글은 API 선언/상태·cgroup 계측·최근 지표 표본을 구분하고, eviction의 노드 working set을 컨테이너 값 하나로 대신하지 않습니다
로그 글은 경로 지정·기록·회전·조회 책임을 CRI 글과 연결하며, kubelet 접근 글에는 연결의 인증·인가 질문을 남깁니다
임시 컨테이너는 저장·시작·프로세스 실행을 나누어 상시 워크로드의 자원/재시작 보장으로 확대하지 않습니다
Deployment는 여러 ReplicaSet의 목표 수, Job은 성공 집계, CronJob은 생성 회차, HPA는 목표 replica 계산과 실제 쓰기를 맡습니다
HPA의 Update·SSA 충돌·강제 인계 설명은 SSA 두 글과 일관됩니다. 이 절은 실제 HPA 쓰기와 GitOps 상호작용을 이해하는 데 필요하므로 역할 정의까지 링크로 대체하지 않았습니다

## 표현 변환·호환 버전과 노드 입력

B10·B20·B21의 도입 및 관련 글 연결 문단을 읽었습니다
직렬화 글은 API 버전 표현과 바이트 형식을 나누고, emulation 글은 binary/emulated/min compat의 역할을 구분합니다
ConfigMap/Secret은 API 변경·kubelet 투영·애플리케이션 재읽기와 컨테이너 재생성을 구분하며, 롤아웃 링크는 실제 교체를 조정할 때의 별도 질문으로 연결합니다
장치 글은 노드의 수량 비교와 장치 ID 선택을 나누고, CRI 입력 준비와 노드 할당 성공을 합치지 않습니다
QoS가 장치 수량 자체로 결정되지 않는다는 연결은 자원 글의 CPU·메모리 계산과 일관됩니다

## 네트워크 준비와 전달

B22의 도입·관련 글 연결 문단을 읽었습니다
CNI는 런타임과 플러그인의 호출 규약, sandbox 글은 앱보다 먼저 준비되는 공유 실행 환경과 참조 수명, overlay 글은 노드 간 패킷 전달을 맡습니다
kubelet이 CNI를 직접 호출하는 것으로 책임을 바꾸지 않았으며 containerd/runc라는 구현 예시는 전체 CRI 요구와 구분합니다
pause를 모든 구현의 필수 계약으로 확대하지 않고, 주소 공급(IPAM)을 캡슐화 여부와 같은 선택으로 합치지 않습니다
후속 namespace 수명·Service·정책 글에서도 해당 경계를 확인했고 아래 관련 절에 기록했습니다

## 인증서·kubelet 접근·HA·저장 변환

B11·B12의 도입과 다른 글 연결 문단을 읽었습니다
인증서 발급은 남는 자격증명, impersonation은 현재 요청의 신원 변경으로 구분하며 APF가 사용하는 신원의 위치도 APF 글과 일관됩니다
kubelet 접근은 사용자의 pods/log 인가 뒤 API 서버 클라이언트가 kubelet에 접속하는 주체 변경을 설명합니다. 로그 파일 글의 경로·회전 책임과 질문이 겹치지 않습니다
HA 글은 etcd 합의, API 서버 요청 분배, controller 리더 선출을 나누며 workqueue/expectations의 범위를 프로세스 간 동시 제어로 확대하지 않습니다
저장 변환 글은 API 버전·직렬화 바이트·암호화 변환을 별도 결정으로 연결하고, 저장 암호화가 API 읽기 권한을 대신하지 않는다는 경계를 본문에 남깁니다

## Event·추적과 네트워크 주소

B13과 B23의 도입·다른 글 연결 문단을 읽었습니다
Event는 기록 구현과 조회 API 그룹을 구분하고, 추적은 API 서버 저장 span을 etcd 내부 단계 계측으로 확대하지 않습니다
두 글의 저장 변환 연결은 no-op/stale와 실제 변환기를 거치는 경우라는 서로 다른 조건을 남깁니다
Service는 EndpointSlice와 커널 전달, ServiceCIDR/IPAddress는 주소 확보와 Service 저장의 별도 쓰기를 맡습니다
Pod 주소 공급과 ClusterIP 할당의 주체·대역·용도가 다르다는 연결도 CNI 글과 일관됩니다

## PVC에서 CSI 준비로 이어지는 흐름

B27의 도입·기본 호출 경로·다른 글 연결 문단을 읽고 B02와 대조했습니다
CSI 글은 sidecar Controller RPC와 kubelet Node RPC를 순차적인 직접 호출처럼 그리지 않고 상태를 보고 각자 드라이버를 호출한다고 설명합니다
attach·stage·publish 글은 같은 노드의 두 Pod라는 기존 사례를 유지하고, attach/stage 생략 조건과 publish 호스트 경로 뒤 runtime 노출을 먼저 한정합니다
따라서 PVC Bound·VolumeAttachment attached·Pod target 준비·컨테이너 경로 노출을 같은 완료로 줄이지 않습니다
CNI와 CSI의 비교도 인터페이스 계약과 구체적인 daemon 배치를 구분합니다

## 이름 조회·외부 진입·네트워크 정책

B24~B26의 도입과 관련 글 연결 문단을 읽었습니다
DNS는 resolver의 후보 질의와 재시도, traffic locality는 Service의 후보 제한·선호와 주소군을 다뤄 이름 해석과 전달 대상을 구분합니다
Ingress/Gateway는 설정 역할과 실제 처리기, CCM은 클라우드 API와 Kubernetes 상태를 조정하는 주체를 설명합니다
CCM 경로를 모든 CNI의 필수 데이터 경로로 연결하지 않는다는 한정도 유지됩니다
표준 NetworkPolicy의 허용 합집합을 관리자 정책의 우선순위·거부·위임에 그대로 일반화하지 않습니다
NAT 전후 정책 판정 순서는 구현 조합에 달린다는 조건을 Service 연결 문단에 남깁니다

## 스토리지 수명·변경·배치의 단위

B28·B29의 도입과 관련 글 연결 문단을 B02·B27과 대조했습니다
StatefulSet은 PVC를 생성·보존할 관계를 정하고, PV 컨트롤러/provisioner는 바인딩·공급을 맡습니다
확장 글은 PVC 요청 수락과 실제 사용 용량 확대를 나누며, CSI의 Controller/Node 호출 책임을 이어 설명합니다
개수 상한은 노드·드라이버별 고유 볼륨 수이므로 publish target 수와 다릅니다
공급 용량은 아직 없는 볼륨의 바이트이며, WFFC 동적 공급과 드라이버 참여 조건 안에서 검사합니다
용량 정보 오브젝트의 소유 참조와 StatefulSet PVC 수명·실제 볼륨 소유권도 서로 구분합니다

## CRD와 라이브러리·별도 API 서버

B30~B32의 도입과 연결 문단을 읽었습니다
CRD는 API 데이터 구조·검증·저장을 선언하고 controller는 실제 조정을 맡습니다
CRD 저장 목표 변경은 기존 저장본 이행과 다르며, 내장 API 직렬화·저장 변환 글에서 구분한 표현/바이트/암호화와 혼동하지 않습니다
일반 reconcile 글은 캐시 시차와 큐·expectations의 원리, controller-runtime 글은 Manager/Controller/Reconciler에 나눈 라이브러리 구성을 맡습니다
aggregation은 CRD가 제공하지 않는 저장·서빙 요구에서 시작하며 실제 지원은 확장 서버 구현에 달렸다는 조건을 유지합니다

## 정책 수단과 확장 선택

B33의 도입·관련 글 연결 문단을 읽었습니다
정책 계층 글은 요청 중 거부/변경과 저장 뒤 조정을 구분하고, 종합 글은 네 요구 사례에서 실제로 필요한 운영 책임을 비교합니다
NetworkPolicy 저장과 집행, 정책 생성물과 GitOps 추적/prune, CRD와 별도 저장소, 재조정과 외부 작업 멱등성을 본문에 다시 필요한 만큼 설명합니다
종합 글이 개별 설정 표를 모두 반복하거나 선행 글 링크만으로 필요한 조건을 대신하지 않습니다

## 커널 심화 다섯 글의 연결

B34~B36의 도입·관련 글 연결 문단을 읽었습니다
CPU quota는 QoS 변환 이후의 기간별 실행 예산과 부모 제한을, 페이지 캐시는 관측 working set과 회수 비용·OOM 범위를 맡습니다
Netfilter는 Service 전달을 일반 IPv4/iptables 경로로 한정하고 hook·conntrack에 남는 상태를 설명합니다
namespace는 sandbox의 프로세스 종료·커널 객체 참조·runtime 정리를 나누며, 임시 컨테이너의 PID 대상 선택을 런타임 지원과 연결합니다
mount 글은 stage/publish의 경로 차이를 파일시스템 트리·bind mount·전파로 설명합니다. stage 지원 조건은 링크 밖 본문에도 남깁니다
Kubernetes API 상태, 사용자 공간 설정, 커널 동작, 관측 값을 하나의 완료나 같은 숫자로 합치지 않습니다

## 독립 검토 반영을 통한 연결 보완

B05의 Policy·Binding 설명 링크가 실제 관련 내용을 다루는 webhook/CEL 글을 가리키도록 반송·수정했습니다
webhook 글의 멀어진 ‘이 문제’는 동시 요청의 총량·유일성 문제라고 명시하도록 수정했습니다
이 변경은 단순 링크 경로 존재 검사만으로 찾을 수 없는 연결 대상과 지시어의 의미 문제입니다
최종 SHA와 검토 완료 여부는 `status.json`으로 별도 확인합니다

## 최종 확인

독립 검토에서 반송한 선행 개념·지시어·절 범위·연결 대상 문제를 수정 담당자가 보완했고 검토자가 해당 부분과 앞뒤 흐름을 다시 읽었습니다
메인도 인증의 기본 결과와 토큰 세부 조건, HPA의 Update와 SSA 도입 순서, eviction의 memory.available 절 범위, CRD의 첫 GVK 설명 등을 수정 후 연결부와 함께 재확인했습니다
본문에서 필요한 최소 정의를 제공한 뒤 심화 링크를 두는 원칙을 유지하며, 링크 존재 여부만으로 자립성을 판정하지 않았습니다

71편의 도입·기본 사례·관련 절에서 같은 개념을 다시 설명하는 목적을 대조했습니다
별도 보조 검사에서도 새로 늘어난 100자 이상 동일 산문 단락은 0개였습니다. 이 검사는 코드·표·인용·출처를 제외한 문자열 비교이며 의미 중복에 대한 위 판단을 대신하지 않습니다
최종 집계는 수정 71/71, 독립 검토 71/71, 미해결 편집 사항 0건이며 현재 본문·수정 기록·독립 검토 기록의 SHA256이 모두 일치합니다
