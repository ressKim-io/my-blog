## 편집 전 전문 독해와 연결 계획

device-resource-allocation 전문·검토서 독해. 확장 자원 검증→NodeResourcesFit→등록·목록·Allocate의 기존 기본 흐름을 유지합니다. 도중 QoS·unhealthy·NUMA 상세를 뒤로 옮겨 device plugin 뒤 DRA의 목록/claim/예약/API/노드 준비를 바로 연결합니다. 이후 NUMA와 CPU·Memory Manager, QoS 및 건강 상태를 실행 시의 추가 조건으로 모읍니다. 기본 정수 경로에서 DRA 위임이 가능하다는 범위 한정은 첫 절에 유지합니다

## 실제 변경


- 기본 device plugin과 DRA 준비 경로를 연속 배치했습니다. NUMA의 첫 언급은 서버 안의 CPU·메모리와 장치 위치라는 역할을 덧붙였습니다
- NUMA·전용 자원 조건·QoS·unhealthy 설명은 두 할당 흐름을 마친 뒤에 모았습니다

## 미채택 제안과 이유

등록을 스케줄러 검사보다 반드시 먼저 읽도록 재배치하지는 않았습니다. 첫 그림이 전체 관계를 보여 주며, 수량을 읽는 스케줄러 뒤 그 수량과 ID 목록을 제공하는 계약으로 내려가는 기존 흐름이 자연스럽습니다

## 보존 대조와 기술 확인

- baseline 대비 front matter·fenced code·링크/그림·inline code 다중집합 보존 검사 실행 완료
- DRA 위임·기능 gate·ResourceSlice 완전성·예약 경합·CDI·optional operations·NUMA 정책 조건 유지
- 새 기술 검증 및 build·런타임 테스트 실행 안 함
- 수량 충분/ID 할당/노드 준비/컨테이너 시작의 실패 경계와 allocation 후 노드 준비 조건을 본문에서 확인했습니다

## 독립 검토 반영

R1: 기존 CDI 역할 정의를 Allocate 응답 표 바로 뒤로 옮겼습니다. 후반 DRA 준비 절에는 런타임의 CDI 명세 조회와 지원 조건·주입 채널 상세를 남겨 첫 역할과 상세가 이어지도록 했습니다
