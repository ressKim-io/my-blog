# B14 수정 기록

담당: editor_b

## 편집 전 전문 독해와 연결 계획

- scheduling-binding-cycles: 원문 전문·검토서 독해. 노드 선택 뒤 assume과 Permit 대기, Binding 쓰기로 이어지는 기존 설명을 보존합니다. Filter 직후의 후보 수 계산은 Binding 성공·실패를 이해한 뒤로 이동하고, PreEnqueue의 상세는 그 뒤 재시도 큐 앞에 둡니다. 확장점 정의는 첫 Filter 설명에 남깁니다. 기본 Pod 범위와 gate 조건은 앞에 유지합니다
- scheduling-constraints: 원문 전문·검토서 독해. nodeAffinity와 taint의 두 방향, cache Pod의 topology 그림은 그대로 연결합니다. 300초·DaemonSet 상세를 배치 뒤 변경 절로 옮기고, spread는 기존 5개 사례의 배치 전후 개수를 먼저 짚은 뒤 기호를 설명합니다
- preemption-pdb: 원문 전문·검토서 독해. 첫 흐름의 다음 시도 대기까지 유지하고 일반 DELETE와 Eviction API의 차이를 PriorityClass보다 먼저 연결합니다. 한 노드의 제거·reprieve를 먼저 완료한 다음 후보 목표 수 최적화를 설명합니다. Eviction 예외와 예산 상태·drain은 후반의 실제 집행 설명에 남깁니다

## 실제 변경


- scheduling-binding-cycles: PreEnqueue 상세와 후보 수 최적화를 실패 정리 뒤로 이동했습니다. 확장점 정의는 Filter 앞에 두고 기존 assume·Reserve·Permit 시간 그림과 Binding 설명을 연속해서 읽도록 했습니다
- scheduling-constraints: 기본 toleration 상세를 배치 후 변경에 연결했습니다. 기존 5개 사례의 새 Pod 추가를 식 앞에서 설명했습니다
- preemption-pdb: Eviction API 정의와 PDB 집행 경계를 첫 흐름 뒤로 옮겼습니다. 후보 목표 수는 한 노드 희생자 선정 뒤로 옮겼습니다

## 미채택 제안과 이유

- scheduling-binding-cycles의 시간 그림은 Permit 절에 유지했습니다. 그림이 사용하는 Permit 대기 역할을 설명한 바로 다음 위치가 자연스러우며, 기본 흐름을 끊던 후보 수 계산을 옮기는 것으로 시간 관계를 연속해 읽을 수 있습니다
- preemption의 미준비 Pod 예외·drain과 세부 예산 계산은 앞당기지 않았습니다. 앞부분에서는 강제 여부를 구분하고 실제 예산 집행에서 조건을 함께 읽도록 했습니다
