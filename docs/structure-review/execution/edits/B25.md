## 편집 전 전문 독해와 연결 계획

### k8s-theory-ingress-gateway-api

원문 전문과 검토서를 읽었습니다. ingressClassName·IngressClass·controller의 관계 두 문장은 초반에 남기고, 레거시·기본 클래스·다중 기본값의 문서 차이는 후반 독립 절로 옮깁니다. 역할 분리 → parentRefs/allowedRoutes → ReferenceGrant를 연결한 뒤 TLS 구간 설명을 둡니다. 인증서 교차 참조 허가를 읽은 직후 구간별 암호화 설정을 비교하도록 하며, CRD·구현 지원·status의 기존 관계는 유지합니다

### k8s-theory-cloud-controller-boundary

원문 전문과 검토서를 읽었습니다. 네 컨트롤러 책임 표와 개요만 도입 뒤로 옮겨 전체 역할을 먼저 제시합니다. Node 초기화 → cloud node lifecycle → route controller를 연속 배치합니다. 각 컨트롤러 주기 수치는 이 Node 경로들을 설명한 뒤 독립 보충으로 둡니다. LB는 저장 시점 뒤 class의 처리자 선택을 설명한 다음 finalizer를 포함한 생성·삭제 경로를 먼저 닫고, class 변경 검증·pending 표시·백엔드 조건으로 확장합니다. 결과를 바꾸는 nil class 조건은 기본 경로 앞에 남깁니다

## 실제 변경

- Ingress 클래스 관계는 앞에 남기고 레거시·기본 선택 상세는 TLS 뒤의 보충 절로 옮겼습니다. Gateway 역할과 부착·교차 참조를 이어 읽게 했습니다
- CCM 역할 표를 앞에 두고 Node의 초기화·연락/존재·경로 관리를 묶었습니다. LB 처리자 선택의 기본 조건 후 생성·삭제를 완결하고 class 변경과 pending을 연결했습니다

## 미채택 제안과 이유

Ingress의 기본 HTTP·TLS 표현 범위와 참조 편집/Secret 읽기 권한 구분은 역할 분리의 문제를 만드는 조건이라 처음 위치를 유지했습니다. CCM의 nil class 조건은 신규 처리 주체를 바꾸므로 LB 기본 경로 앞에 유지했고 후보 노드 세부는 기존처럼 기본 생성·정리 뒤에서 읽게 했습니다

## 보존 대조와 기술 확인

baseline의 front matter·코드 블록·링크·이미지 경로·인라인 코드 보존을 검사했습니다. 이동한 절 전후를 재독해 참조선과 패킷 경로, allowedRoutes와 ReferenceGrant, taint와 finalizer의 동작 차이·pending의 한계를 확인했습니다. 새 기술 검증은 하지 않았습니다. 빌드·실행 테스트는 실행 안 함
