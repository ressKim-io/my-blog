# B16 수정 기록

## 편집 전 전문 독해와 연결 계획

- qos-cgroups: 전문·검토서 독해. 100m/500m 가정에서 QoS와 cgroup 변환·CPU/메모리 반응으로 이어지도록 미지정 request와 API defaulting을 후반으로 옮깁니다. allocatable과 kubepods 한도의 차이는 CPU/메모리 제어 다음에 둡니다. Pod-level은 실제 QoS 판정을 바꾸므로 해당 주장 옆에 유지합니다
- resource-accounting-scoring: 전문·검토서 독해. 일반 컨테이너·init·sidecar 집계와 Pod-level 대체를 RuntimeClass YAML 앞에 둡니다. scoringStrategy의 설정 위치와 schedulerName 연결을 전략 소개 앞에 두고 프로파일 제약은 후반에 유지합니다. kubectl helper 옵션은 노드 선택 흐름을 마친 뒤 읽습니다
- node-swap: 전문·검토서 독해. 기동/정책→자격→상한→cgroup v2는 유지합니다. 같은 Burstable Pod의 컨테이너 차이를 자격 표에 바로 연결하고, 배치·축출 설명을 cgroup v1과 tmpfs 탐지보다 먼저 둡니다

## 실제 변경


- 계획한 절 이동을 적용했습니다. qos-cgroups는 명시된 선언에서 실행 제어까지 이어지고, 이후 누락/defaulting 예외를 읽도록 했습니다
- resource-accounting-scoring은 요청 집계를 먼저 설명하고 실제 설정 주체를 세 전략보다 앞에서 밝혔습니다. 기존 A/B 후보·균형 점수 가정은 유지했습니다
- node-swap은 자격 표 다음에 동일 Pod 내 컨테이너 차이를 두고 QoS의 상세 판정을 별도 소절로 연결했습니다

## 미채택 제안과 이유

- QoS 분류의 Pod-level 조건은 뒤로 빼지 않았습니다. 분류표 바로 아래에 실제 분류 경로가 달라지는 조건을 남겨야 합니다
- resource-accounting-scoring의 새 수치 예제는 만들지 않았습니다. 실행 단계별 합/최댓값의 기존 번호 목록과 이후 A/B 수치 예제가 각각 역할을 설명합니다
- swap의 QoS 재정의는 링크로 축약하지 않았습니다. Pod-level·컨테이너 수준 판정 차이라는 원문 사실을 보존하고 독립적으로 읽을 수 있도록 남겼습니다

## 보존 대조와 기술 확인

- baseline 대비 front matter 전체·fenced code·링크/그림·inline code 다중집합 누락 없음 확인
- 수치·가정·버전·소스·예외·불확실성은 원문 단락에 유지했습니다. 기술적 정확성의 신규 검증은 실행하지 않았습니다
- Python 3 대조 검사 실행 완료. build·런타임 테스트는 담당 제한으로 실행 안 함
- 독자 질문: request/limit/allocatable/cgroup 역할, QoS와 OOM 생존 보장 차이, init/sidecar 동시 실행 집계, 플러그인 합산, 기동 허용과 swap 사용의 차이, swap이 배치 메모리를 늘리지 않는 이유를 본문에서 확인했습니다
