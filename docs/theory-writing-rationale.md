# Kubernetes 이론 글을 개선한 이유와 유지할 편집 기준

2026-10-25부터 26일까지 Kubernetes 이론 71편의 설명 순서를 고치고, 8편에 보조 그림을 추가했습니다
목표는 **해당 내부 원리를 처음 배우는 독자가 글을 앞에서부터 읽으며 주체·동작·결과를 연결할 수 있게 하는 것**이었습니다

이 문서는 Codex와 Claude가 다음 이론 글을 작성하거나 수정할 때 같은 판단을 이어가기 위한 기록입니다
문체는 [공통 말투와 편집 기준](writing-voice.md)을 따르고, 글마다 필요한 설명 순서는 원문과 독자의 질문에 맞춰 결정합니다

## 구조를 고쳐야 했던 이유

이번 검토의 독자는 Pod·Deployment 등을 사용해 봤지만 내부 구현은 처음 배우는 사람입니다
API를 사용한 경험만으로 컨트롤러의 캐시, 커널 통계의 집계 범위, 저장 단계의 차이까지 알고 있다고 가정할 수 없습니다

구조 검토에서는 기본 동작을 알기 전에 세부 조건을 만나거나, 용어의 역할을 뒤에서야 알게 되는 전개를 보완했습니다
개별 문장의 근거가 있어도 독자가 그 문장을 이해할 준비가 되어 있는지는 별도로 확인해야 했습니다
개념·설정·구현·관측을 오갈 때도 지금 설명 수준을 바꾸는 이유와 앞 동작의 관계가 필요했습니다

실제 PVC 글의 첫 본문은 클래스 미지정·빈 문자열·기본 클래스 소급 지정 같은 분기로 시작했습니다
정상적인 PVC와 PV의 연결을 보기 전에 선택 조건과 예외부터 배워야 했고, 제목의 중심인 claimRef 선기록 이유는 뒤에 있었습니다
그래서 역할을 구분한 뒤 하나의 기본 바인딩 사례를 끝까지 따라가고, 동적 공급과 WFFC·세부 조건을 그 사례에 연결하도록 바꿨습니다
[편집 전 검토서](structure-review/posts/k8s-theory-pvc-storageclass-binding.md)에 당시 순서와 문제 이유가 남아 있습니다

편집 후 독립 검토에서도 추가 문제가 나왔습니다
VolumeAttributesClass의 이름 매칭을 설명하면서 이 오브젝트의 역할이 충분히 소개되지 않았습니다
StorageClass와의 역할 차이를 해당 표 앞에 보완하고, 버전과 nil·빈 값 비교 조건을 유지했습니다
이 사례는 검토서의 권장 순서를 구현한 뒤에도 실제 독해가 필요한 이유입니다
[파일럿 재검토 기록](structure-review/execution/reviews/B02.md)에 반송과 해결 근거가 있습니다

## 설명 순서를 정한 기준

먼저 글의 중심 질문과 하나의 기본 사례를 정합니다
독자가 현재 알고 있는 것에서 다음 설명으로 넘어갈 수 있는지, 기존 문단을 어떤 순서로 연결할지 결정한 뒤 편집합니다
이미 자연스럽게 이어지는 사례와 설명은 유지합니다

| 판단할 부분 | 적용 기준 |
|---|---|
| 개념의 첫 등장 | 다른 내용을 설명하는 데 쓰기 전에 역할과 필요한 최소 정의를 제공합니다 |
| 기본 사례 | 요청·주체·상태 변화·결과가 연결된 흐름을 먼저 완성합니다 |
| 중요한 조건 | 기본 결과를 바꾸는 조건과 적용 범위는 해당 주장 옆에 둡니다 |
| 구현 세부와 예외 | 그 차이를 알아야 할 이유가 생긴 뒤 기본 동작과 연결합니다 |
| 예제의 관점 | 대상·주소·수치·시점·관찰 주체를 유지하고 바뀌면 이유와 대응 관계를 설명합니다 |
| 다른 글 링크 | 핵심 설명에 필요한 최소 개념을 본문에 남긴 뒤 심화 내용을 연결합니다 |
| 분량 | 필요한 기전·조건은 충분히 설명하고 같은 요약·예고·연결 문장의 반복은 덜어냅니다 |

위 기준을 모든 글의 고정 목차로 사용하지 않습니다
항상 같은 도입·문제 제기·목차·요약·마무리를 붙이거나, 검토서의 연결 문장 예시를 복사하면 실제 문맥과 어긋날 수 있습니다
헤더만 재배열해서는 문단의 전제나 사례의 흐름까지 고칠 수 없으므로 원문 전문과 그림·표·코드를 함께 읽습니다

## 쉽게 읽히게 바꾸면서 보존한 것

기술 사실·버전·고정 소스 ref·출처·코드·수치·가정·불확실성은 보존했습니다
원문에 없는 개인 경험, 실패, 실험 결과, 성능 수치를 추가하지 않았습니다
새 예시가 필요할 때는 가정임을 밝히고 기존 근거가 설명하는 조건 안에서 구성했습니다

API 요청 수락, 저장 완료, 컨트롤러의 후속 조정, 노드에서의 실제 실행, 관측값 갱신은 서로 다른 단계일 수 있습니다
예를 들어 PVC의 Bound를 attach·mount 완료와 합치거나, HPA의 추천값을 실제 Ready Pod 수로 표시하면 설명은 짧아져도 의미가 달라집니다
이런 차이는 관련 주장 옆에 남겼습니다

원문 자체의 기술적 의문은 구조 편집만으로 해결했다고 처리하지 않습니다
이번 작업의 [기술 재확인 목록](structure-review/execution/technical-followup.md)도 그대로 보존했습니다
새 주장을 추가하거나 기존 주장을 정정할 때는 해당 버전의 공식 문서·소스와 필요한 실행 근거를 별도로 확인해야 합니다

## 그림을 더한 이유와 선택 기준

구조 개선이 끝난 71편에는 이미 고유 SVG 145장이 있었습니다
그림을 추가할 때는 기존 자산을 먼저 확인하고, 문장이나 기존 흐름도만으로 독자가 머릿속에서 재구성해야 하는 관계를 골랐습니다

| 추가한 그림 | 드러내려는 관계 |
|---|---|
| init·sidecar·앱의 자원 집계 | 순차 실행과 겹치는 구간, 자원별 요청 최댓값 |
| HPA 축소 안정화 창 | 시간이 흐르며 창 밖으로 나가는 추천값과 선택 결과 |
| usage와 working set | 통계에서 제외한 캐시와 실제 메모리 사용의 차이 |
| NUMA 배치 | 서버 한 대 안에서 CPU·메모리·장치가 놓인 위치 |
| conntrack과 NAT | 같은 연결의 요청·응답에서 변하는 주소·포트 |
| VXLAN MTU | IP MTU 경계 안팎과 각 헤더가 차지하는 공간 |
| CRD 가지치기 | 스키마 경계에 따라 남거나 제거되는 필드 |
| 스냅샷 복원 | API 오브젝트·스토리지 실물·새 볼륨의 대응 관계 |

추가 후 고유 SVG는 153장이 됐습니다
8장은 이번 원문을 읽고 고른 결과이며, 글당 그림 수나 전체 추가량의 기준으로 사용하지 않습니다
이미 관계를 잘 보여주는 기존 그림과, 표나 짧은 설명으로 충분한 부분은 유지합니다
[그림 목록과 제작 기록](structure-review/diagrams/README.md)에서 실제 자산을 확인할 수 있습니다

그림에도 본문과 같은 기술 조건이 필요합니다
예를 들어 HPA의 7·3은 추천값으로 표시하고, working set의 뺄셈은 메모리 해제로 그리지 않았습니다
MTU 그림에서는 바깥 Ethernet을 IP MTU 예산 밖에 두었고, 스냅샷 복원은 원본을 되감는 대신 새 볼륨을 준비하는 관계로 표현했습니다
색만으로 의미를 구별하지 않고 라벨·선·해칭을 함께 사용했습니다

그림은 앞 문맥에서 필요한 질문이 생기는 위치에 넣습니다
그림 삽입을 위해 기존 내용을 다시 예고하는 문장을 자동으로 붙이지 않습니다
이번에도 Conntrack·MTU·스냅샷에 추가했던 반복 연결 문장 3개를 검토 후 제거했습니다
크기와 글자 수를 기계적으로 맞추는 대신 모바일·데스크톱에서 직접 렌더해 확인했습니다

## 수정과 독립 검토를 분리한 이유

수정자가 세운 순서에만 맞춰 읽으면, 실제 독자에게 필요한 전제가 빠져도 이미 알고 있는 내용으로 메울 수 있습니다
그래서 PVC 한 편을 먼저 수정하고 독립 검토·반송·재확인으로 편집 기준을 잡은 다음 나머지 작업 묶음을 진행했습니다
71편 전체가 36개 묶음이며 파일럿도 그 안에 포함됩니다

수정자는 담당 원문 전문과 검토서를 읽고 문단 연결 계획을 세웠습니다
독립 검토자는 먼저 글별 검토서를 보지 않고 수정 본문을 처음부터 끝까지 읽었습니다
그다음 원문과 검토서를 대조해 기술 내용·조건·코드·출처의 누락을 확인했습니다
병렬 작업에서는 담당 파일이 겹치지 않게 나누고 다른 담당자의 변경을 되돌리지 않았습니다

검토는 다음 질문으로 진행합니다

1. 지금 이 내용을 설명하는 이유가 앞 문맥에서 생겼는가
2. 아직 설명하지 않은 개념으로 다른 내용을 설명하고 있지 않은가
3. 기본 사례의 흐름이 끝나기 전에 구현 세부나 예외로 빠지지 않는가
4. 뒤의 설명을 알아야 앞부분을 이해할 수 있는 곳이 없는가
5. 개념·설정·구현·관측 사이를 이동할 때 연결이 자연스러운가
6. 예제의 대상이나 관점이 이유 없이 바뀌지 않는가
7. 지시어·그림·표·코드·절 참조가 이동한 문단과 맞는가
8. 선행 글 링크를 읽지 않아도 이 글의 핵심 설명을 이해할 수 있는가
9. 불필요한 요약·예고·반복 연결 문장이 설명을 늘이지 않는가

문제를 찾으면 위치·독자가 막히는 이유·수정 방향을 적어 원래 수정 담당자에게 돌려보냅니다
수정 후에는 해당 문장만 보지 않고 앞뒤 흐름을 다시 읽습니다
마지막으로 메인이 글 사이의 역할 분담·연결·중복을 확인합니다
수정 완료와 독립 검토 완료는 별도로 기록합니다

## 내용 검토와 실행 검증의 역할

독해 검토는 설명 순서와 의미의 연결을 확인하고, 원문 대조는 사실과 조건의 보존을 확인합니다
MDX·링크·lint·빌드는 파일이 올바르게 처리되고 게시될 수 있는지를 확인합니다
링크가 존재해도 엉뚱한 내용을 가리킬 수 있으므로 실행 검증만으로 본문의 이해 가능성을 판정하지 않습니다

| 단계 | 확인한 결과와 기록 |
|---|---|
| 본문 구조 개선 | 수정 71/71·독립 검토 71/71, [글 사이 연결 검토](structure-review/execution/integration-review.md)와 [실행 검증](structure-review/execution/verification.md) |
| 그림 추가 | 제작 8/8·독립 검토 8/8, [내용·시각 검토](structure-review/diagrams/independent-review.md)와 [실행 검증](structure-review/diagrams/verification.md) |
| 게시 확인 | 최종 커밋 `fc89af3`의 [자동 배포](https://github.com/ressKim-io/my-blog/actions/runs/40257019395)가 2026-10-26 11:03 KST에 성공했고, 실제 글 8편의 SVG 참조·응답·파일 일치와 모바일 375px·데스크톱 1280px 표시를 확인 |

위 결과는 구조·보존·렌더링·게시 검증의 범위입니다
실제 초보 독자의 학습 효과를 측정하거나 모든 기술 주장을 클러스터에서 재현한 결과로 확대하지 않습니다

## Claude와 Codex가 후속 작업에서 읽을 기록

이 문서로 편집 이유를 확인한 뒤, 요청받은 글의 현재 본문과 기존 그림부터 읽습니다
Kubernetes 71편의 구체적인 근거가 필요하면 [검토 문서 안내](structure-review/README.md)에서 대상 글의 검토서와 실행 기록만 찾아 읽습니다
다른 이론 글에도 독자의 선행 지식·설명 순서·조건 보존이라는 기준을 적용할 수 있지만, 이번 71편의 목차나 예시를 그대로 이식하지 않습니다

`docs/structure-review/posts/`와 `manifest.json`은 편집 전 기준입니다
`execution/`은 2026-10-25 본문 편집 시점, `diagrams/`는 2026-10-26 그림 추가 시점의 기록입니다
그림이 추가된 8편은 앞 단계의 본문 해시와 달라질 수 있으므로 기록 시점을 확인하고 현재 파일과 대조합니다
검사를 통과시키려고 과거 manifest·원문 해시·검토 해시를 덮어쓰지 않습니다

이 문서를 읽었다는 이유만으로 범위 밖 글을 일괄 수정하지 않습니다
적용 범위와 commit·push·배포는 현재 사용자의 요청과 기존에 유효한 승인을 따릅니다
